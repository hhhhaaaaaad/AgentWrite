## 零、核心设计决策（ADR）

### D-1 语料隔离粒度：per-config 派生 userId + finalize 清理（v12 修正）

**演进**：v11 用 `eval_user_id = BASE + hash(run_id)`——但 run_id 每 run 唯一，同 config 每次 run 换新命名空间，reset 清的永远是空命名空间 → **历史语料无限累积**。而 FULLTEXT 的 IDF 是全表统计、BM25 是混合检索常驻一路（无「exact 跳过 BM25」的 freeze 项），跨周期 IDF 随历史漂移击穿 AC#12。

**Decision（选定 per-config 派生）**：

```
eval_user_id = EVAL_USER_ID_BASE + (int(config_fingerprint[:8], 16) % EVAL_USER_ID_RANGE)
```

- **由 `config_fingerprint` 派生（非 run_id）**：同 config 的 run 共享同一命名空间；同 config 已被 `uq_runs_active_cfg` 强制串行，串行下 reset 天然清掉上次残留。
- **finalize 清理自身命名空间（先清空后释放）**：run finalize 阶段**先**清理自身 `eval_user_id` 的语料（`DELETE ... WHERE eval_user_id` + `removeByUserId`），**然后**才 CAS 置 succeeded/failed/cancelled 释放槽位（D-7 修正，见 §零 D-7）。使语料**不残留**，FULLTEXT IDF 长期稳定——「每次只一个 config 的语料在表」从近似变为真正成立。
- **不同 config 仍各自隔离**：保留并行 A/B（各自命名空间，互不干扰）。
- **IDOR 不变**：服务端派生、客户端不可传；Java 校验 `EVAL_USER_ID_BASE ≤ eval_user_id < BASE + RANGE`，越界拒绝。
- **id 漂移无关**：命名空间复用导致自增 id 漂移，但 Recall 用 contentHash 匹配，与 id 无关。

**次生约束（已知口径，诚实标注）**：并行 A/B（不同 config，不同命名空间）运行时，FULLTEXT IDF 对 A/B 双方**对称混合**（两 config 语料同表），exact 模式**绝对**指标有微小对称 IDF 偏移；相对对比仍有效。同 config 可复现 run 串行 + finalize 清理 → IDF 稳定，AC#12 不受影响。

**备选（fallback，写死触发条件）**：若 Java 侧硬约束「eval DB/collection 只能一个 user」（无法支持保留命名空间多 userId），退化 **corpus 级串行**：`uq_runs_active_corpus ON eval_runs ((1)) WHERE status IN ('pending','running')` 全局单飞 + Celery `--concurrency=1`。本方案按 per-config 隔离设计。

### D-2 存储隔离落地：独立 Java 实例（最终拍板）

**Decision**：存储隔离 A（专用 MySQL database + 专用 Qdrant collection + 专用 eval 用户）通过 **独立 Java 实例** 落地，不采用双 datasource 同实例路由。

- **形态**：另起一个 Spring Boot 实例，`memory.eval.enabled=true`，`spring.datasource` 指向专用 eval database、`memory.qdrant.collection` 指向专用 collection、业务 cron 全部禁用（`@ConditionalOnProperty(name="memory.eval.enabled", havingValue="false", matchIfMissing=true)` 挂在 5 个 `@Scheduled` 上）。
- **为何不选双 datasource**：`IMemoryRecordDao` 与 `IMemoryVectorStore` 当前各只注入一个 datasource/collection（`QdrantVectorStore` 单 collection、`SimpleMemoryVectorStore` 单 map）；双源路由需改 DAO/VectorStore 的 `@Primary` 注入与事务管理器，侵入业务代码、回归风险高。独立实例零侵入、隔离最彻底、符合「部署独立、逻辑不独立」。
- **成本口径**：额外一个 JVM（估算 512MB–1GB 堆，见 §十五 容量估算）。
- **唯一共享边界**：与业务实例共享同一套 jar/镜像与 DDL 迁移，仅配置不同，确保「测的就是线上那套逻辑」。

### D-3 zombie 防护：fencing token（最终拍板，替代 check-then-act 残余窗口）

**Decision**：破坏性阶段（reset/seed）的 fencing 采用 **fencing token**，从根上闭合 v12 遗留的 TOCTOU 窗口，不再把 per-stage check 当作兜底。

- **键控粒度（v15 修正，这是本轮最关键修正）**：fencing 的权威状态按 **`eval_user_id`（per-config 命名空间）** 键控，**不是 `run_id`**。因为破坏性写（reset/seed）操作的实体是 `eval_user_id` 命名空间，而「僵尸 A」与「后继 B」是同 config、**同 `eval_user_id`、但不同 `run_id`**。若按 `run_id` 键控，B 是全新 run、从不触碰 A 的 fencing 行，A 的旧 token 永远有效、仍能删 B 语料——只闭合了「同 run_id 双 worker crash-resume」，没闭合「僵尸→后继 run（异 run_id）」这一 D-3 自述要根治的场景。
- **机制（权威源下沉 Java）**：fencing 权威状态存 Java 侧 MySQL 表 `eval_fencing`（主键 `eval_user_id`），Python 的 Postgres 只存镜像供读取。Java 侧校验 token 与执行破坏性写在同一事务内原子完成。
- **acquire 用事务内读-改-写（v17 关键修正，替代 MySQL 语义上无效的 upsert+CAS）**：`POST /api/v1/eval/fencing/acquire` 携带 `{eval_user_id, expected_version, new_run_id}`。Java 侧在**同一事务内**：① `SELECT fencing_version, active_run_id FROM eval_fencing WHERE eval_user_id=:uid FOR UPDATE`（锁定读，串行化所有 acquire）；② **首行无行 → `INSERT` 建立 `fencing_version=1, active_run_id=:new_run_id`**（返回 version=1；事务隔离级别 pin 为 REPEATABLE READ，`FOR UPDATE` 取 gap lock 串行化首 acquire；极端下 `INSERT` 撞唯一键 `DuplicateKeyException` → catch 视作「已有行」→ 走对账 +1 分支）；**已有行 → 用 `expected_version` 对账当前 `fencing_version`**——不等则**回滚并返回 `{conflict, current_version}`**（Python 用 `current_version` 重试一次），相等则**无条件 `UPDATE eval_fencing SET fencing_version=fencing_version+1, active_run_id=:new_run_id WHERE eval_user_id=:uid`**（无 CAS WHERE），返回新 version。> 关键：并发已被 `uq_runs_active_user` + `uq_runs_active_cfg` 挡住（同 `eval_user_id`/同 config 至多一个 active run），acquire **不需要乐观锁的等值 UPDATE**；`FOR UPDATE` 锁定读后无条件递增即可。「对账 expected_version」只用于检测「Python 镜像已过期」并回传 current_version 供重试，不再依赖 `ON DUPLICATE KEY UPDATE`（其命中唯一键后只做 SET 赋值、无 WHERE 子句、无法判定 expected 过期，是无效 SQL）。
- **lease 接管 / run 开始的两步（钉死，v17 修正镜像基准）**：(1) Postgres CAS 抢 lease（`UPDATE eval_runs SET lease_owner=:me, heartbeat_at=now() WHERE id=:id AND status='running' AND lease_owner=:observed_owner AND heartbeat_at=:observed_heartbeat`，**不再在 lease 接管时 +1 fencing_version**）；(2) 调 Java acquire（读-改-写如上），acquire 返回新 version 后 **Python 写回 `eval_runs.fencing_version`**（镜像==权威，AC#23）。**每次 run 首次破坏性写前必 acquire**（pending→running 抢占后、reset 之前）；两步失败则放弃接管、告警、不执行破坏性写。
- **reaper 判死后的权威交接（v16 闭合后继 run 断裂）**：reaper 判死 run（CAS 置 failed）后，**同步调 Java `POST /api/v1/eval/fencing/release`**，原子 `UPDATE eval_fencing SET active_run_id=NULL WHERE eval_user_id=:uid AND active_run_id=:dead_run_id`（清空 active_run_id，fencing_version 不降）。后继 run B 接管时 acquire 的 `expected_version` 取「当前权威 fencing_version」，CAS 递增成功 → B 的 active_run_id 与 fencing_version 都更新，A 的旧 token（旧 version）随之失配。这样后继 run 不会因「active_run_id 仍是死 run A」而 403 卡死。
- **破坏性写校验（真正原子，锁定读，无行语义钉死，v17 补 run_id 数据源）**：reset/seed 请求 header 携带 `X-Eval-Fencing: {fencing_version}` **与 `X-Eval-Run-Id: {run_id}`**，Java 在**同一事务内** `SELECT fencing_version, active_run_id FROM eval_fencing WHERE eval_user_id=:uid FOR UPDATE`（锁定读，串行化校验与递增）——**若查无行（首次破坏性写前未 acquire）→ 403 拒绝并告警「fencing 未建立」**（不允许放行，防绕过）；有行则校验「`X-Eval-Fencing` == 当前 fencing_version 且 `active_run_id == X-Eval-Run-Id`」，通过才执行 `DELETE ... WHERE eval_user_id=:uid` / seed，不匹配 403。`FOR UPDATE` 保证「校验」与「acquire/release 的 version/active_run_id 变更」互斥。> 明确：`token == version` 单独已足以拒绝僵尸旧 token（version 单调递增，旧 token 必失配）；`active_run_id == X-Eval-Run-Id` 是冗余第二道，其 run_id 数据源来自 header 显式传参（**非从 eval_user_id 推导**，fencing 按 eval_user_id 键控、Java 无法从 eval_user_id 推出 run_id）。
- **为何强于 check-then-act**：check-then-act 的 `SELECT` 与后续 `DELETE` 之间非原子，zombie 通过检查后停顿超阈值，B 接管 seed，A 恢复 reset 仍会删 B 语料。fencing token 把校验下沉到 Java 破坏性写入口，A 的旧 token 在 B 接管（version+1）后必然失配，Java 侧拒绝执行——这是真正的原子 fencing。
- **与 per-stage check 的关系**：per-stage check 降级为「快速失败 + 观测」（仍保留，用于提前中止与告警），fencing token 才是硬防线。
- **为何必须下沉 Java**：per-config 派生下，同 config 的 run 共享同一 `eval_user_id` 命名空间，Java 无法仅靠「命名空间」区分新旧 run 的调用；只有 Java 持有按 `eval_user_id` 键控的 fencing 权威，才能在事务内区分并拒绝旧 run 的 token。
- **Java 改动量**：新增 `eval_fencing` 表（主键 `eval_user_id`）+ acquire 端点 + reset/seed 事务内 `FOR UPDATE` 校验，改动小、风险低。

### D-4 LLM-judge 纳入第一期（最终拍板，补齐注入质量维度）

**Decision**：LLM-judge（成对胜率 / 事实错误率）**纳入第一期**，不再后置；`eval_judge_jobs` 表从「后置」改为 Phase 4 交付。

- **理由**：注入质量维度（维度④）的「无关注入率」可用 budgeted score 近似，但「成对胜率」「事实错误率」是记忆系统「到底有没有用」的终极证明，缺了它们五维里有一维半是空心的，「反哺闭环是灵魂」也缺了最强的一条证据链路。
- **实现要点**：位置偏置消解（每个 pair 生成 A/B 与 B/A 两份，`position_swap` 标记，两份判断一致才采信）；模型适配器抽象 judge 后端（默认复用项目现有 DeepSeek，可切）；judge 结果异步落 `eval_judge_jobs`，不阻塞 run 主流程，run finalize 后按需补齐维度④。
- **成本口径**：judge 只对注入质量维度的抽样子集运行（见 §十五 成本估算），不是全量 pair。

### D-5 跨模型版本指标可比性分层（持久性核心，v14 新增）

**问题**：`config_fingerprint` 含 `config_hash`（= 模型版本），embedding 升级 → 新 config → 新命名空间 + 新趋势点。但不同 embedding 模型的 Recall/MRR/NDCG 绝对不可比（向量空间已变），抽取① 的 Precision/Recall 也随 LLM 抽取模型漂移。若不加区分，趋势图会把「模型升级」与「参数调优」混为一谈，「长期积累跨版本对比」这条 NFR 名存实亡。

**Decision：指标按「该指标对哪个模型维度敏感」推导分层**（用推导规则替代硬编码映射，v15 修正）：

**推导规则**：一个指标的「可比范围」取决于它是否依赖某个「随模型版本变化的分布/空间」。
- **绝对可比层**：指标只依赖「结构/内容键 + 明确判定规则」，不依赖 embedding 向量空间、不依赖 LLM 抽取/判断的生成分布。这类指标的数值由输入内容与确定性规则唯一决定，跨模型版本可连续比较。
- **相对可比层**：指标依赖 embedding 向量空间（检索② 全部指标）或 LLM 生成分布（抽取① 的 P/R、注入④、以及任何 judge 判定的指标）。

**分层结果（按规则推导，修正 v14 的自相矛盾）**：

| 层 | 指标（按依赖维度推导） | 依赖的模型维度 | 趋势线处理 |
|---|---|---|---|
| **绝对可比** | 一致性③（重复/冲突/一致率/过期残留）、治理⑤（误合并/漏隔离/撤销成功率）、**注入④ 的无关注入率**（budgeted score 确定性近似，不依赖 judge） | 仅确定性规则（对账脚本 + Shadow Mode 只读 compute + budgeted score） | 跨 model、跨周期画连续趋势线 |
| **相对可比** | 检索②（Recall@5/MRR/NDCG/Hit@1）→ 依赖 embedding 空间；抽取①（P/R/**错误归属率/低价值写入率**）→ 依赖抽取 LLM；注入④（成对胜率/事实错误率）→ 依赖 judge | embedding 空间 / 抽取 LLM / judge | 按 model 分段，段内趋势，跨段「分段台阶」不连成线 |

> 关键修正：v14 把抽取① 的「错误归属率/低价值写入率」误归入绝对可比层，但它们与抽取 P/R 同源、都依赖 LLM 抽取分布，应一并归入相对可比层。分层判据是「该指标对哪个模型维度敏感」这一条统一规则，而非对每个指标逐个硬编码。

- **分段键修正（v16）**：相对可比层的分段键必须覆盖**每个指标依赖的模型维度**——检索②/抽取① 按 `config_hash`（含 embedding/reranker/抽取 LLM 配置）分段；**注入④ 的成对胜率/事实错误率额外按 `judge_model` 分段**（`judge_model` 是 per-job 字段，不在 `config_hash` 里，故维度④ 用 `config_hash + judge_model` 作为复合分段键）。绝对可比层不分段。
- **「无关注入率」归属统一（v16 修正自相矛盾）**：`无关注入率` 用 budgeted score 确定性近似计算（§3.5 已标「确定性」），**不依赖 judge**，归入**绝对可比层**；只有「成对胜率/事实错误率」依赖 judge，归相对可比层。三处口径统一为：无关注入率 = 绝对可比（确定性 budgeted score），成对胜率/事实错误率 = 相对可比（judge）。
- **落地**：`eval_runs.model_version_id` / `param_snapshot_id` 关联模型与参数，查询趋势时 join 得出 `config_hash`；维度④ 再 join `eval_judge_jobs.judge_model` 得复合分段键。前端对相对可比指标强制按对应分段键渲染，绝对可比指标画连续线。
- **反哺闭环的约束**：ground_truth 纠错 → content_digest 变 → 新 config。若仅 ground_truth 变而模型不变，相对可比指标仍属「同 config 内可比」（分布未变）；若模型也变，则检索/抽取/注入归入「跨 model 不可比」，只比绝对可比层。
- **可测试性（v16 修正）**：AC#22 / §13 步16 验证分类正确性——单测断言「错误归属率/低价值写入率」归相对可比层、「无关注入率」归绝对可比层（不依赖 judge）、「治理⑤」归绝对可比层；并断言「成对胜率」用 `config_hash + judge_model` 复合键分段。**注意：单测只能断言「实现与映射一致」，无法证伪「某指标对某模型维度敏感」这一规则本身——规则的正确性需通过模型变更实验验证**（列为 Follow-up）。

### D-6 可复现 run 的 exclusive 隔离（机制化 IDF 冲突，v14 新增）

**问题**：可复现 run（AC#13，同 config N≥3）要求「每次只一个语料在表 → IDF 稳定」，但 `uq_runs_active_cfg` 只串行**同 config**，挡不住并发**不同 config** 的 A/B run 把第二个语料放进 FULLTEXT 索引、扰动可复现 run 的全局 IDF。此前靠「操作纪律」约束，不构成机制。

**Decision：可复现 run 标记为 `exclusive`，机制化互斥**：

- `eval_runs` 增加 `exclusive BOOLEAN NOT NULL DEFAULT FALSE`（可复现 run 创建时置 true）。
- **互斥规则（两条，原子检查）**：若本 run `exclusive=true`，要求「当前不存在任何 `pending/running` 的其他 run」；若本 run `exclusive=false`，要求「当前不存在 `exclusive=true` 且 `pending/running` 的 run」。不满足则 409。
- **原子检查与占位（锁序修正）**：用单行 guard 表 `eval_run_guard(id=1, exclusive_owner UUID NULL, owner_run_id UUID, heartbeat_at TIMESTAMPTZ)`。创建 run 时在同一事务内 `SELECT ... FROM eval_run_guard WHERE id=1 FOR UPDATE`（单行锁定读，串行化所有 run 创建，覆盖「扫描 eval_runs 无其他 active」的检查），再按互斥规则判定并写入 `exclusive_owner`。普通 A/B（互不 exclusive）只在创建瞬间竞争这一行、事务极短，不影响「并行 A/B 运行期」。
- **回收路径（v15 关键修正，闭合槽位泄漏）+ 心跳源对齐（v17）**：`eval_run_guard` 是**权威互斥态，必须可回收**——(1) run 正常 finalize（**先清理命名空间、后 CAS 置 succeeded**）在置 succeeded 的同一事务内 `UPDATE eval_run_guard SET exclusive_owner=NULL, owner_run_id=NULL WHERE owner_run_id=:me AND exclusive_owner IS NOT NULL`；(2) reaper 判死 stale run 后同样回收；(3) `heartbeat_at` 由持有者定期心跳，reaper 发现 `exclusive_owner` 非空但 `heartbeat_at` stale 时，判定 owner run 已死并回收（避免崩溃导致的永久 409）。> **心跳源对齐（v17 闭合 MEDIUM + v18 补事务原子性）**：`eval_run_guard.heartbeat_at` 由持有 worker 的**同一心跳任务**在**同一事务内**同时更新 `eval_runs.heartbeat_at` 与 `eval_run_guard.heartbeat_at`（两表同在 Postgres，单事务提交，防双写非原子导致 run fresh / guard stale），stale 阈值与 run 心跳**同一套**；reaper 对 guard 的 stale 判定复用同一阈值，避免两套心跳阈值不一致或双写非原子导致误回收活跃 exclusive run 的独占权（破坏 AC#13/AC#24）。
- **效果**：可复现 run 期间全局独占，IDF 稳定成立；普通 A/B 运行期照常并发。互斥从「操作纪律」升级为「数据库不变量 + 可回收」，杜绝永久死锁。

### D-7 per-config 哈希碰撞降级：正确性→吞吐抖动（v14 新增）

**问题**：`eval_user_id = BASE + hash(config_fingerprint[:8]) mod RANGE` 是 32-bit 哈希 mod RANGE，两个**不同 config** 可能碰撞到同一 `eval_user_id`。若碰撞后仍各自 reset，会重新引入互删（正确性风险）。

**Decision：碰撞的正确性风险通过唯一索引降级为吞吐抖动**：

- 加 `uq_runs_active_user ON eval_runs (eval_user_id) WHERE status IN ('pending','running')`——任一时刻一个 `eval_user_id` 只能有一个 active run。
- **碰撞后果降级**：哈希碰撞时，两个不同 config 因该唯一索引冲突而 409 串行化（安全降级，绝不互删），最坏是「偶发串行化」而非「数据互删」。
- **finalize 清理窗口闭合（v15 关键修正，闭合 M2）**：v14 的「绝不互删」在 finalize 窗口失守——finalize 先 CAS 置 `succeeded`（唯一索引立即释放 `eval_user_id` 槽位），后继 run B 可在 A「清理命名空间」完成前取得同一 `eval_user_id` 并 seed，A 的延迟清理会删掉 B 的语料。修正为：**清理顺序反转**——finalize 阶段先清理自身命名空间（`DELETE ... WHERE eval_user_id` + `removeByUserId`），**然后**才 CAS 置 `succeeded`。即「先清空、后释放槽位」，槽位在清理完成后才释放，后继 run 取得 `eval_user_id` 时命名空间必已清空，晚到的 zombie 清理因 fencing token（按 `eval_user_id` 键控，D-3）失配而被 Java 403 拒绝。两者（fencing 键改 `eval_user_id` + 清理顺序反转）共同闭合互删。
- **碰撞概率约束（pin）**：生日碰撞概率 `P ≈ n²/(2·RANGE)`，取 `RANGE = 1_000_000`，并发不同 config 上限 n=100 时 P≈0.5%，且碰撞只降级为串行、不损失正确性。若未来并发 config 数增长，只需增大 RANGE，不改变机制。
- **`EVAL_USER_ID_BASE` 约束（pin）**：`BASE = 10_000_000`，业务 userId 走 BIGSERIAL 从 1 起，BASE 留足空间避开业务命名空间，`BASE + RANGE` 不越 `BIGINT`。

### 3.2 数据流（一次评测 run 的完整生命周期）

```
用户(前端) ──▶ FastAPI POST /runs {dataset_version, param_snapshot_id, mode}
                │ 1. 鉴权 + RBAC
                │ 2. Idempotency-Key 命中 → 比对 config_fingerprint：一致返回；不一致 409
                │ 3. 派生 eval_user_id = BASE + hash(config_fingerprint)（per-config 隔离，D-1/D-7）
                │ 4. exclusive run 抢占 guard（D-6）：事务内占位全局互斥，冲突 409
                │ 5. 写入 eval_runs(status='pending', config_fingerprint, eval_user_id, exclusive)
                │ 6. 投递 Celery run_eval_task(run_id)
                ▼
Celery worker 领取 run_eval_task(run_id) —— 状态分支 + CAS 抢占 + 心跳 + per-stage lease check
  │  pending → CAS 抢占
  │  running → 续跑前 fencing 检查（lease CAS + Java acquire 同步 fencing_version）
  │  破坏性阶段(reset/seed)在 Java 侧事务内校验 fencing token（D-3，原子拒绝旧 token）
  │  reset(物理删 MySQL + removeByUserId 向量库，仅自身 eval_user_id) ──▶ seed(幂等+catch DupKey)
  │    ──▶ 向量就绪屏障(hnsw) ──▶ 五维 ──▶ finalize(先清理命名空间 → 调 fencing/release 交接 → CAS succeeded 释放槽位)
  ▼
前端轮询 GET /runs/{id}

（后台）Celery beat reaper：stale heartbeat → revoke(terminate) + CAS failed
```

### 3.3 异步任务编排 —— 四件语义分离 + per-config 隔离 + 单飞（全 CAS pin）

**四件语义分离**：

| 语义 | 载体 | 机制 |
|---|---|---|
| run 身份 | `eval_runs.id`（UUID） | 一个 run = 一次执行 |
| 配置指纹 | `config_fingerprint`（非唯一） | `md5(join('|',[params_hash, config_hash, content_digest, mode]))` |
| 双击幂等 | `Idempotency-Key` → `idempotency_key` 唯一 | 命中比对 fingerprint，一致返回，不一致 409 |
| 并发护栏（同 config） | 部分唯一索引 | `WHERE status IN ('pending','running')` |

**per-config 隔离（跨 config 并发安全 + 语料不残留）**：`eval_user_id` 由 `config_fingerprint` 派生（§零 D-1）；finalize 后清理自身命名空间。同 config 串行（`uq_runs_active_cfg`）→ 语料不累积；不同 config 各自命名空间 → 并行 A/B 安全。

**CAS 谓词全 pin**：

| 操作 | CAS 谓词（pin 死） | 作用 |
|---|---|---|
| 抢占 pending→running | `UPDATE ... SET status='running', lease_owner=:me, heartbeat_at=now(), started_at=now() WHERE id=:id AND status='pending'` | 唯一 worker 抢 pending |
| lease 接管（crash-resume） | `UPDATE ... SET lease_owner=:me, heartbeat_at=now() WHERE id=:id AND status='running' AND lease_owner=:observed_owner AND heartbeat_at=:observed_heartbeat` | 两 worker 同抢 stale 时，只有 observed 匹配者成功；**随后 Java acquire 返回新 version，Python 写回 `eval_runs.fencing_version` 镜像（非 lease 接管时 +1）** |
| fencing acquire（Java，事务内读-改-写） | `SELECT ... FOR UPDATE` 锁定读；无行 `INSERT` 建行（version=1）；有行对账 expected_version 后无条件 `UPDATE ... SET fencing_version=fencing_version+1, active_run_id=:new_run_id WHERE eval_user_id=:uid`（无 CAS WHERE）；不等则返回 `{conflict, current_version}` | 权威源在 Java，按 eval_user_id 键控；expected_version 来自 `GET /fencing/{eval_user_id}`，Python 用 current_version 重试一次 |
| fencing release（Java） | `UPDATE eval_fencing SET active_run_id=NULL WHERE eval_user_id=:uid AND active_run_id=:dead_run_id` | **finalize 与 reaper 判死后都调用**，清 active_run_id，后继 run 可接管 |
| 破坏性写（Java 事务内） | `SELECT fencing_version, active_run_id FROM eval_fencing WHERE eval_user_id=:uid FOR UPDATE`；**无行→403「fencing 未建立」**；有行校验 header `X-Eval-Fencing`==version 且 `active_run_id`==header `X-Eval-Run-Id` 才 DELETE/seed，否则 403 | 锁定读 + 原子拒绝 zombie 旧 token（D-3，根治 TOCTOU）；run_id 来自 header 显式传参 |
| per-stage lease check | 破坏性阶段前 `SELECT lease_owner, heartbeat_at WHERE id=:id`；`lease_owner != :me` 或 stale → 中止 | 降级为「快速失败 + 观测」，非硬防线 |
| finalize | **先清理自身命名空间（复用 `/eval/reset` 端点，携带 `X-Eval-Fencing` + `X-Eval-Run-Id`，走事务内 FOR UPDATE 校验）** → **调 fencing/release 清 active_run_id** → **然后** `UPDATE ... SET status='succeeded', finished_at=now() WHERE id=:id AND status='running' AND lease_owner=:me` | 不复活判死 run；**先清空（fencing 守卫）、后 release 交接、再释放槽位**（D-7 + v17 + v18：finalize 清理必须走 fencing 守卫，否则 zombie 晚到 finalize 删后继语料） |
| reaper 判死 | `UPDATE ... SET status='failed', error_message='reaped', finished_at=now() WHERE id=:id AND status='running' AND heartbeat_at=:observed_stale_heartbeat`，**随后调 fencing/release 清 active_run_id** | 比对 stale 心跳避免误杀；判死后交接 fencing 权威 |

**阶段幂等**：

| 阶段 | 幂等保证 |
|---|---|
| reset | MySQL `DELETE FROM` + 向量库 `removeByUserId`（仅自身 eval_user_id） |
| seed | check-then-return + `catch DuplicateKeyException → existed` |
| 指标 | 确定性 + 结果 upsert（两表 UNIQUE + ON CONFLICT） |
| Recall | contentHash 直接匹配，无 createdId |

**状态机与重试**：

| 关注点 | 设计 |
|---|---|
| 重试 vs 续跑 | transient 重试与崩溃续跑统一；确定性失败 `FAILED` 不重试 |
| 卡死恢复 | reaper heartbeat-based + `revoke(terminate=True)` + CAS |
| 取消 | `CANCELLED` + 阶段间检查 + `revoke` |
| 不丢 | `task_acks_late=True` + `task_reject_on_worker_lost=True` |
| 不重 | `idempotency_key` 唯一 + body 一致性 |
| 不并发 | per-config 隔离（跨 config）+ 部分唯一索引 + CAS + fencing（同 run） |

### 3.4 检索评测：contentHash 直接匹配 + exact 模式算法澄清

- `MemoryRetriever.MemoryItem`（`:517`）已带 `content`；`MemoryItemDTO.content`（`:16`）已在 DTO。
- Recall 直接 `md5(retrieved.content) ∈ ground_truth.relevant_content_hashes`，无 createdId。
- `/eval/seed` 返回 `{"inserted","existed"}`；`/eval/search` 必须含 `content`。
- **contentHash 契约**：`content_hash = lowercase hex MD5(UTF-8 bytes of exact content)`，无规范化；语料 ≤ 512 字符；`ground_truth` 由 seed payload 同一字符串派生；与 `MemoryRecord.content_hash` 同一函数。
- **exact 模式算法澄清（Minor #5）**：exact = 冻结 6 要素 + `exact:true` **向量检索**（Qdrant 全扫，非 HNSW 近似），**BM25 FULLTEXT 仍是混合检索常驻一路**（不是 contentHash 全扫）。故确定性维度（AC#12）的稳定性依赖 §零 D-1 的 per-config 命名空间（同 config 串行 + 语料不残留 → IDF 稳定）。
- **向量就绪屏障**：seed 后 hnsw 模式 poll `vectorSyncPendingCount==0`（或校验全部 seeded item 已 synced）；exact 模式全扫不依赖向量，跳过。

| 维度① Recall 低且维度② Recall 低 | 抽取漏了 → 修抽取 Prompt / 身份化 |
| 维度① P/R 正常但维度② Recall 低 | 检索漏了 → 修融合 / 召回 / 精排 |
| 维度① 重复率高且维度③ 重复率高 | 去重/身份化失效 → 修 identity |
| 维度② Recall 正常但维度④ 无关注入率高 | 注入组装问题 → 修过滤 / 预算 / 任务映射 |
| 维度⑤ 误合并率高 | 治理误判 → 修聚类阈值 / 加人工确认 |

### 3.6 Java 可调参数清单（全量，默认值取自 `MemoryProperties`）

`/eval/params` 是参数单一真源；以下为可调参数的完整清单、默认值与建议可调范围（默认值均已从 `MemoryProperties.java` 与 `MemoryRetriever.java` 核实）。

| 参数 | 默认值 | 归属 | 说明 | 建议范围 |
|---|---|---|---|---|
| `retrieval.rrfK` | 60 | 检索 | RRF 融合常数 k | 20–100 |
| `retrieval.alpha` | 0.1 | 检索 | recency 重排因子权重 | 0–0.5 |
| `retrieval.beta` | 0.1 | 检索 | importance 重排因子权重 | 0–0.5 |
| `retrieval.recencyHalfLifeDays` | 30 | 检索 | recency 指数衰减半衰期（天） | 7–90 |
| `retrieval.profileBoost` | 0.15 | 检索 | 画像候选布尔 boost 比例 | 0–0.5 |
| `retrieval.minConfidence` | 0.0 | 检索 | 回表后最低置信度阈值 | 0–1.0 |
| `threshold`（`DEFAULT_THRESHOLD`） | 0.1 | 检索 | 粗排相似度过滤阈值 | 0–0.3 |

**缓存 key 完整性约束**：上述动态参数若影响检索结果，必须全部纳入 `search` 的缓存 key（`rrfK/threshold/topK/taskType/alpha/beta/recencyHalfLifeDays/profileBoost/reranker.enabled`），否则「调参」会命中的是旧缓存假象（AC#8 专门断言非缓存假象）。

### 3.7 eval 冻结模式（6 要素，钉死）

`SearchParams.freezeSideEffects=true` 下冻结以下 6 个副作用，保证「评测检索不污染语料、不漂移状态」：

| # | 冻结项 | 机制 | 目的 |
|---|---|---|---|
| 1 | 访问回写 | 跳过 `recordAccessAsync` | 检索不改变 access/importance |
| 2 | 缓存 | 旁路 `search` 缓存 | 每次真实执行，非缓存假象 |
| 3 | recency | 固定 epoch（`memory.eval.recency-baseline`） | 时间不漂移 |
| 4 | reranker | 旁路（`reranker.enabled=false` / skipRerank） | 排除非确定性精排 |
| 5 | expire | 墙钟 pin（仅 pin，不 assert expire=null） | 生命周期过滤不漂移 |
| 6 | exact | `exact:true` 贯穿链（Qdrant body 含 `params.exact`） | HNSW 近似换全扫 |

### 3.8 Java eval 端点契约（`MemoryEvalController`，`/api/v1/eval`）

| 端点 | 方法 | 暴露 | 契约要点 |
|---|---|---|---|
| `/api/v1/eval/seed` | POST | `addDirect` 批量 | 请求 `[{type, content}]`；返回 `{"inserted","existed"}` + `content→createdId` 映射；幂等 key = `MD5(content)` |
| `/api/v1/eval/reset` | POST | 物理删 + 清向量 | `deleteByUserId` + `removeByUserId`（synchronous delete-await）；携带 fencing token |
| `/api/v1/eval/fencing/{eval_user_id}` | GET | fencing 权威源只读（expected_version 数据源） | 返回 `{fencing_version, active_run_id}`；**无行返回 `{fencing_version:0, active_run_id:null}`**（首 run Python 按首次 acquire 处理） |
| `/api/v1/eval/fencing/acquire` | POST | fencing 权威源同步（事务内读-改-写） | 请求 `{eval_user_id, expected_version, new_run_id}`；事务内 `SELECT ... FOR UPDATE` → 无行 `INSERT` 建立（version=1）/ 有行对账 expected_version 后无条件 +1；返回新 version 或 `{conflict, current_version}` |
| `/api/v1/eval/fencing/release` | POST | finalize/reaper 后的权威交接 | 请求 `{eval_user_id, dead_run_id}`；原子 `UPDATE ... SET active_run_id=NULL WHERE eval_user_id=:uid AND active_run_id=:dead_run_id` |
| `/api/v1/eval/search` | GET | `memoryRetriever.search` | 参数 `threshold/rrfK/topK/taskType/freezeSideEffects/exact`；返回含 `content` 的 `MemoryItem` 列表 |
| `/api/v1/eval/extract` | POST | `MemoryExtractor.extract` | 请求 `{existingMemories,newMessages,lastMessages}`；响应仅 `List<MemoryCandidate>`（移除 decideOperation） |
| `/api/v1/eval/retrieve-context` | POST | `retrieveBudgetedContext` bypassCircuit | 返回 `{budgeted, formatted}`；熔断 victim-path 隔离 |
| `/api/v1/eval/governance-samples` | GET | 治理产物只读导出 | 三源样本，导入后脱钩 |
| `/api/v1/eval/governance/replay` | POST | 只调 compute 层（只读） | 重放 clusterDuplicates/checkFactConsistency 决策，不落库 |
| `/api/v1/eval/circuit-breaker` | GET | `isDegraded()` | `{degraded: bool}` |
| `/api/v1/eval/metrics` | GET | 两 getter | `extractionRejectRate` + `vectorSyncPendingCount` |
| `/api/v1/eval/params` | GET | 参数当前值只读 | 单一真源 |

**fencing 端点说明**：`seed` / `reset` 的请求 header 携带 `X-Eval-Fencing: {fencing_version}` 与 `X-Eval-Run-Id: {run_id}`，Java 在**同一事务内** `SELECT ... FROM eval_fencing WHERE eval_user_id=:uid FOR UPDATE` 校验「token == 当前 fencing_version 且 active_run_id == X-Eval-Run-Id」，通过才执行破坏性写，不匹配 403（§零 D-3，权威源在 Java，按 eval_user_id 键控）。Python 在 acquire 前用 `GET /api/v1/eval/fencing/{eval_user_id}` 读权威值作 expected_version，acquire 返回新 version 后写回 `eval_runs.fencing_version`（Postgres 镜像）。

## 六、Java 侧改造（沿用 v6 + 生产级微调 + 承重改动显式 + 存储隔离接入点）

### 6.1 eval 端点最小权限角色
- `ROLE_EVAL` + `/api/v1/eval/**` `@PreAuthorize("hasRole('EVAL')")`。

### 6.2 seed 幂等（承重）
- `selectByUserIdAndHash(userId, contentHash)` + `addDirect void→Long` + `catch DuplicateKeyException → existed`。

### 6.3 reset 清向量库（承重）
- `IMemoryVectorStore.removeByUserId(userId)`：Qdrant `/points/delete` filter `{user_id}` **synchronous delete-await**；Simple 剥离匹配 userId 的 VectorEntry。
- reset = MySQL `DELETE FROM` + `memory_history` 孤儿清理 + `removeByUserId`。
- **warm-up 澄清**：seed 的 `upsert` 自然回填向量，无需额外 re-sync。

### 6.4 IDOR 防护 + per-config 派生 userId
- eval 端点不接受客户端传 userId，Python 服务端按 `config_fingerprint` 派生传入。
- Java 校验 `EVAL_USER_ID_BASE ≤ eval_user_id < BASE + RANGE`，越界 403。
- `MemoryManager.addDirect(Long userId,...)` / `delete(userId, memoryId)` 已支持 userId 列。

### 6.5 `hnsw_ef` 暴露 + `/eval/search` 返回 content
- `IMemoryVectorStore.search` 重载补 `hnsw_ef`；`/eval/search` 必须含 `content`。

### 6.6 eval 端点网络暴露面
- `/api/v1/eval/**` 仅内网。

### 6.7 存储隔离 A 的 Java 落地机制（已拍板：独立 Java 实例）

- **现状**：`IMemoryRecordDao`（MySQL）与 `IMemoryVectorStore`（Qdrant）各只接一个 datasource/collection，Phase 0 会撞墙。
- **三种接入点**：
  1. **独立 Java 实例（推荐）**：起一个专用 eval Spring Boot 实例，`memory.eval.enabled=true` + 指向专用 eval DB/collection 的配置。隔离最彻底、无侵入，成本是额外一个 JVM。
  2. **双 datasource/collection**：同一实例内按 `memory.eval.enabled` 路由到专用 DB/collection（`@Primary` 业务源 + eval 源），省 JVM 但需改 DAO/VectorStore 的数据源注入。
  3. **tenant 路由**：单源内按 userId 前缀路由，实现复杂、隔离弱，不推荐。
- **Decision（已拍板，见 §零 D-2）**：采用**独立 Java 实例**（不再保留双 datasource 备选）。起一个专用 eval Spring Boot 实例，`memory.eval.enabled=true`，指向专用 eval DB/collection，cron 禁用 + 冻结态 + exact 贯穿。

### 6.8 fencing token 的 Java 落地（新增，见 §零 D-3）
- **权威源在 Java（事务内读-改-写 + GET + release）**：新增 `eval_fencing` 表（主键 `eval_user_id`，§5.9）。
  - `POST /api/v1/eval/fencing/acquire`：事务内 `SELECT ... FOR UPDATE` 锁定读 → 无行 `INSERT` 建立（version=1）/ 有行对账 expected_version 后无条件 +1（无 CAS WHERE）；返回新 version 或 `{conflict, current_version}`。
  - `GET /api/v1/eval/fencing/{eval_user_id}`：只读返回 `{fencing_version, active_run_id}`，作为 Python acquire 前 expected_version 的权威读取来源。
  - `POST /api/v1/eval/fencing/release`：原子清 `active_run_id`（**normal finalize 与 reaper 判死后都调用**）。
- **破坏性写校验（同一事务，锁定读，无行拒绝）**：`reset`/`seed` 从 header 读 `X-Eval-Fencing` 与 `X-Eval-Run-Id`，在事务内 `SELECT ... FROM eval_fencing WHERE eval_user_id=:uid FOR UPDATE` 校验「`X-Eval-Fencing` == 当前 fencing_version 且 `active_run_id == X-Eval-Run-Id`」；**查无行（未 acquire）→ 403 拒绝「fencing 未建立」**（不放行防绕过）。通过才执行 DELETE/seed。
- **镜像写回（v18，降级为观测）**：Python 在 acquire 返回新 version 后，把它**写回 `eval_runs.fencing_version`**（Postgres 镜像）作观测指标；镜像==权威只用于对账告警，**不参与任何破坏性写决策**（破坏性写由权威 FOR UPDATE 校验独立兜底）。
- **token 刷新 pin（v18）**：破坏性写前的 token 统一用 `GET /fencing/{eval_user_id}` **实时读权威**（不用缓存），避免陈旧缓存 token 403 拒绝合法写。

### 6.9 退役脚本 + exact 模式澄清

- **Minor #4**：`11-eval-insert-corpus.sql` 用 `MD5(CONCAT(9999,content))`，与契约 `MD5(content)` 不一致。**Phase 0 退役该脚本**，seed 端点为唯一灌入通道；Phase 2 迁移 V1 时按 `MD5(content)` 重算 content_hash/ground_truth。
- **Minor #5**：exact = 冻结 6 要素 + `exact:true` 向量检索，BM25 FULLTEXT 仍常驻一路（非 contentHash 全扫）；IDF 稳定性依赖 per-config 命名空间 + 语料不残留。

## 八、可靠性 / 容错 / 监控

### 8.1 可靠性

| 关注点 | 设计 |
|---|---|
| 崩溃恢复 | 状态分支续跑 + 阶段幂等 |
| double-live fencing | 入口 lease CAS + **fencing token（权威源在 Java `eval_fencing`，按 `eval_user_id` 键控，破坏性写 `FOR UPDATE` 事务内校验）** + per-stage check（降级为快速失败+观测） |
| **fencing 残余风险（已根治）** | v12 的 check-then-act TOCTOU 经 §零 D-3 fencing token 闭合：权威源按 `eval_user_id` 键控下沉 Java，破坏性写 `FOR UPDATE` 锁定读 + 校验，zombie 旧 token 在 lease 接管（`fencing_version+1`）后必然失配（含跨 run_id 的同命名空间场景）。per-stage check 保留为观测层 |
| 卡死恢复 | reaper heartbeat-based：stale `heartbeat_at` → `revoke(terminate=True)` + CAS failed；stale `pending` → failed；admin force-fail |
| reaper 局限 | `revoke(terminate=True)` 跨容器/host 不可靠 → fencing token + per-stage check + 检测告警兜底 |
| finalize 防护 | **先清理自身命名空间（复用 `/eval/reset`，携带 fencing token）→ 调 fencing/release 清 active_run_id → 后 CAS `WHERE status='running' AND lease_owner=:me` 置 succeeded**（D-7 闭合清理窗口 + v17 释放 fencing + v18 清理走 fencing 守卫） |
| 任务不丢 | `task_acks_late=True` + `task_reject_on_worker_lost=True` |
| 双击不重 | `idempotency_key` 唯一 + body 一致性 |
| 并发正确性 | per-config 隔离（跨 config）+ 部分唯一索引 + CAS + fencing token（同 run） |
| 幂等 | reset（MySQL+向量）、seed（catch DupKey）、Recall contentHash、结果 upsert |
| 重试 vs 续跑 | transient 重试、确定性失败不重试 |
| 取消 | `CANCELLED` + 阶段间检查 + `revoke` |
| 熔断/限流 | connector 对 Java |
| 配置外部化 | pydantic-settings + env + secrets |
| schema 版本化 | Alembic |
| 数据备份 | Postgres WAL + `pg_dump` + **MySQL `eval_fencing` 权威态纳入备份（见 §8.5）** |

### 8.4 告警规则（阈值 + 动作）

| 告警 | 触发条件 | 级别 | 动作 |
|---|---|---|---|
| run 卡死 | `status='running'` 且 `heartbeat_at` 超 stale 阈值 | P1 | 自动 reaper 判死 + 通知 |
| run 空结果 | `status='succeeded'` 但 `case_results` 数为 0 | P1 | 提示 zombie fencing 失配，人工重跑 |
| 可复现漂移 | 同 config N≥3 的 max abs diff > ε | P2 | 提示 IDF 漂移 / embedding 漂移，隔离复现 run |
| Java 连接异常 | connector 5xx/超时率 > 阈值 | P1 | 熔断 + 通知，排查 eval 实例 |
| 语料残留 | `eval_corpus_size` 在 finalize 后未归零 | P2 | 提示 finalize 清理失败，人工 reset |
| judge 不一致 | `eval_judge_consistency` 低于阈值 | P3 | 提示位置偏置未消解，人工复核 |
| 参数漂移 | `/eval/params` 与上次快照 hash 不一致 | P3 | 提示线上参数被改，人工确认 |

> 告警配置沿用 Java 侧已有 `MemoryProperties.Alert` 的「首月不启用仅埋点」策略，基线收集后再启用阈值。

### 8.5 备份 / 恢复（RPO / RTO）

| 对象 | 备份方式 | RPO | RTO |
|---|---|---|---|
| Postgres（评测元数据 + 结果） | WAL 归档 + 每日 `pg_dump` + 每日 `pg_basebackup` | ≤ 5 分钟（WAL）/ ≤ 24h（dump） | ≤ 30 分钟 |
| MySQL eval database（语料，短暂态） | 不单独备份（语料由 dataset 可重建，finalize 后本应清空） | — | 由 dataset 重新 seed |
| **MySQL `eval_fencing`（fencing 权威态）** | **必须备份**（`mysqldump` 单表 + binlog，或与业务 MySQL 同 RPO） | ≤ 5 分钟（binlog）/ ≤ 24h（dump） | ≤ 30 分钟 |
| Qdrant collection（向量，短暂态） | 不单独备份（向量由 seed upsert 重建） | — | 由 dataset 重新 seed |
| 评测集原始文件（dataset JSON/YAML） | 纳入 git + 对象存储版本 | 实时 | 即时恢复 |

**核心原则**：唯一不可重建的资产是**评测集原始文件 + 结果/反馈/审计元数据 + `eval_fencing` 权威态**（这些要可靠备份）；语料和向量都是「从评测集可重建的短暂态」，finalize 后本应清空，不占备份预算。`eval_fencing` 虽小，但丢失会导致 fencing 权威归零、防护自毁，故单独纳入备份（Architect M2）。

### 8.6 故障处理 runbook（前 5 类高频故障）

| 故障 | 现象 | 定位 | 处置 |
|---|---|---|---|
| run 卡死 | run 长期 `running`，心跳停滞 | `idx_runs_heartbeat` 查 stale | reaper 自动判死；确认无僵尸后重跑 |
| zombie 删语料 | 新 run 结果为空 | fencing 告警 / `eval_run_reaped_total` | fencing token 已根治；确认后重跑，无需人工清库 |
| 可复现失败 | AC#13 失败，指标漂移 | `eval_idf_drift` / embedding 自检 | 隔离复现 run（无并发不同 config）；重 embed 自检 |
| 向量未就绪 | hnsw 模式 search 结果不全 | `vector_sync_pending_count` | 等向量就绪屏障归零；或切 exact 全扫 |
| judge 结果不一致 | A/B 与 B/A 判反 | `eval_judge_consistency` | 排查位置偏置；人工复核受影响 pair |

### 8.7 容量估算（单机起步，生产级基准）

| 资源 | 估算 | 依据 |
|---|---|---|
| 评测集规模 | 200 query→记忆对 + 50 对话→记忆对（起步）→ 数千（长期） | 覆盖 4×6 边界矩阵 |
| Postgres 容量 | 起步 < 1GB；长期按 10 万 case + 1 万 run 估算 < 10GB | 结果/反馈/审计 JSONB |
| MySQL eval database | 语料 ≤ 512 字符 × 数千条，finalize 后清空 | 短暂态，峰值 < 100MB |
| Qdrant collection | 与语料同规模，finalize 后清空 | 短暂态 |
| 独立 Java 实例 | 堆 512MB–1GB | eval profile 禁用 cron/回写，负载低于业务实例 |
| Celery worker | 单 worker（per-config 串行）+ N worker（并行 A/B） | 正确性来自 per-config 隔离 + CAS + fencing，非单 worker |
| LLM-judge 成本 | 仅维度④抽样子集跑 judge（约 20–50 pair/run） | 全量 judge 成本高，抽样保性价比 |

## 十、Acceptance Criteria（可测试）

1. **连接**：登录 Java（`ROLE_EVAL`）调 `/eval/search`，返回含 `content`。
2. **seed 幂等**：返回 `{"inserted","existed"}`；重复 seed 不抛 `DuplicateKeyException`。
3. **reset 彻底清空**：`/eval/reset` 后 MySQL 无残留 + 向量库无 stale；连续 reset no-op；孤儿处理。
4. **per-config 隔离 + 哈希碰撞降级**：同 config 共享命名空间（串行 + reset 自清）；不同 config 并发互不干扰；哈希碰撞到同一 `eval_user_id` 时由 `uq_runs_active_user` 串行化（409 而非互删）。
5. **语料不残留**：run finalize 后自身命名空间语料被清理（IDF 不随历史累积）。
6. **异步 run 状态机**：202 + run_id；`PENDING→RUNNING→SUCCEEDED`；长 run 不阻塞。
7. **双击幂等 + body 一致性**：同 key 同 config 返回同一 run；同 key 不同 config 409。
8. **崩溃续跑 + lease CAS + fencing token（含生命周期）**：(a) kill 后重启续跑成功；(b) 双 worker 同抢 stale 只一个接管；(c) fencing 权威源按 `eval_user_id` 键控，zombie 携带旧 fencing token 调 reset/seed 被 Java 事务内 403 拒绝（含跨 run_id 同命名空间）；(d) `FOR UPDATE` 锁定读下 acquire 与破坏性写互斥；(e) **首个 config 首次破坏性写前 acquire 建立行（无行则 403 拒绝而非放行）**；(f) **reaper 判死后 release 清 active_run_id，后继 run acquire 成功接管**。
9. **卡死恢复**：stale heartbeat → reaper CAS failed；stale pending → failed；force-fail 支持。
10. **finalize CAS + 清理（先清空后释放 + fencing 守卫）**：reaper 判死/lease 接管后原 worker 不复活/不覆盖；**finalize 先清理自身命名空间（复用 /eval/reset 携带 fencing token）、后 CAS 置 succeeded**；晚到 zombie 的清理（无论走 reset 还是 finalize 入口）因 fencing token 失配被 Java 403 拒，不误删后继 run 语料。
11. **重试语义**：transient 重试成功；确定性失败不重试。
12. **五维指标**：Recall@5/MRR/NDCG@5/Hit@1 + 抽取 Precision/Recall/方差 + 治理误合并/漏隔离率 + 注入无关注入率/成对胜率（LLM-judge 位置偏置消解）。
13. **可复现（跨周期 + exclusive）**：同 `config_fingerprint`（exact）N≥3，`exclusive=true` 全局独占（D-6，机制化挡并发 A/B 干扰 IDF），确定性维度 max abs diff < ε=0.01；contentHash 跨 reset 不漂移；无 stale 向量；**语料不残留 → IDF 稳定**。
14. **指纹可移植 + ground_truth 可见**：staging/prod 同 fingerprint；**ground_truth 纠错 → content_digest → fingerprint 变**（反哺闭环归因可见）。
15. **向量就绪屏障**：hnsw seed 后 synced 才 search；exact 跳过。
16. **RBAC**：viewer 无法建 run/改数据集。
17. **IDOR 防护**：eval_user_id 越出命名空间被拒（403）。
18. **审计**：mutation 落 `eval_audit_log`。
19. **反哺闭环**：样本流转 + 归档重算 content_digest + 回归 diff + 超阈值告警。
20. **可观测性**：Flower（basic-auth）+ run_id 日志。
21. **边界**：Java 旧路径回归全绿；`exact` 贯穿 4 调用点非 eval 三处缺省 false。
22. **跨模型可比分层（分类正确性）**：单测断言「错误归属率/低价值写入率」归相对可比层、「无关注入率」归绝对可比层（不依赖 judge）、「治理⑤/一致性③」归绝对可比层；检索②/抽取① 按 `config_hash` 分段、**注入④ 成对胜率/事实错误率按 `config_hash + judge_model` 复合键分段**。
23. **fencing 权威一致性（镜像降级为观测，v18）**：acquire 返回新 version 后 Python 写回 `eval_runs.fencing_version` 作**观测镜像**（非决策不变量）；对账断言「权威以 MySQL 为准，镜像由 acquire 返回值回写，最终一致」；**不一致只告警、不阻断破坏性写**（破坏性写已由 Java 权威 `FOR UPDATE` token 校验独立兜底，镜像无决策读取，阻断是自伤可用性）；token 刷新统一走 `GET /fencing/{eval_user_id}` 实时读权威（不用缓存，避免陈旧 token 403 合法写）。
24. **exclusive guard 回收**：run 正常 finalize、reaper 判死、崩溃后 `heartbeat_at` stale 三种情况均回收 `eval_run_guard.exclusive_owner`，无槽位永久泄漏。

## 十三、Verification Steps

1. **单元**：metrics、datasets、params、feedback、幂等 upsert、content_digest（含 ground_truth）。
2. **契约**：respx mock Java + seed 幂等 + IDOR + eval_user_id 范围校验。
3. **Java 回归**：`mvn test` 全绿 + removeByUserId + 存储隔离接入点。
4. **冻结态**：search 无副作用、recency 固定、reranker 旁路、expire pin、exact:true。
5. **reset 清向量库**：reset 后 `SimpleMemoryVectorStore` 按 `eval_user_id` 过滤计数 = 0（不是全 map size，并行 A/B 下全 map 含其他命名空间）；Qdrant filter 无 stale。
6. **per-config 隔离 + 语料不残留 + 哈希碰撞降级**：两 config 并发互不干扰；finalize 后命名空间清空；同 config 串行自清；碰撞 config 409 串行化而非互删。
7. **异步/幂等/崩溃/lease CAS/zombie + fencing 权威源**：双击 + body；kill 续跑；双 worker lease CAS；zombie 旧 fencing token 被 Java 事务内 403 拒绝（含跨 run_id 同命名空间）；`FOR UPDATE` 锁定读下 acquire 与破坏性写互斥；Postgres 镜像 vs MySQL 权威一致。
8. **卡死恢复**：reaper CAS failed；finalize 不复活。
9. **可复现（exclusive）**：同 fingerprint N≥3 + exclusive 全局独占，max abs diff < 0.01；IDF 不随历史漂移；并发 A/B 被 409 挡在 exclusive 外。
10. **指纹可移植 + ground_truth 可见**：staging/prod 同 fingerprint；ground_truth 纠错 → fingerprint 变。
11. **向量就绪屏障**：hnsw synced 才 search。
12. **RBAC/审计/IDOR**。
13. **反哺闭环**。
14. **可观测性**：Flower + run_id 日志。
15. **端到端**：docker compose up，跑 §10 全 AC。
16. **跨模型可比分层（分类正确性）**：单测断言「错误归属率/低价值写入率」归入相对可比层、「无关注入率」归绝对可比层（不依赖 judge）、「治理⑤/一致性③」归入绝对可比层；相对可比层按 `config_hash` 分段、**维度④ 成对胜率/事实错误率按 `config_hash + judge_model` 复合键分段**（与 AC#22 对齐）。
17. **exclusive guard 回收**：三路（finalize/reaper/stale 心跳）均回收 `exclusive_owner`，崩溃后不永久 409。

## 十五、RALPLAN-DR 摘要

### Principles（5 条）

1. **部署独立、逻辑不独立**。
2. **可复现优先**：存储隔离 A + 冻结 6 要素 + exact gate + contentHash + reset 清向量库 + **语料不残留**。
3. **真实性与可复现分工**：双模式检索。
4. **数据即资产**：版本化 + 审计 + 内容可寻址指纹（**含 ground_truth**）。
5. **共享态粒度正确**：语料 **per-config 隔离**（同 config 串行自清 + finalize 清理，跨 config 并行安全）+ 同 run 单飞（CAS/fencing token，TOCTOU 已根治）+ 四件语义分离。
6. **问题边界收敛**：fencing 权威源下沉 Java（原子校验）；exclusive run 机制化 IDF 隔离；跨模型指标可比性分层；哈希碰撞降级为吞吐抖动（不损失正确性）。

### Decision Drivers（top 3）

1. **长期积累与团队协作** → Postgres + RBAC + 版本化 + ground_truth 可见指纹。
2. **可靠性与重负载 + 并行 A/B** → 异步 + per-config 隔离 + CAS/fencing token + reaper + 语料不残留。
3. **可复现** → 存储隔离 A + 冻结 6 要素 + exact + contentHash + reset 清向量库 + IDF 稳定。

### Viable Options（>=2）

| 选项 | 描述 | 利 | 弊 | 判定 |
|---|---|---|---|---|
| **O1（选定）** | per-config 派生 + finalize 清理 + 异步 Celery + Postgres + 两档 RBAC + 内容可寻址（含 ground_truth）+ 单飞/fencing + reaper | 语料不残留、IDF 稳定、并行 A/B、反哺闭环可见 | 保留命名空间 + 派生略增复杂度 | ✅ 选定 |
| O2 | corpus 级串行（全局单飞 + `--concurrency=1`） | 最简；IDF 天然稳定 | 无并行 A/B | ⚠️ fallback |
| O3 | 固定 EVAL_USER_ID | 简单 | 跨 config reset 互删 + 历史累积 | ❌ |
| O4 | 同步 FastAPI + SQLite | 快 | 超时/无并发/无 RBAC 审计观测 | ❌ |

**隔离子选项**：per-config 派生（选，语料不残留 + 并行 A/B）vs run_id 派生（v11，历史累积）→ 选 per-config；corpus 串行 fallback。
**fencing 子选项**：fencing token（选，Java 拒绝旧 token 的破坏性写，根治 TOCTOU）vs per-stage check（check-then-act，有残余窗口）→ 选 fencing token，per-stage check 降级为观测。

| 镜像 fail-stop | AC#23 不一致阻断破坏性写（镜像无决策读取，自伤可用性） | **降级为「只告警不阻断」；镜像定为观测指标，token 刷新统一走 GET 实时读权威** |
| acquire 无行 INSERT | 未 pin 隔离级别与撞键 | **pin REPEATABLE READ + catch DuplicateKeyException 视作已有行走对账 +1** |
| GET 无行 | 哨兵语义未定义 | **无行返回 `{fencing_version:0, active_run_id:null}`** |
| 心跳双写 | 未声明事务边界 | **同一事务内更新 run + guard 两处 heartbeat_at** |

## 附一·五：Phase 0 实现收尾注记（v18 终审 4 条 MINOR，不阻塞，实现时顺带 pin）

> 第 6 轮终审（Architect APPROVE + Critic APPROVE）判定设计收敛，仅留 4 条注释级收尾，实现 Phase 0 时一并处理，无需再次返稿：

1. **finalize 块幂等/重试语义**：finalize 三步（清理→release→CAS）非原子，若在 release 成功后、CAS 前 crash，run 进入 `status='running'` 但 `active_run_id=NULL` 的 fenced-out 态，靠 heartbeat stale → reaper 判死兜底。实现时 pin：finalize 上下文中 reset 的 403 视为「已清理，跳过」而非 fatal，使整块幂等可重试。
2. **放弃接管的 lease 回写**：acquire 失败时「放弃接管」应回写 `lease_owner=NULL`（缩短卡死窗口），否则 run 只能等 reaper 判死。
3. **镜像回拉自动化**：镜像降级为观测后，`镜像回拉 MySQL 权威`的自动脚本列为 Phase 6 可选项（避免告警疲劳）。
4. **UUID 规范化契约**：`active_run_id CHAR(36)` 的 run_id 统一为「小写带连字符 UUID 字符串（`str(uuid)`）」，纳入契约测试（防大小写/前缀不一致导致全链路 403）。

## 附二：评审收敛历程（5 轮，供追溯）

| 轮次 | 判定 | 核心发现 |
|---|---|---|
| v7（初稿） | REJECT | 异步状态机三连矛盾（claim 与续跑互斥 / run_key 唯一撞可复现 / 自增 id 漂移） |
| v8 | ITERATE | 四件语义分离正确，但「阶段幂等收敛」支柱在代码侧未兑现（seed 不幂等 / case 无唯一 / createdId 映射复活 id 漂移） |
| v9 | ITERATE | contentHash 匹配正确，但「mutable shared state」未收敛（reset 只清 MySQL 不清向量库） |
| v10 | REJECT | 收敛了 run row 与结果 identity，但漏掉「语料」这个最关键的 mutable state（跨 run 共享） |
| v11 | REVISE | per-run 隔离方向对，但语料无限累积致 IDF 漂移 + ground_truth 对指纹不可见 |
| **v12** | **收敛** | per-config 派生 + finalize 清理 + content_digest 纳入 ground_truth + fencing 残余风险诚实化 |

**评审方法**：每轮 Architect 和 Critic 都独立评审同一份快照（Critic 不接收 Architect 输出），多轮独立命中同一根因（强共识信号）。5 轮从「状态机设计矛盾」逐层收敛到「共享态粒度」这个最深的设计决策。
