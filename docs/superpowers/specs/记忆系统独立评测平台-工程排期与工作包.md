# 记忆系统独立评测平台：工程排期与工作包

> 本文是《记忆系统独立评测平台方案（v18 终稿）》的工程落地版。
> 原始方案文件不修改、不替代，完整内容仍保留在：
> `docs/superpowers/specs/记忆系统独立评测平台方案.md`
>
> 估算基准：1 名熟悉 Java、Python、Docker 和基础前端的全栈开发者，按串行关键路径估算。
> 1 人天按 8 小时计；人天是开发工作量估算，不等同于自然日承诺。

## 1. 排期总览

| 阶段 | 目标 | 优先级 | 估算人天 | 累计人天 |
|---|---|---:|---:|---:|
| Phase 0 | 基础设施和 Java eval 能力 | P0 | 12 | 12 |
| Phase 1 | Python 骨架、认证、连接层、数据模型 | P0 | 8 | 20 |
| Phase 2 | 测试集管理和异步 run 编排 | P0 | 15 | 35 |
| Phase 3 | 五维评测引擎和结果落库 | P0 | 12 | 47 |
| Phase 4 | 参数、结果页面、观测、LLM-judge | P1 | 13 | 60 |
| Phase 5 | 反哺闭环和安全收口 | P1 | 7 | 67 |
| Phase 6 | 联调、全量验收、部署文档 | P0 | 8 | 75 |
| **合计** | 可持续使用的第一版 |  | **75 人天** |  |

单人串行建议按 15 周、每周 5 个有效开发日规划。预留约 20% 的联调和故障排查缓冲后，建议整体窗口为 18 周。

## 2. 优先级规则

- **P0**：没有它就无法安全执行真实评测，必须先完成。
- **P1**：能形成完整调优闭环，第一版应完成。
- **P2**：增强可观测性、体验或扩展性，可在首个稳定版本后完成。

关键路径为：

```text
Java eval 契约
  -> 数据模型与 connector
  -> run 状态机 / per-config / fencing
  -> 五维指标
  -> 结果展示
  -> 反哺与全量验收
```

## 3. Phase 0：基础设施与 Java 侧（12 人天，P0）

### WP0-1：部署隔离骨架（1.5 人天）

- 创建 platform、memory 双网络。
- 配置 Postgres、Redis、Qdrant、Java eval 实例、Flower、beat。
- 为 eval 实例配置专用 MySQL database 和 Qdrant collection。
- 禁用 eval 实例业务 cron。

依赖：无。  
验收：`docker compose up` 后所有服务健康，platform 只能通过指定网络访问 Java eval 实例。

### WP0-2：Java eval 权限和端点骨架（1.5 人天）

- 增加 `ROLE_EVAL`。
- 增加 `/api/v1/eval/**` controller、内网访问限制和统一错误码。
- 增加 eval_user_id 范围校验，拒绝 IDOR。
- 暴露 `/eval/params`、`/eval/metrics`、`/eval/circuit-breaker`。

依赖：WP0-1。  
验收：viewer 无法调用 Java eval mutation；越界 eval_user_id 返回 403。

### WP0-3：seed/reset 和向量删除承重改造（3 人天）

- `selectByUserIdAndHash` 支持 seed 幂等检查。
- `addDirect` 返回 inserted/existed 语义。
- 捕获 `DuplicateKeyException`，把并发重复写收敛为 existed。
- `deleteByUserId` 物理删除并处理孤儿。
- `IMemoryVectorStore.removeByUserId` 同步删除并等待完成。
- 退役 `11-eval-insert-corpus.sql`。

依赖：WP0-2。  
验收：连续 seed 不报重复键；reset 后 MySQL 和 Qdrant 均无当前命名空间残留。

### WP0-4：检索、抽取、注入、治理 eval 端点（2 人天）

- `/eval/search` 返回 content。
- `/eval/extract` 只返回 `List<MemoryCandidate>`。
- `/eval/retrieve-context` 支持 budgeted context 和熔断 victim-path。
- `/eval/governance-samples`、`/eval/governance/replay` 只读。
- 贯穿 `freezeSideEffects`、`exact` 和 hnsw_ef。

依赖：WP0-3。  
验收：契约测试覆盖请求、响应、exact 透传和 replay 不落库。

### WP0-5：Java fencing 权威实现（4 人天）

- 创建 `eval_fencing` 表。
- 实现 GET fencing、acquire、release。
- acquire 使用事务内 `SELECT ... FOR UPDATE`。
- pin REPEATABLE READ；处理首行 INSERT 和唯一键撞键。
- reset/seed/finalize 清理在同一事务内校验 token 和 run_id。
- 备份脚本纳入 `eval_fencing`。

依赖：WP0-3。  
验收：旧 token、错误 run_id、无 fencing 行均返回 403；后继 run release 后可正常接管；并发 acquire 只产生单调版本。

### Phase 0 出口

- Java `mvn test` 全绿。
- eval 实例可独立启动。
- seed/reset/search/extract/retrieve/replay 契约固定。
- fencing zombie 边界测试通过。

## 4. Phase 1：Python 骨架与数据模型（8 人天，P0）

### WP1-1：工程骨架和配置（1.5 人天）

- 创建 `eval-platform/`。
- FastAPI、SQLAlchemy 2、Alembic、Celery、Redis、httpx、pytest。
- pydantic-settings、env、docker secrets。
- 统一错误、日志和 request/run correlation。

依赖：Phase 0。  
验收：API、worker、beat 可独立启动，健康检查可用。

### WP1-2：Postgres 核心 schema（3 人天）

实现原文 §5 的表和索引：

- 用户、数据集、版本、case。
- 参数快照、模型版本。
- experiment、run、guard。
- run results、case results。
- feedback、judge jobs、audit。

特别固定：

- canonical_json。
- content_hash。
- content_digest 必须包含 ground_truth。
- active run 部分唯一索引。

依赖：WP1-1。  
验收：Alembic 可升级、回滚；唯一索引和外键约束通过测试。

### WP1-3：认证、RBAC、审计和 connector（3.5 人天）

- JWT + bcrypt。
- admin/viewer 权限依赖。
- Java connector 连接池、超时、重试、熔断。
- respx 契约测试。
- mutation append-only 审计。

依赖：WP0-4、WP1-2。  
验收：viewer 无法创建 run、改数据集或执行 mutation；Java 5xx 可观测并触发熔断。

## 5. Phase 2：数据集与异步编排（15 人天，P0）

### WP2-1：数据集三源导入和版本化（3 人天）

- 支持 query→memory、conversation→memory、治理样本三源。
- 校验 schema、content_hash 和 ground_truth。
- 版本不可变，归档生成新版本。
- 计算 content_digest。

依赖：WP1-2。  
验收：同内容去重；ground_truth 修改会产生新 digest。

### WP2-2：run 创建、幂等和配置指纹（2 人天）

- 计算 `config_fingerprint`。
- Idempotency-Key 同 fingerprint 返回原 run。
- 同 key 不同 fingerprint 返回 409。
- 派生 per-config eval_user_id。
- 实现 `uq_runs_active_cfg` 和 `uq_runs_active_user` 语义。

依赖：WP2-1。  
验收：双击不重；不同 config 可并行；碰撞 config 只能 409 串行。

### WP2-3：Celery 状态机、租约和 checkpoint（3 人天）

- pending→running CAS。
- running lease 接管 CAS。
- 阶段 checkpoint 和崩溃续跑。
- acks_late、reject_on_worker_lost。
- cancel、transient retry、确定性失败不重试。

依赖：WP1-3、WP2-2。  
验收：kill worker 后可续跑；双 worker 只有一个接管；结果不重复。

### WP2-4：per-config reset/seed 和向量屏障（2 人天）

- worker 在破坏性阶段前 acquire fencing。
- reset、seed 携带 token 和 run_id。
- hnsw 等待 `vectorSyncPendingCount=0`。
- exact 跳过向量屏障。

依赖：WP0-5、WP2-3。  
验收：并行 A/B 不互删；hnsw 未 ready 不进入 search；exact 可直接评测。

### WP2-5：finalize、reaper 和 exclusive guard（5 人天）

- finalize：清理 → release → CAS succeeded。
- reaper：stale running/pending 判死并 release fencing。
- `eval_run_guard` 创建时事务锁定。
- finalize/reaper/stale guard 三路回收。
- 心跳任务同事务更新 run 和 guard 两处 heartbeat。
- finalize 403 按已清理处理，支持重试。

依赖：WP2-3、WP2-4。  
验收：zombie finalize 不删除后继语料；exclusive 崩溃后不会永久 409；run 状态不会被旧 worker 覆盖。

## 6. Phase 3：评测引擎与指标（12 人天，P0）

### WP3-1：检索指标（2 人天）

- contentHash 匹配。
- Recall@5/10、MRR、NDCG@5、Hit@1。
- exact 与 HNSW 结果口径区分。

依赖：WP2-4。  
验收：createdId 漂移不影响结果；指标和人工样例一致。

### WP3-2：抽取指标（2 人天）

- Precision、Recall。
- 错误归属率、重复抽取率、低价值写入率。
- 多次运行方差。

依赖：WP0-4、WP2-1。  
验收：ground truth 对账正确，重复抽取和低价值样本可定位。

### WP3-3：一致性和治理指标（3 人天）

- 重复率、冲突率。
- MySQL/Qdrant 一致率、过期残留率。
- 误合并率、错误隔离率、误归档率、撤销成功率。
- replay 只读 compute/apply 分层。

依赖：WP0-4、WP2-4。  
验收：replay 不改变语料和状态；治理样本可以逐 case 追溯。

### WP3-4：注入指标和结果 upsert（3 人天）

- 无关注入率。
- Token 超预算率。
- judge 结果预留接口。
- `eval_run_results`、`eval_case_results` 幂等 upsert。

依赖：WP3-1、WP3-2、WP3-3。  
验收：run 重试不会产生重复结果；每个 case/维度均可回查。

### WP3-5：可比分层和口径标注（2 人天）

- 绝对可比与相对可比映射。
- 检索/抽取按 config_hash 分段。
- judge 指标按 config_hash + judge_model 分段。
- 结果携带模式、模型和参数口径。

依赖：WP3-4。  
验收：AC#22 对应单测通过；趋势查询不会跨不兼容模型连线。

## 7. Phase 4：参数、展示、观测与 Judge（13 人天，P1）

### WP4-1：参数管理（2 人天）

- `/eval/params` 单一真源。
- 参数快照和 params_hash。
- 检查检索缓存 key 覆盖所有动态参数。
- 参数漂移告警数据。

依赖：WP1-2、WP0-4。  
验收：调参结果不会命中旧缓存；run 永久绑定参数快照。

### WP4-2：结果 API 与 React 可视化（4 人天）

- run 列表、详情、进度和错误。
- 雷达、趋势、A/B、分组、方差。
- 绝对层连续趋势，相对层分段趋势。
- 口径、模型、模式和样本数展示。

依赖：Phase 3。  
验收：用户可以从 run 详情定位到 case 和指标明细。

### WP4-3：Flower、结构化日志和指标（2 人天）

- Flower basic-auth。
- JSON 日志关联 run_id/case_id。
- run/stage duration、status、retry、reaped、Java error、corpus size、IDF drift。

依赖：WP2-3。  
验收：一次失败 run 可通过 run_id 串起 API、worker 和 Java 调用。

### WP4-4：LLM-judge（5 人天）

- 成对 A/B 与 B/A 位置交换。
- 一致才采信。
- judge adapter，默认复用 DeepSeek。
- `eval_judge_jobs` 异步落库。
- 成对胜率、事实错误率和 judge consistency。

依赖：WP3-4、WP4-2。  
验收：judge 不阻塞主 run；位置偏置不一致 pair 可标记和复核。

## 8. Phase 5：反哺闭环与安全收口（7 人天，P1）

### WP5-1：反馈状态机和归档（3 人天）

- `new → reviewing → approved → archived`。
- rejected 和打回路径。
- 归档生成新 dataset_version。
- 重算包含 ground_truth 的 content_digest。

依赖：WP2-1、WP3-4。  
验收：错误样本可追溯到来源、审核人和新版本。

### WP5-2：回归 diff gate（2 人天）

- 新旧版本按 content_hash join。
- 维度和指标 diff。
- 超阈值告警。
- 记录 ground_truth 变化导致的 fingerprint 变化。

依赖：WP3-5、WP5-1。  
验收：反哺后可以自动判断提升、回归和新增样本。

### WP5-3：安全和审计收口（2 人天）

- 全量 endpoint 权限测试。
- IDOR、SQL 注入、凭据和网络隔离检查。
- mutation 审计完整性。
- viewer/admin 最小权限复核。

依赖：Phase 4、WP1-3。  
验收：安全测试和审计检查通过。

## 9. Phase 6：联调和验收（8 人天，P0）

### WP6-1：自动化验收套件（3 人天）

覆盖原文 §十和 §十三：

- seed/reset、per-config 隔离、语料不残留。
- 幂等、状态机、崩溃续跑、reaper、fencing。
- exclusive guard 回收。
- 五维指标、可复现、ground_truth 指纹。
- vector ready、RBAC、IDOR、审计、观测。

依赖：Phase 0-5。  
验收：24 条 Acceptance Criteria 全部有自动化或明确手工证据。

### WP6-2：端到端环境和数据演练（2 人天）

- docker compose 全链路启动。
- 导入 V1 评测集。
- exact 和 HNSW 各跑一轮。
- 并行 A/B、exclusive、kill/restart、reaper 场景演练。

依赖：WP6-1。  
验收：关键路径无人工清库、无 orphan vector、无结果重复。

### WP6-3：部署、备份和 runbook（2 人天）

- 部署参数和 secrets 清单。
- Postgres、dataset、`eval_fencing` 备份恢复。
- 五类高频故障 runbook。
- 容量和扩容说明。

依赖：WP6-2。  
验收：新环境可按文档部署；fencing 权威态和结果可恢复。

### WP6-4：架构收口和遗留问题登记（1 人天）

记录并明确后续处理：

- ε、heartbeat interval/stale threshold、user range 实测校准。
- exclusive 409、排队或退避策略。
- fencing 镜像自动回拉。
- 模型变更实验验证可比分层规则。

依赖：WP6-3。  
验收：所有未决项都有负责人、触发条件或后续版本归属。

## 10. 单人开发优先级建议

### 第一优先级：先打通安全最小闭环

`WP0-1 → WP0-2 → WP0-3 → WP0-5 → WP1-1 → WP1-2 → WP1-3 → WP2-2 → WP2-3 → WP2-4`

完成后，平台已经可以安全地创建并执行一个最小评测 run，且具备 reset、seed、幂等、恢复和 zombie 防护。

### 第二优先级：形成可定位问题的评测闭环

`WP2-1 → WP3-1 → WP3-2 → WP3-3 → WP3-4 → WP3-5`

完成后，可以回答“问题发生在抽取、检索、存储治理还是注入”。

### 第三优先级：形成可持续调优平台

`WP4-1 → WP4-2 → WP4-3 → WP4-4 → WP5-1 → WP5-2 → WP5-3`

完成后，具备调参、趋势、LLM judge 和反哺回归能力。

### 第四优先级：生产化收口

`WP6-1 → WP6-2 → WP6-3 → WP6-4`

没有这一阶段，不建议把平台作为长期评测基线使用。

## 11. 每个工作包的交付规范

每个工作包完成时必须留下：

1. 代码或迁移文件。
2. 单元测试、契约测试或端到端证据。
3. 配置和环境变量说明。
4. 失败场景和恢复方式。
5. 对应原始方案章节和 Acceptance Criteria。

不接受只“功能跑通”但没有验收证据的工作包。

## 12. 估算说明与风险缓冲

以下情况可能增加 10-20 人天：

- 现有 Java DAO/VectorStore 实际接口与方案描述不一致。
- Qdrant 删除和同步状态在真实环境中存在异步延迟。
- LLM 抽取和 judge 的测试数据需要多轮人工标注。
- 前端已有工程规范与本文假定不一致。
- Postgres、MySQL、Qdrant 版本差异导致事务或索引行为不同。

建议将 Phase 0 和 Phase 2 各预留 1-2 人天技术 spike，将 Phase 6 预留 3 人天故障回归缓冲。若实际只能按业余时间开发，应按人天而不是自然周顺延。

## 13. 版本出口

### MVP 出口

完成 Phase 0-3，约 47 人天：

- 能连接 Java eval 实例。
- 能管理评测集。
- 能异步执行 run。
- 能产出五维基础指标。
- 具备 per-config、fencing、reset 清理和可复现基础。

### 第一版生产可用出口

完成 Phase 0-6，约 75 人天：

- 有参数管理、结果展示、观测、LLM-judge。
- 有反馈反哺和回归 diff。
- 有全量验收、备份、部署和 runbook。

原始方案中的所有 ADR、端点契约、DDL、指标公式、验收标准和风险定义继续有效；本排期只增加工程顺序、工作包、优先级和人天估算。

## 15. 工作包统一执行模板

每个 WP 按以下顺序执行，避免“代码完成但不可验收”：

1. **确认输入**：读取原文对应章节、已有接口和当前代码行为。
2. **先写契约**：确定请求/响应、状态、异常、幂等和数据约束。
3. **实现最小路径**：只覆盖当前工作包，不提前扩展下游展示。
4. **补失败路径**：超时、重复请求、worker crash、权限错误或数据不一致。
5. **留下测试证据**：单测、契约、集成或人工演练记录。
6. **更新配置文档**：环境变量、数据库迁移、启动方式和回滚方式。
7. **执行出口检查**：依赖的前置 WP 已完成，验收条件逐项勾选。

工作包完成的标准不是“接口能返回成功”，而是“正常路径、失败路径和恢复路径都能被解释”。

## 16. 关键工作包的输入、输出和验收证据

### 16.1 WP0-5 fencing

**输入**：`eval_user_id`、expected version、new run id、reset/seed headers。  
**输出**：权威 fencing version、conflict/current version、403 拒绝语义。  
**证据**：

- 首次 acquire 无行建 version=1。
- 并发 acquire 只有一个顺序结果。
- 旧 token 在后继 run 接管后被拒绝。
- release 后后继 run 可以重新 acquire。
- reset/seed 校验与破坏性写在同一事务。

### 16.2 WP2-5 finalize/reaper

**输入**：run lease、heartbeat、fencing token、exclusive 标志。  
**输出**：语料清理、fencing 交接、run 终态、guard 回收。  
**证据**：

- 清理未完成时不会释放 active user 槽位。
- finalize 中途 crash 后可重试或被 reaper 收敛。
- 被判死 worker 的晚到 finalize 不覆盖 succeeded/failed。
- exclusive guard 在正常结束、reaper 和 stale 三路都回收。

### 16.3 WP3 指标引擎

**输入**：dataset cases、ground truth、Java response、模式和模型信息。  
**输出**：维度级结果、case 级结果、方差、口径信息。  
**证据**：

- contentHash 匹配不依赖 createdId。
- empty result、重复结果和缺 ground truth 有明确错误语义。
- 同一 run 重试后结果 upsert，不产生重复行。
- 相对可比指标按正确分段键聚合。

### 16.4 WP5-2 回归 diff

**输入**：旧 dataset version、新 dataset version、旧 run、新 run。  
**输出**：新增/删除/不变 case、指标变化、回归告警。  
**证据**：

- ground_truth 变化能解释为新 digest/fingerprint。
- 新增样本不会被错误当作旧样本回归。
- 维度阈值和置信度信息随 diff 保留。

## 17. 人天估算口径

### 17.1 人天包含

- 代码实现。
- 必要的数据库迁移和配置。
- 单元/契约测试。
- 一次正常路径联调。
- 工作包文档和验收记录。

### 17.2 人天不包含

- 新增基础设施采购或云资源审批。
- 大规模历史数据清洗。
- 重新训练 embedding、抽取模型或 judge 模型。
- 复杂 UI 视觉设计和多端适配。
- 生产环境长期值班和数据标注的人力。

### 17.3 估算置信度

| 工作范围 | 当前置信度 | 原因 |
|---|---|---|
| Java 端点和 DAO 改造 | 中 | 依赖现有接口实际复杂度 |
| Python schema、connector | 高 | 依赖明确，测试边界清楚 |
| Celery fencing/reaper | 中 | 并发故障需要真实演练 |
| 五维指标 | 中 | ground truth 和样本质量影响较大 |
| React 展示 | 中低 | 取决于现有前端基础和交互要求 |
| LLM-judge | 中低 | 模型成本、响应格式和标注一致性不确定 |

## 18. 关键路径上的可并行事项

虽然基准按单人串行，但后续如果临时增加协作者，可以并行以下事项：

| 主路径 | 可并行工作 | 不可提前越过的依赖 |
|---|---|---|
| Java fencing | Postgres Alembic schema | run 编排必须等字段和约束确定 |
| run 状态机 | 数据集导入校验 | run 创建必须依赖 dataset version |
| 指标引擎 | 结果查询 API 草稿 | 展示必须依赖稳定结果 schema |
| LLM-judge | 观测日志和 Flower | judge 结果必须绑定 run/model |
| 反馈闭环 | 前端结果细节页 | feedback 必须依赖可定位 case 结果 |

不能通过并行规避的关键依赖是：Java 契约、fencing 语义、结果 schema 和 content_digest。

## 19. 里程碑与停止线

### M0：Java eval 可安全被调用

完成 Phase 0。若 seed/reset、向量删除或 fencing 仍不稳定，不进入大量 Python 开发。

### M1：最小 run 可恢复

完成 WP1-1 至 WP2-5。必须证明 kill worker、lease 接管、reaper 和 finalize 顺序正确。

### M2：结果可解释

完成 Phase 3。必须能从维度结果定位到具体 case、contentHash、模型、参数和数据集版本。

### M3：调优闭环可用

完成 Phase 4-5。用户可以调参、比较、复核错误样本并生成回归版本。

### M4：允许作为长期基线

完成 Phase 6。没有备份恢复、全量 AC 证据和 runbook，只能作为实验工具，不作为长期基线。

## 20. 风险登记与触发动作

| 风险信号 | 触发条件 | 立即动作 | 影响 |
|---|---|---|---|
| Qdrant 删除延迟 | reset 后 pending 不归零 | 暂停 hnsw，切 exact，排查同步 | 增加 WP0/2 工期 |
| fencing 版本冲突异常 | acquire 出现非预期跳号或 403 | 停止并行 run，保留 MySQL 证据 | 阻塞 Phase 2 |
| IDF 漂移 | exclusive 同 config 重跑超过 ε | 检查残留语料和 guard | 阻塞可复现验收 |
| judge 不一致 | A/B 与 B/A 一致率低 | 降低自动采信，转人工复核 | 延后 judge 出口 |
| 结果重复 | 唯一约束或 upsert 失败 | 停止重试，修复结果事务 | 阻塞 Phase 3 |
| 数据集质量不足 | ground truth 缺失或争议高 | 先冻结 V1，补标注规范 | 增加 Phase 2 人天 |

风险触发后优先保护数据正确性和审计完整性，不为了赶排期而关闭 fencing、reset 清理或唯一约束。

### 22.1 AgentWrite 项目先行条件

独立平台可以先做骨架和 schema，但以下能力没有交付前，不建议启动真实 run 编排：

5. eval profile 可独立连接专用 MySQL/Qdrant，并禁用业务 cron。

### 22.2 独立平台可并行启动的工作

在 AgentWrite 改造期间，独立平台可以并行做：

1. FastAPI/Celery/React 工程骨架。
2. Postgres schema 和 Alembic。
3. auth、RBAC、audit。
4. dataset version、content_hash、content_digest。
5. Java connector 的 mock 契约测试。

但不能提前硬编码 Java 响应字段；所有 connector DTO 以 AgentWrite 侧最终契约为准。

### 22.3 联调顺序

推荐联调顺序：

```text
AgentWrite eval profile 启动
  -> Python connector health
  -> params 拉取
  -> fencing GET/acquire/release
  -> reset no-op
  -> seed 幂等
  -> search contentHash
  -> 单 run exact
  -> crash/reaper/finalize
  -> 五维指标
  -> 前端和反馈闭环
```

这个顺序先验证破坏性操作和身份边界，再验证指标和展示，能最大限度减少“页面做好了但底层契约不稳”的返工。
