## 〇、优化的灵魂：先定位、再优化（不是"无脑换模型"）

一个最常见的反模式，也是面试官最想看你避开的：

> ❌ **效果不好 → 直接"换更强模型 / 加更多训练数据"**

正确姿势是三步：

```
效果不好 ──①五维可归因定位──► 哪一维低？
                │
                ▼
          ②针对性优化（按维度选方向）
                │
                ▼
          ③回黄金集回归（改了有没有变好）
```

**为什么"先定位"是灵魂**：五个维度的优化方向**完全不同**，方向选错就是白费劲。

> 反例：如果 Recall@K 低（检索漏了），你去改抽取 Prompt——白费劲。因为问题根本不在抽取层。

**一句话定位**：

> "我不说'效果不好就优化'，而是**先定位**——用五维评测找到是哪个维度低（抽取 Precision 低？检索 Recall 低？注入无关注入高？），再**针对性优化**，最后**回黄金集验证**有没有变好。核心是'可归因的优化'——改哪、为什么改、改完有没有效果，都有指标闭环。"

### 症状 → 维度 → 方向总表（面试速记卡）

| 症状 | 定位到的维度 | 优化方向 |
|---|---|---|
| 抽了一堆垃圾 / 漏抽关键事实 | ① 抽取质量 | 调置信度门槛 / 改 Prompt / 换抽取模型 |
| 明明有记忆却检索不到 | ② 检索质量 | 调融合 / 加召回通道 / 换 Embedding |
| 重复记忆多 / 自相矛盾 / 双写不一致 | ③ 一致性 | 调去重阈值 / 扩归一化词表 / 补对账 |
| 注入了无关记忆 / 超预算 | ④ 注入质量 | 调任务映射 / 调预算 / 收紧相关性 |
| 误合并 / 漏隔离 | ⑤ 治理质量 | 调巡检阈值 / Shadow Mode / 补信号 |

## 一、维度①：抽取质量优化（抽错 / 漏抽）

### 1.1 症状 → 根因 → 方向

| 症状 | 根因 | 优化方向 |
|---|---|---|
| Precision 低（抽太多垃圾） | 阈值太松 / 过度引申 | 收紧置信度门槛、强化 evidence 校验、补 Few-shot 反例 |
| Recall 低（漏抽） | 阈值太紧 / 规则不全 | 放松阈值、扩充抽取规则、换更强抽取模型 |
| 错误归属率高（AI 冒充用户） | `attributed_to` 隔离弱 | 强化来源隔离规则 |
| predicate 归一化命中率低 | 同义词表不全 | 扩充中英同义词映射表 |

### 1.2 具体手段展开

**① 置信度门槛（最常用、成本最低）**：Precision 低就收紧，Recall 低就放松。

> 例子：抽取"技术栈 Java 17"+"用户喜欢 Java"，后者是过度引申。若 confidence 0.72（低于 0.8 门槛），收紧门槛到 0.8 → 丢弃"喜欢 Java"这条垃圾。

**② Few-shot 反例**：从错误样本库取 `hallucination`（幻觉）/ `over_inference`（过度引申）根因的样本，作为反例写进抽取 Prompt。

> 例子：Prompt 里加反例 "用户说'我们用 Java'，❌ 不能抽成'用户喜欢 Java'——这是引申，原文没说过'喜欢'"。

**③ 来源隔离规则**：`attributed_to` 区分 user/AI/第三方，AI 的输出不能当用户事实存。

**④ 换更强抽取模型**：杠杆最高，但成本也最高——只在①②③都调不动时最后考虑。

### 1.3 面试追问 + 答法

**Q：抽取质量差，先调什么？**
> "先调最便宜的——置信度门槛和 Few-shot 反例，这两项零额外成本。最后才考虑换更强模型，因为模型是成本最高、收益最不确定的一项。"

**Q：怎么知道是抽取问题，不是检索问题？**
> "看五维评测：Precision 低是抽取问题（抽错了），Recall@K 低是检索问题（抽对了但检索不到）。两个维度独立算，不会混淆。"

## 二、维度②：检索质量优化（该召回没召回）

### 2.1 症状 → 根因 → 方向

| 症状 | 根因 | 优化方向 |
|---|---|---|
| 融合排序差（对的关键记忆没排前面） | RRF 参数 / 权重不合理 | 调 RRF 的 k 值、α/β boost 系数 |
| 召回不全（语义上相关但漏了） | Embedding 模型弱 / 通道少 | 换更强 Embedding、加召回通道 |
| 中文关键词检索差 | MySQL FULLTEXT 默认分词不准 | 加 `ngram` parser |
| 精排不准（召回有但重排错序） | Reranker 权重不当 | 调精排权重、换更强 rerank 模型 |

### 2.2 具体手段展开

**① RRF 参数调优（离线评测验证）**：调 `k` 值和 boost 系数，看 Recall@K / MRR 有没有变好。

> 例子：RRF_K 从 60→100，Recall@5 从 0.62→0.65 → 采用；若 0.62→0.60 → 回退。

**② 加召回通道（多路召回）**：现有「语义 + 全文」之外，可加「用户画像 / 实体 / 偏好」通道，多路召回后 RRF 融合。这是"召回不全"的标准解法。

**③ 中文分词 `ngram` parser**：MySQL FULLTEXT 默认按空格分词，对中文几乎失效。加 ngram 后关键词通道的召回率直接提升，成本极低。

**④ 换更强 Embedding 模型**：这是"杠杆"——向量质量同时决定语义召回 + 抽取去重的准确性，换对了能同时提升两个维度。

### 2.3 面试追问 + 答法

**Q：RRF 的 k 值怎么选？**
> "不拍脑袋选，离线评测调。拿黄金集，把 k 从 40 到 100 扫一遍，看 Recall@K / MRR 的拐点在哪，选拐点附近的 k。这是参数调优的标准姿势——用评测集说话，不是感觉。"

**Q：召回率低，加通道还是换模型？**
> "先加通道（便宜、可控、可解释），再看换模型（贵、但能同时提升多个维度）。加通道是加法、换模型是乘法，成本收益不同。"

## 三、维度③：一致性优化（重复 / 冲突 / 双写不一致）

### 3.1 症状 → 根因 → 方向

| 症状 | 根因 | 优化方向 |
|---|---|---|
| 重复记忆多 | 余弦去重阈值太松 | 收紧去重阈值（0.9→0.85） |
| 同一概念抽成多个 predicate | 归一化词表不全 | 扩充中英同义词表 |
| 自相矛盾（"研二"vs"已毕业"） | 身份判定弱 / 冲突没走 DISPUTED | 强化身份判定、冲突标 DISPUTED 而非覆盖 |
| MySQL/Qdrant 不一致 | 双写补偿有漏洞 | 补对账脚本、强化 CAS、payload 存 status + filter 源头过滤 |

### 3.2 具体手段展开

**① 调去重阈值**：重复率上升 → 收紧余弦阈值（0.9→0.85）；误合并（把不同记忆当同一条）→ 放松。

> 例子："用 Java 17"和"用 Java 8"语义接近但事实不同，阈值太松会误合并。收紧阈值后分两条存。

**② 扩充 predicate 归一化词表**：`tech_stack / 技术栈 / techStack → tech-stack`，命中率低就加同义词。

**③ 冲突走 DISPUTED 而非覆盖**：同 subject 异 value，至少一个错，标 DISPUTED 等裁决，不静默覆盖——这是"宁可不存、不可存错"的体现。

**④ 双写一致性**：MySQL 权威 + PENDING + CAS 原子认领，外加 payload 存 status + filter 源头过滤 + 对账脚本兜底。修复时改 MySQL 必须同步标 Qdrant 的 payload status，否则下次语义召回还是旧记忆（浪费嵌入）。

### 3.3 面试追问 + 答法

**Q：修复记忆时怎么保证 MySQL 和向量库一致？**
> "三层：MySQL 是权威；Qdrant payload 里冗余存 status，检索时源头过滤掉非 Active；物理删除走 PENDING 标记 + 补偿任务。再加定期对账脚本，发现两边不一致就补同步。核心是'payload 存状态 + 源头过滤'，而不是依赖事后修。"

## 四、维度④：注入质量优化（无关注入 / 超预算 / 胜率低）

### 4.1 症状 → 根因 → 方向

| 症状 | 根因 | 优化方向 |
|---|---|---|
| 无关注入率高 | 任务→记忆类型映射不合理 | 调映射、收紧相关性阈值 |
| token 超预算 | 预算分配不合理 | 调 max-tokens、按类型分配预算 |
| 成对胜率低（有记忆不如无记忆） | 注入的记忆本身没价值 | 回退注入策略、重新审视"哪些记忆真正有用" |

### 4.2 具体手段展开

**① 任务化注入映射**：任务类型 → 该注入哪些记忆类型。写正文/生成大纲需要上下文，润色类不注入。映射不合理就调。

**② token 预算调优**：按记忆类型分配预算（事实 > 偏好 > 指令），超了截断。CJK≈1 token/字、其他≈0.3 token/字，预算计算据此做。

**③ 成对胜率驱动**：评测"有记忆 vs 无记忆"的成对胜率，若注入后反而不如不注入，说明注入是负收益——回退策略，宁可不注入、不可注入错。

> 例子：润色文章时注入"用户技术栈 Java 17"这条记忆，对润色没帮助反而占 token。成对胜率测出负收益 → 润色类任务不注入技术栈记忆。

### 4.3 面试追问 + 答法

**Q：注入怎么防止"过度注入"？**
> "三重控制：任务化映射（只注入当前任务相关的记忆类型）、token 预算（硬上限）、相关性阈值（不够相关就不注入）。外加成对胜率评测——测出注入是负收益就回退。核心原则'宁可不用、不可用错'。"

## 五、维度⑤：治理质量优化（误合并 / 漏隔离）

### 5.1 症状 → 根因 → 方向

| 症状 | 根因 | 优化方向 |
|---|---|---|
| 误合并率高 | 聚类阈值太松 | 收紧聚类阈值、先 Shadow Mode 只出建议校准后再自动执行 |
| 错误隔离率低 | 缺用户否定信号 | 补用户否定信号源（最强信号）、强化 evidence 回溯 |
| 治理误判多 | 自动执行太激进 | 全部先软标记可撤销，人工确认后硬化 |

### 5.2 具体手段展开

**① Shadow Mode（影子模式）**：治理先只出建议、不自动执行，跑一段时间校准准确率，达标了再开自动执行。这是"误合并率高"最稳的解法。

**② 补用户否定信号**：用户显式否定（"你记错了 / 不对"）是最强信号，比内部矛盾、证据回溯都可靠。补上这条信号源，错误隔离率直接提升。

**③ 软标记可撤销**：治理动作全部先标 QUARANTINED / DISPUTED / PROBATION 等软状态，可回滚（undo 表），人工确认后再硬化。避免"自动合并错了改不回来"。

### 5.3 面试追问 + 答法

**Q：治理误判了怎么办？**
> "两个兜底：一是软标记可撤销——所有治理动作先标软状态、支持 undo 回滚；二是 Shadow Mode——自动执行前先影子跑校准。宁可慢、不可错。"

## 六、跨维度「杠杆式」优化（性价比最高的几个）

有些优化能同时影响多个维度，优先级天然更高：

| 杠杆 | 同时影响 | 说明 |
|---|---|---|
| 换更强 Embedding 模型 | ②检索 Recall + ③抽取去重 | 向量质量是一切的底座 |
| 换更强抽取 LLM | ①抽取 P/R + 错误率 | 源头质量决定下游 |
| 加 ngram 中文分词 | ②检索 Recall（关键词通道） | 低成本、直接提中文检索 |
| 补用户否定信号 | ⑤治理 + ③一致性 | 最强纠错信号 |

**面试加分点**：优化时优先做「杠杆项」——先问自己"这个改动只影响一个维度，还是影响多个维度"，优先做一石多鸟的。

## 七、定位 → 优化 → 度量 闭环（PDCA）

```
① 五维评测定位（哪个维度低）
② 针对性优化（按上文选方向）
③ 同一黄金集回归（改了有没有变好）
④ 没变好 → 换方向 / 根因分类错了
```

**关键**：每一步优化都要回评测集验证，不能"感觉变好了"就完。这就是「五维可归因评测」存在的意义——它既是**定位问题的工具**，又是**验证优化的试金石**。

> 例子：检索 Recall@5 低 → 调 RRF_K → 回黄金集 → 0.62→0.65 采用；改抽取 Prompt → Precision 0.81→0.79 → 回退。每个改动都有指标背书。

## 附一：面试完整串讲（3 分钟脚本）+ 追问速查

### 完整串讲脚本

> "记忆系统效果不好，我不直接说'优化'，而是**先定位**——用五维可归因评测找到是哪个维度低（抽取 Precision 低？检索 Recall 低？注入无关注入高？），因为五个维度优化方向完全不同，用错方向就白费劲。
>
> 然后**针对性优化**：抽取问题调置信度门槛和 Few-shot 反例（最便宜），检索问题调 RRF 参数、加召回通道、换 Embedding，一致性调去重阈值、扩归一化词表，注入调任务映射和 token 预算，治理用 Shadow Mode 和用户否定信号。
>
> 最后**回黄金集回归**——改了有没有变好、有没有回归，都有指标背书，形成 PDCA 闭环。
>
> 我特别强调一个反模式：不要一上来就'换更强模型'，那是成本最高、收益最不确定的一项，应该最后才考虑。"

### 追问速查

| 追问 | 一句话答案 |
|---|---|
| 效果不好先干什么？ | 先五维定位，再针对性优化，最后回黄金集验证 |
| 抽取质量差先调什么？ | 置信度门槛 + Few-shot 反例（最便宜），最后才换模型 |
| RRF 的 k 值怎么选？ | 离线评测扫参，选 Recall@K/MRR 拐点 |
| 怎么保证双写一致？ | payload 存 status + 源头过滤 + 对账脚本兜底 |
| 怎么防止过度注入？ | 任务化映射 + token 预算 + 相关性阈值 + 成对胜率 |
| 治理误判怎么办？ | 软标记可撤销 + Shadow Mode 先校准 |
| 什么是杠杆优化？ | 一个改动同时影响多个维度，优先做 |
