# 记忆系统评测与监控闭环方案

> 定位：把记忆系统的质量保障表达为一条**可落地、可归因、可越用越准**的三层闭环，明确「已实现 / 未做 / 怎么补」。
> 依赖文档：
> - [评测集设计与指标手册](./评测集设计与指标手册.md)（第①层离线评测的五维指标，本文只引用不重述）
> - [2026-09-22 完整改造实施计划](./2026-09-22-memory-complete-implementation-plan.md)（§2.4 错误分级 / §2.5 离线巡检 / §2.6 熔断降级，第②层已实现部分的依据）
> 核心原则贯穿全文：**先埋点后调阈值、宁可不删不可删错、能确定才隔离、疑似只标记。**

---

## 0. 定位：三层质量闭环

记忆系统的质量保障不是「上线前测一次」或「上线后挂几个告警」，而是一条闭环：

```
① 离线评测（静态测试集）   → 定基线、调阈值
② 实时监控 + 熔断          → 发现异常、及时止血
③ 错误记忆实时处理         → 定位错误、自主修复
④ 反馈闭环                → 错误样本反哺评测集，越用越准
```

四者分工与当前状态：

| 层 | 职责 | 回答的问题 | 当前状态 |
|---|---|---|---|
| ① 离线评测 | 用黄金评测集算五维指标 | 「这个改动有没有提升、有没有回归」 | ❌ 未做（评测集脚本/`EvaluationRunner` 未落地） |
| ② 实时监控 + 熔断 | 埋点 + 告警 + 巡检 + 断路器 | 「线上现在有没有异常、要不要止血」 | ✅ 已实现（P3 落地，见第 2 节） |
| ③ 错误记忆实时处理 | 分层检测疑似错误 + 保守处理 | 「这条记忆是不是错的、怎么处理」 | ❌ 未做（本文重点，见第 3 节） |
| ④ 反馈闭环 | 错误样本反哺评测集/Prompt/阈值 | 「错误怎么变成下一次的准确」 | ❌ 未做（是 ③ 的延伸） |

**读法**：①和②是「防守」，③和④是「进攻」。当前系统已经能「发现异常」（②），但还不能「自主纠错」（③），更不能「越用越准」（④）。本文第 3 节给出补齐 ③④ 的完整设计。

## 1. 第①层：离线评测（静态效果测试）

> 详细指标定义见 [评测集设计与指标手册](./评测集设计与指标手册.md)，本文只交代它在闭环中的定位。

### 1.1 为什么必须「先建黄金评测集」

记忆系统的质量损失可能发生在五个**互不重叠**的阶段（抽取 / 检索 / 一致性 / 注入 / 治理），如果只测「最终回答好不好」，无法定位是抽错、检索漏、还是注入乱。因此评测拆成五维，各自对应一个阶段、各自可独立算 P/R 类指标：

| 维度 | 对应阶段 | 回答的问题 |
|---|---|---|
| ① 抽取质量 | 抽取 | 该不该存？抽得准不准、漏不漏？ |
| ② 检索质量 | 检索 | 能不能检索出来？排序对不对？ |
| ③ 一致性与记忆变乱 | 存储 + 治理 | 库有没有被污染？重复、冲突、双写不一致多少？ |
| ④ 注入质量 | 注入 | 注入组装是否合理、是否超预算、是否提升回答？ |
| ⑤ 治理质量 | 治理 | 合并/隔离/归档做得对不对？会不会误伤？ |

### 1.2 在闭环中的三件事

离线评测承担三个不可替代的角色：

1. **定基线**：改造前在同一黄金集上跑出 `Recall@5`、`MRR`、抽取 P/R 等的具体数字，作为后续所有改动的对照锚点。
2. **调阈值**：熔断阈值、融合参数（`RRF_K`、`α/β` boost 系数）、余弦去重阈值（0.9）等，都靠离线评测确认「改这个值有没有变好」。
3. **守护回归**：每次改 Prompt / 融合公式 / 阈值，都在**同一黄金集**上重跑，输出「有提升还是无回归」。

### 1.3 与第④层的接缝

黄金评测集之外，还有一条「免费的」评测数据源——**真实用户纠错**（第 3 节第④层闭环的产物）。用户纠错样本经人工复核后自动归档进评测集，作为 negative case 扩充黄金集。这是「离线评测」与「线上纠错」在闭环里汇合的地方。

## 2. 第②层：实时监控 + 熔断（已实现）

> 本节描述的是 P3 已落地的真实代码，不是计划。以下类/方法名可直接在仓库里找到。

### 2.1 指标层：MemoryMetrics + IMemoryMetricsPort

- **架构**：`MemoryMetrics` 落在 `infrastructure` 层（`cn.sutone.ai.infrastructure.metrics.MemoryMetrics`），实现 domain 侧端口 `IMemoryMetricsPort`（`cn.sutone.ai.domain.agent.adapter.repository.IMemoryMetricsPort`）。domain 层（`MemoryExtractor` / `MemoryRetriever` / `MemoryManager` / `MemoryVectorSyncJob`）只依赖端口，不反向依赖 infrastructure，避免循环依赖（标准端口-适配器模式）。
- **命名规范**：`memory.<域>.<指标>`，仿 `MqMetrics` 构造注入 `MeterRegistry`。

已实现的指标端口（16 个方法 + 1 个派生率 Gauge），覆盖七个域：

| 域 | 指标 | 类型 |
|---|---|---|
| Qdrant | `memory.qdrant.failures[op]` | Counter |
| 向量补偿 | `memory.vector.sync.pending` / `.success` / `.failed` | Gauge / Counter |
| 抽取 | `memory.extraction.accepted[type]` / `.rejected[reason]` / `.reject_rate` | Counter / Gauge |
| 检索 | `memory.retrieval.recalled[channel]` / `.filtered[reason]` / `.duration` | Counter / Timer |
| 链路 | `memory.pipeline.duration` / `memory.rerank.duration` | Timer |
| 写入 | `memory.write.insert[type]` / `.update[type]` / `.duplicate` / `.conflict` | Counter |

含 `type` / `reason` / `channel` / `op` 等 tag 维度展开后，可观测序列超过 40 个。

**首月观测面（先埋点后调阈值）**：`MemoryMetrics` 的注释明确——上线首月只对四个核心指标告警（`qdrant.failures` / `vector.sync.pending` / `extraction.accepted` / `extraction.rejected`），其余指标仅埋点记录、不告警，待基线收集后按豆包阈值再启用。派生率 `reject_rate` 由 `@Scheduled refreshDerivedRates()` 周期计算（默认 60s），首月只暴露不触发。

**指标的双重用途（关键）**：指标不只是「告警完就结束」，而有两条消费路径：

```
指标异常 ──┬── ① 触发熔断（异常信号：写失败率/积压/驳回率超阈值 → 关闭注入止血）
           └── ② 驱动反哺（质量下降信号：重复率/冲突率上升 → 定位根因 → 反哺 Prompt/阈值）
```

前者是「防守」（异常时止血），后者是「进攻」（质量下降时进化）。同一个指标，既是熔断的扳机，又是反哺的输入——这是监控指标设计的核心洞察，避免「只告警、不改进」的死循环。

### 2.2 熔断层：MemoryCircuitBreaker + inspectCorrectionCircuit

- **断路器**（`domain/.../service/memory/circuit/MemoryCircuitBreaker`）：持有 `AtomicBoolean degraded` 作为「注入是否被熔断」的**唯一真值源**。`memory.inject.enabled` 配置仅作启动初始值，运行时不再依赖静态 `@Value`。对外暴露 `open(reason)` / `close()` / `halfOpen(sampledAccuracy)` / `isDegraded()`。
- **降级分级**：
  1. 一级降级：断路器 `open` → `MemoryManager.retrieveContext()` 直读 `isDegraded()` 返回空上下文（避免把错误/陈旧记忆注入误导 LLM），写路径保留。
  2. 二级降级：暂停结构化写入，仅归档原始对话片段（`status=OBSERVATION`）。
  3. 三级：人工介入告警。
- **触发巡检**（`infrastructure/.../job/MemoryGovernanceJob.inspectCorrectionCircuit`，每分钟）：首月 `alert.enabled=false` 时直接返回不触发（先埋点后调阈值）。启用后当前接入两个可测信号——抽取驳回率超阈值、向量同步积压超阈值（`VECTOR_SYNC_PENDING_THRESHOLD=500`），任一触发即 `circuitBreaker.open(reason)`。`qdrant.failures` 写失败率、`retrieval.p99` 两路信号在代码注释里标注为「TODO 后续接」。
- **恢复灰度**：`halfOpen(sampledAccuracy)` 要求抽样准确率 > 0.95（由离线评测集确认）才关闭断路器，再按 10% → 50% → 100% 灰度放量。

### 2.3 治理巡检层：MemoryGovernanceJob（任务 1-4 已实现）

治理任务已实现真实逻辑（非 TODO），并遵守「先软标记、后硬化」可逆性契约（写 `memory_governance_undo` + `memory_governance_undo_item`）：

| 任务 | 调度 | 动作 | 状态 |
|---|---|---|---|
| `clusterDuplicates` 重复聚类 | 每日 3:30 | 非代表行软标记 `MERGE_PENDING` | ✅ |
| `checkFactConsistency` 事实一致性巡检 | 每周一 4:00 | 同 `(user,subject,predicate)` 异 value 的互斥对，保留最早行为 ACTIVE，其余标 `DISPUTED` | ✅ |
| `cleanExpired` 过期清理 | 每日 5:00 | 过期且 30 天未访问 → `ARCHIVED` | ✅ |
| `spotCheckHallucination` 幻觉抽检 | 每周日 6:00 | 抽样 confidence 0.8-0.9 → 回溯 evidence → 不支撑者 `QUARANTINED` | ✅ |
| `inspectCorrectionCircuit` 熔断巡检 | 每分钟 | 见 2.2 | 🟡 已实现但仅接 2 信号 |

> 关键保守策略（`MemoryExtractor.verifyEvidence`）：LLM 不可用 / 解析失败 / 输出「不确定」均**放行**（返回 true），仅在明确输出「不支持」时判疑似幻觉（返回 false），避免误隔离。这是「宁可不删、不可删错」原则在代码里的体现。

### 2.4 已实现「状态机」一页速查

`MemoryStatus` 权威枚举（`domain/.../model/valobj/MemoryStatus`）已落地，可检索性两段式：默认注入/召回只取 `ACTIVE`；历史查询（带时间限定）取 `ACTIVE/SUPERSEDED/ARCHIVED`；`DISPUTED` 仅经独立裁决入口可达；`PROBATION/QUARANTINED/MERGE_PENDING/OBSERVATION` 仅审计/治理视图可见。这是第 3 节错误处理的**动作出口**。

## 3. 第③层：错误记忆实时处理（未做，本文重点）

第②层能「发现异常、关闭注入、软标记疑似」，但它**不能判断「某一条具体记忆是对是错」**。第③层要补齐的正是这个能力——但它有一个无法绕过的根本边界，必须先说清楚。

### 3.1 根本边界（最重要的一段）

**记忆系统「自主判断内容对错」本质需要外部 ground-truth，而系统没有。**

系统手里只有「用户告诉过它的东西」——一段抽取出来的 `content` 加一条 `evidence` 原文片段，没有「真相」。它无法区分：

- 「我记的这条是错的」 vs 「用户后来改主意了」；
- 「这条是幻觉」 vs 「用户说过但证据没存全」；
- 「这条过时了」 vs 「用户还没更新」。

所以**能做的是「分层检测疑似错误 + 保守处理」，不能 100% 自主判错**。处理强度必须与「信号可靠度」严格挂钩：

| 可靠度 | 判断依据 | 处理强度 |
|---|---|---|
| 能确定（被用户否认 / 内部矛盾） | 有明确外部或内部证据表明「这条不对」 | 隔离（QUARANTINED / SUPERSEDED），不删原始行 |
| 疑似（证据缺失 / 低置信） | 只是「撑不起来」或「置信度低」，不排除是证据没存全 | 标待确认（PROBATION / 复审队列），**不自动删** |

**一句话原则：宁可不删、不可删错。** 能确定 → 隔离；疑似 → 标待确认，等证据。所有处理先软标记（改 `status`）、写撤销记录，不物理删除、不改向量，确认后才硬化。

### 3.2 四层信号检测（判断记忆是否错，从强到弱）

| 层 | 信号 | 可靠度 | 处理 | 现状 |
|---|---|---|---|---|
| ① 用户显式否定 | "你记错了 / 不对 / 我不用 X 了" | 最强 | 立即 `QUARANTINED` + `SUPERSEDED` | ❌ 缺信号源（无否定解析 / 无纠错 API） |
| ② 内部一致性冲突 | 同 `subject` 异 `value` | 强 | `DISPUTED` 等裁决 | ✅ `checkFactConsistency` |
| ③ 证据回溯失败 | `evidence` 撑不起 `content` | 中 | `QUARANTINED` 软隔离 | ✅ `spotCheckHallucination` + `verifyEvidence` |
| ④ 统计异常 | 低置信高频注入 / 驳回率飙升 | 弱 | 降权 / 熔断，**不隔离单条** | 🟡 指标已埋、熔断待接 |

逐层说明：

- **第①层（最强，未做）**：用户明确否定是唯一接近 ground-truth 的信号，但它依赖「系统能听懂用户说"记错了"并把否定指向具体某条记忆」——这需要独立的纠错信号源（见 3.4），当前完全没有。
- **第②层（强，已实现）**：`checkFactConsistency` 每周按 `(user_id, subject, predicate)` 聚合 ACTIVE 记忆，发现同谓词异值（如「技术栈 Java」vs「技术栈 Python」）就把非最早行标 `DISPUTED`。它不需要外部真值，纯粹靠库内矛盾自证「至少有 N-1 条是错的」，但不能断定哪条对。
- **第③层（中，已实现）**：`spotCheckHallucination` 抽样 confidence 0.8-0.9 的「灰色地带」记忆，回溯 `evidence` 校验是否被原文支撑，不支撑者 `QUARANTINED`。可靠度中，因为它只在「证据确实撑不起」时成立，但「证据没存全」不等于「内容错」，故采取保守策略（verifyEvidence 只在明确「不支持」时判疑似幻觉）。
- **第④层（弱，部分接入）**：驳回率飙升、低置信高频注入等统计信号，只能说明「整体质量在恶化」，无法定位具体哪条错，所以处理是**降权 / 熔断整条链路**，而不是隔离单条记忆。指标已埋，熔断仅接入 2 路，`qdrant.failures` / `retrieval.p99` 待接。

### 3.3 三层学习（定位错误后怎么处理）

检测只是第一步，处理分三层，越往后越「慢」但越「值钱」：

**第 1 层 实时止血（秒级，改状态）**
- 软隔离（`status=QUARANTINED` / `SUPERSEDED`），原始行与向量保留。
- 写撤销记录（复用 `memory_governance_undo` + `memory_governance_undo_item`），可回滚。
- 用户给了正确值 → `SUPERSEDE` 旧版本 + 新版本 `ACTIVE`（版本化更新）。
- 派生记忆（旧记忆被替代后，可能影响依赖它的其他记忆）入复审队列。

**第 2 层 沉淀经验（分钟级，落库）**
- 写错误样本库 `memory_error_sample`，字段包含：错误内容 + 原始对话 + 证据 + 根因分类 + 模型版本 + 置信度（见 3.4 DDL）。
- 根因分类：`hallucination`（幻觉）/ `over_inference`（过度引申）/ `attribution_error`（归属错误）/ `expired`（过期失效）/ `conflict`（内部冲突）/ `duplicate`（重复）。

**第 3 层 反哺改进（天级，改评测/Prompt/阈值）**
- 错误样本 → 评测集 **negative case**（人工复核后归档，扩充黄金集）。
- 根因分布 → **Prompt 迭代**（哪类根因占比高，就针对性改抽取/校验规则）。
- confidence 分布 → **阈值校准**（0.7 低置信线、0.8-0.9 抽检带、余弦 0.9 等）。

**根因分类决定反哺方向**（不能笼统「改进」，否则反哺没靶子）：

| 根因 | 反哺到哪 |
|---|---|
| hallucination（幻觉，无证据） | 抽取 Prompt（要求 evidence 强校验） |
| over_inference（过度引申，有证据但撑不起） | 阈值（收紧置信度门槛） |
| attribution_error（归属错误，AI 冒充用户） | 规则（attributed_to 隔离） |
| expired（过期失效，曾经对现在错） | 生命周期（过期策略） |

同一个「错误样本」，根因不同、反哺目标完全不一样——这正是错误样本库必须带 `error_type` 根因分类字段的原因。

### 3.4 落地设计（要补的硬缺口）

第③层缺失的三块硬能力，按「先有信号源 → 再沉淀样本 → 最后反哺」的顺序补齐：

#### 3.4.1 纠错信号源（补第①层，当前完全没有）

**方案 A：对话否定信号解析**（抽取阶段识别）
在抽取 Prompt 增加「强否定词识别」规则：当用户消息含「记错了 / 不对 / 不用了 / 早就不 / 改成」等强否定词，且指向某个已存在的 `subject/predicate` 时，输出纠错候选（`operation=DELETE` / `UPDATE` + `target_memory_id`），而非当普通新记忆 ADD。这条走 P1 已有的 `operation` 字段，是最省新入口的做法，但受限于「否定必须在抽取时被识别到」。

**方案 B：用户纠错 API**（记忆管理页主动报错）
新增端点，让用户在记忆管理页点「这条不对」，主动标记：

```text
POST /api/v1/memory/{id}/report-error
Body: { "reason": "wrong" | "outdated" | "not_mine", "correction": "可选，正确内容" }
```

落库为 `memory_error_sample`（`correction_source=user_api`）+ 关联记忆软隔离。这条是**最强、最准**的信号，但依赖产品侧加交互入口。

> 建议两者都做：方案 A 是「被动捕获」（用户说错了自动识别），方案 B 是「主动上报」（用户点按钮）。B 的样本质量远高于 A，是第④层反馈闭环最干净的数据源。

#### 3.4.2 错误样本库（补第②层学习）

```sql
CREATE TABLE memory_error_sample (
    id                 BIGINT AUTO_INCREMENT PRIMARY KEY,
    memory_id          BIGINT       NULL     COMMENT '关联记忆 id（软隔离/删除后仍可追溯）',
    user_id            BIGINT       NOT NULL COMMENT '归属用户',
    error_type         VARCHAR(32)  NOT NULL COMMENT '根因分类：hallucination/over_inference/attribution_error/expired/conflict/duplicate',
    content            TEXT         NULL     COMMENT '错误记忆内容（脱敏后）',
    evidence           TEXT         NULL     COMMENT '抽取时的证据原文片段（脱敏后）',
    original_dialogue  TEXT         NULL     COMMENT '原始对话上下文（脱敏后）',
    correction_source  VARCHAR(16)  NOT NULL COMMENT '来源：dialogue_negation/user_api/consistency/evidence_fail/stats',
    model_version      VARCHAR(64)  NULL     COMMENT '抽取模型 + prompt 版本',
    confidence         DOUBLE       NULL     COMMENT '抽取时的置信度（用于阈值校准）',
    detected_at        DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    review_status      VARCHAR(16)  NOT NULL DEFAULT 'PENDING' COMMENT 'PENDING/ACCEPTED/REJECTED（人工复核）',
    reviewed_at        DATETIME     NULL,
    feedback_round     INT          NOT NULL DEFAULT 0 COMMENT '已反哺到评测集的轮次',
    INDEX idx_error_type (error_type),
    INDEX idx_review (review_status),
    INDEX idx_memory (memory_id)
) COMMENT '记忆错误样本库（第③层错误实时处理的沉淀层，反哺评测集/Prompt/阈值）';
```

关键设计点：
- **不直接改 `memory_record`**，错误样本是独立旁路，避免污染权威数据。
- `review_status` 字段强制「人工复核后才反哺评测集」，防止错误样本本身带噪污染黄金集。
- `correction_source` 区分信号来源，用于后续统计「哪类信号最准」。

#### 3.4.3 反哺链路（补第③层学习）

```
memory_error_sample（review_status=ACCEPTED）
        │
        ├─→ 评测集 negative case（人工复核后，扩充黄金集）
        ├─→ 根因分布 → 抽取/校验 Prompt 迭代
        └─→ confidence 分布 → 阈值校准（0.7 低置信线 / 抽检带 / 余弦阈值）
```

这一步把「错误」变成「下一次更准的燃料」，是闭环第④层的落地形态。它依赖 3.4.1 有信号源、3.4.2 有样本库，所以排最后。

**反哺要闭环度量**（否则不知道反哺有没有用，即 PDCA 的 Check/Act 环节）——反哺后回归看这几个指标是否改善：

- `memory.error` 计数是否下降（错误在变少）
- 抽取 Precision / Recall 是否提升（评测集回归）
- 无关注入率是否下降（注入更准）

若没改善，说明**根因分类错了或反哺方向错了**，需重新定位——这就是「防错→查错→纠错→优化」完整闭环的最后一环。

## 4. 面试角度

**被问「你怎么保证记忆系统的质量？」** 用三层闭环框架答，先给结构，再给关键判断：

> 我用三层闭环来保证质量：
> 1. **离线定基线**——先建黄金评测集，把质量拆成抽取/检索/一致性/注入/治理五个可归因维度，每维独立算 P/R，能定位「到底是抽错、检索漏、还是注入乱」，而不是笼统说效果不好。
> 2. **在线监控熔断**——上线后埋点 40+ 指标 + 熔断器，发现 Qdrant 写失败率、向量补偿积压、抽取驳回率等异常就关闭记忆注入止血，首月先埋点后调阈值，不预设未经验证的准确率承诺。
> 3. **实时纠错反哺**——用分层信号检测错误记忆（用户否定 > 内部一致性冲突 > 证据回溯失败 > 统计异常），错误样本落库后反哺评测集 negative case、Prompt 迭代、阈值校准，越用越准。

**关键判断（加分点）**：强调「**宁可不删、不可删错**」——记忆系统没有外部 ground-truth，不能 100% 自主判错，所以「能确定的（被否认/内部矛盾）才隔离，疑似的（证据缺失/低置信）只标待确认，不自动删」；所有治理操作先软标记、写撤销记录、确认后才硬化。这体现的是对「可逆性」和「不误伤」的工程敬畏，而不是「自动删错误」的表面自动化。
