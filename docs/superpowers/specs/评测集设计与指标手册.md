# 记忆系统评测集设计与指标手册

> 定位：为记忆系统（抽取→存储→检索→注入→治理）提供一套**可落地、可量化、可归因**的效果评测方案。
> 配套文档：[完整改造计划](./2026-09-22-memory-complete-implementation-plan.md)（§8 测试与评测）、[持续治理方案](./2026-09-22-memory-quality-fallback-design.md)（§12 专项验收）。
> 核心思想：**先建黄金评测集（ground-truth），再对每个维度算 P/R 类指标，且每个维度能独立定位「质量损失发生在哪个阶段」。**

---

## 0. 为什么需要「分维度」评测

记忆系统的质量损失可能发生在五个互不重叠的阶段，如果只测「最终回答好不好」，无法定位是抽错、检索漏、还是注入乱。因此把评测拆成五维，各自对应一个阶段：

| 维度 | 对应阶段 | 回答的问题 |
|---|---|---|
| ① 抽取质量 | 抽取 | 该不该存？抽得准不准、漏不漏？ |
| ② 检索质量 | 检索 | 能不能检索出来？排序对不对？ |
| ③ 一致性与记忆变乱 | 存储 + 治理 | 库有没有被污染？重复、冲突、双写不一致多少？ |
| ④ 注入质量 | 注入 | 注入组装的记忆是否合理、是否超预算、是否提升回答？ |
| ⑤ 治理质量 | 治理 | 合并/隔离/归档做得对不对？会不会误伤？ |

五维独立计算，可以做到「维度② Recall@K 低 → 问题在检索，不在抽取」。

## 1. 黄金评测集构建（一切评测的基础）

### 1.1 两类评测集

| 评测集 | 形态 | 用于哪个维度 |
|---|---|---|
| **对话→记忆对** | 一段对话（用户消息 + AI 回复）+ 人工标注「该抽出的记忆集」 | ① 抽取质量 |
| **query→记忆对** | 一个 query + 人工标注「该召回的记忆 id 列表」 | ② 检索质量、④ 注入质量 |

### 1.2 标注格式

**对话→记忆对**（每个 ground-truth 记忆含结构化字段，方便逐字段比对）：

```json
{
  "dialogue_id": "d001",
  "messages": [
    {"role": "user", "content": "我们项目用 Java 17 + Spring Boot 3.4，数据库是 MySQL 8.0"},
    {"role": "assistant", "content": "好的，记下了你的技术栈。"}
  ],
  "ground_truth_memories": [
    {
      "content": "技术栈 Java 17 + Spring Boot 3.4 + MySQL 8.0",
      "type": "fact",
      "attributed_to": "user",
      "subject": "user",
      "predicate": "tech-stack",
      "value": "Java 17 + Spring Boot 3.4 + MySQL 8.0"
    }
  ]
}
```

**query→记忆对**：

```json
{
  "query_id": "q001",
  "query": "用户平时用什么技术栈？",
  "task_type": "LEGACY",
  "relevant_memory_ids": [101, 102],   // 该召回的记忆 id（排序无关，Recall 用）
  "ranked_memory_ids": [101, 102, 103]  // 按相关度排序（NDCG 用，可选）
}
```

### 1.3 覆盖矩阵（类型 × 边界 case）

评测集必须覆盖**4 种记忆类型 × 6 类边界 case**，否则指标虚高：

| 边界 case | 说明 | 测什么 |
|---|---|---|
| 相似但不同 | 「用户用 Java」「用户偏好 Java」是两条 | 身份化不误合并 |
| 同义重复 | 「主要写 Java」「平时用 Java」是同一条 | 去重 |
| 时间演化 | 「以前 Java 8」「现在 Java 17」 | 版本化演进 |
| AI 输出冒充用户 | AI 推测的偏好不该进 fact/preference | 归属隔离 |
| 一次性指令 | 「帮我写篇 JVM 文章」不是长期偏好 | 低价值过滤 |
| 跨会话碎片 | 会话 A「用 Java」、会话 B「做 Agent」 | 跨会话关联 |

### 1.4 规模与来源

- **起步规模**：`query→记忆对` ≥ 200 条；`对话→记忆对` ≥ 50 段（覆盖上表 4×6=24 种组合）。
- **来源**：真实对话脱敏 + 人工构造边界 case（边界 case 必须人工构造，真实对话里稀疏）。
- **逐步扩充**：上线后从真实用户纠错/反馈中持续补充（见 §5）。

### 1.5 隔离原则（防指标虚高）

1. **评测样本不得出现在抽取 Prompt 的 Few-shot 里**，否则 P/R 虚高。
2. **评测集与训练/调参集隔离**：调阈值用的集不能拿来报最终指标（防过拟合）。
3. **黄金集版本化**：每次改动 Prompt/融合公式，都要在**同一黄金集**上回归，才能对比「有提升还是无回归」。

## 2. 五维评测指标（公式 + 构建 + 计算）

### 维度① 抽取质量（该不该存）

| 指标 | 公式 | 说明 |
|---|---|---|
| Extraction Precision | 抽取正确数 / 抽取总数 | 抽出的记忆里有多少真该存。低 = 抽了太多垃圾 |
| Extraction Recall | 抽取正确数 / ground-truth 总数 | 该存的记忆里有多少被抽出。低 = 漏抽 |
| 错误归属率 | 误标 attributed_to 数 / 抽取总数 | AI 内容被标成 user 的比例 |
| 重复抽取率 | 与已有记忆语义重复的新增数 / 抽取总数 | 去重失效 |
| 低价值写入率 | 一次性指令/闲聊被抽成记忆数 / 抽取总数 | 长期价值判断失效 |

**构建**：对话→记忆对（§1.1）。
**计算**：跑抽取得到候选记忆，逐条与 ground-truth 对齐（content 语义匹配 + type 匹配 + attributed_to 匹配，任一不符算「错误」），再算 P/R。
**判定**：P ≥ 0.85 且 R ≥ 0.80 视为达标（初始参考值，用评测集校准）。

### 维度② 检索质量（能不能检索出来）

| 指标 | 公式 | 说明 |
|---|---|---|
| Recall@K | 命中相关记忆数 / 相关记忆总数 | K 通常取 5 / 10 |
| MRR | Σ(1/首个相关记忆的排名) / query 数 | 第一个相关记忆排多前 |
| NDCG@K | DCG@K / IDCG@K | 相关记忆是否排在前面 |

**构建**：query→记忆对（§1.1），标注 `relevant_memory_ids` + `ranked_memory_ids`。
**计算**：对每个 query 跑检索得 top-K，比对 ground-truth 算命中/排序。
**判定**：Recall@5 ≥ 改造前基线（同一黄金集回归），且 MRR 提升 ≥ 5% 或 NDCG@5 不下降。

### 维度③ 一致性与记忆变乱

| 指标 | 公式 | 说明 |
|---|---|---|
| 重复率 | 存在多个 ACTIVE 同 (subject,predicate) 的记忆数 / 有效记忆总数 | 去重失效 |
| 冲突率 | 同 subject 存在互斥 value 的对数 / 有效记忆总数 | 冲突检测失效 |
| MySQL/Qdrant 一致率 | Qdrant points 数 == MySQL SYNCED 数 的比例 | 双写一致性 |
| 过期残留率 | 已过 expire_time 仍 ACTIVE 的数 / 有效记忆总数 | 生命周期过滤失效 |

**构建**：不需要人工标注——用**离线巡检脚本 + 对账脚本**扫描库直接统计。
**计算**：定时跑巡检，输出重复簇/冲突对/过期清单，抽样人工复核「变乱」比例。
**判定**：重复率 < 5%、冲突率 < 3%、一致率 > 99.9%、过期残留率 < 2%。

### 维度④ 注入质量（组装是否合理）

| 指标 | 公式 | 说明 |
|---|---|---|
| 无关注入率 | 无关注入数 / 总注入数 | 注入的记忆里有多少与当前任务无关 |
| Token 超预算率 | 超预算次数 / 总注入次数 | Token 预算控制失效 |
| 成对胜率 | 有记忆回答优于无记忆回答的比例 | 记忆是否真的「有帮助」 |
| 事实错误率 | 注入记忆与用户真实事实不符的比例 | 错误记忆被注入 |

**构建**：构造任务（写大纲/写正文/润色），标注「该任务该注入哪些记忆」+「哪些记忆是无关的」。
**计算**：
- 无关注入率 = 无关注入数 / 总注入数（人工或 LLM 判每条注入是否相关）。
- 成对胜率 = 同一任务，有记忆 vs 无记忆各生成一次，人工/LLM 判哪个更好。
**判定**：无关注入率 < 10%、Token 超预算率 < 1%、成对胜率 > 55%。

### 维度⑤ 治理质量（关联是否合理）

| 指标 | 公式 | 说明 |
|---|---|---|
| 误合并率 | 误合并数 / 治理合并总数 | 把不同记忆错误合并 |
| 错误隔离率 | 该隔离却未隔离数 / 应隔离总数 | 错误记忆漏治理 |
| 误归档率 | 误归档数 / 治理归档总数 | 把有效记忆错误归档 |
| 撤销成功率 | 撤销成功数 / 撤销尝试总数 | 治理可逆性 |

**构建**：人工标注「哪些是重复簇、哪些是冲突对、哪些该过期」，作为治理 ground-truth。
**计算**：**Shadow Mode 阶段**让治理任务只出建议、不改数据，把「治理建议」vs「人工标注」逐条比对，算 P/R。
**判定**：误合并率 < 5%、错误隔离率 > 90%、误归档率 < 3%、撤销成功率 = 100%（硬性）。

## 3. 分阶段定位（问题归因）

五维指标独立，可以反推「质量损失在哪个阶段」：

| 症状 | 归因 |
|---|---|
| 维度① Recall 低、维度② Recall 也低 | 抽取漏了 → 先修抽取 Prompt/身份 |
| 维度① P/R 正常、维度② Recall 低 | 检索漏了 → 修融合/召回/精排 |
| 维度① 重复率高、维度③ 重复率高 | 去重/身份化失效 → 修 identity |
| 维度② Recall 正常、维度④ 无关注入率高 | 注入组装问题 → 修过滤/预算/任务映射 |
| 维度⑤ 误合并率高 | 治理误判 → 修聚类阈值/加人工确认 |

**结论**：这套评测能回答「到底是抽错、检索漏、还是注入乱」，而不是笼统说「效果不好」。

## 4. 评测 harness 与实施顺序

### 4.1 harness 设计

- 复用现有 `MemoryEvaluationTest`（`@SpringBootTest`）作为集成评测入口，但**把评测集抽到独立文件**（JSON/YAML），不硬编码在测试里。
- 新增 `EvaluationRunner`：加载评测集 → 跑抽取/检索/注入 → 输出五维指标到报告文件（markdown/CSV）。
- 治理维度单独用 `GovernanceShadowRunner`：跑治理任务（Shadow Mode）→ 输出治理建议 → 与人工标注比对。

### 4.2 实施顺序（与开发阶段对齐）

1. **P1 完成时**：先建「对话→记忆对」评测集，跑维度①（抽取质量），标定抽取 P/R 基线。
2. **P2 完成时**：建「query→记忆对」，跑维度②（检索质量）+ 维度④（注入质量），标定检索基线。
3. **P3 治理落地时**：跑维度③（一致性）+ 维度⑤（治理质量），用 Shadow Mode 先标定治理准确率。
4. **每次改动回归**：改 Prompt/融合公式/阈值后，在同一黄金集上重跑，对比「有提升还是无回归」。

### 4.3 阈值校准原则

所有「判定阈值」（P≥0.85、Recall@5 基线等）都是**初始参考值**，不是承诺值。上线后用真实数据 + 用户纠错反馈（见下）持续校准，形成「先埋点 → 收集基线 → 定阈值 → 迭代」的闭环。

## 5. 线上反馈闭环（把真实用户变成评测信号）

黄金评测集之外，还有一条「免费的」评测数据源——**用户行为**：

| 信号 | 含义 | 对应指标 |
|---|---|---|
| 用户明确纠错「你记错了」 | 错误记忆 | 维度④ 事实错误率、维度⑤ 错误隔离率 |
| 用户重复陈述同一事实 | 记忆没存对/没召回 | 维度① Recall、维度② Recall |
| 用户否定旧记忆 | 该更新/删除 | 维度③ 冲突率 |

**闭环**：把用户纠错样本自动归档进评测集（人工复核后），持续扩充黄金集、修正指标基线——这正是豆包方案「PDCA 规则迭代」在评测侧的落地。
