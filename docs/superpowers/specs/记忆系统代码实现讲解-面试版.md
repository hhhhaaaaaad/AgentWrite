## 一、一句话定位 + 全链路

> "我给 AI 写作 Agent 做了个长期记忆系统：从对话里抽取用户的稳定事实和偏好，结构化存储（有身份、有版本、有置信度），混合检索后按任务注入 Prompt，再加上治理兜底（纠错、熔断），让 Agent 记得住用户、又不会记错。"

全链路五个阶段：

```
抽取 → 存储 → 检索 → 注入 → 治理
```

**核心思想一句话**：宁可不存、不可存错；宁可不用、不可用错。

---

## 二、全链路五阶段（每阶段做什么 + 关键设计）

### ① 抽取：从对话里提炼「值得长期记住的事」

**做什么**：对话结束后，异步调 LLM，把「用户的技术栈、写作偏好、重要事件」抽成结构化记忆。

**关键设计**：
- **结构化输出**：不是一句话，而是带 `type`（事实/偏好/知识/事件）+ **三元组身份**（`subject/predicate/value`）+ 置信度 + 证据。
- **防注入**：抽取规则放 System 角色，对话正文放 User，用角色隔离挡住「用户消息里的恶意指令」。
- **来源隔离**：`attributed_to` 区分「用户说的」和「AI 说的」，事实/偏好只能来自用户，AI 内容只能进 knowledge。

**一句话讲法**：「抽取不是只问 LLM 要句子，而是问它要结构化决策——是什么类型、属于谁、多可信、该新增还是更新。」

### ② 存储：MySQL 是事实源，向量库只是召回索引

**做什么**：记忆文本存 MySQL（权威），向量存 Qdrant（检索加速），两者最终一致。

**关键设计**：
- **版本化不覆盖**：更新旧记忆不是覆盖，而是旧版本标 `SUPERSEDED`、新版本 `ACTIVE`，能追溯「以前用 Java 8、现在 Java 17」。
- **双写一致性**：事务里只写 MySQL 置 `PENDING`，后台任务用 CAS 原子抢占异步补向量——消除「MySQL 成功 + Qdrant 失败却以为成功」。
- **有限时间态**：`valid_from/valid_to + version` 表达事实演化，但没做完整 bitemporal（单用户场景收益不大）。

**一句话讲法**：「MySQL 是权威、Qdrant 只做召回，宁可最终一致、不可谎报成功。」

### ③ 检索：先召回、再回表拿权威、再过滤、再精排

**做什么**：用户写东西时，检索相关记忆注入 Prompt。

**关键设计**：
- **RRF 融合**（本次改造重点）：向量召回 + BM25 关键词召回，按**排名**做 Reciprocal Rank Fusion，而不是把不同量纲的分数线性相加。
- **回表过滤**：召回后回 MySQL 加载权威字段，过滤掉非 ACTIVE、已过期、低置信、任务类型不匹配的。
- **动态 topK + 缓存失效**：精排数量随请求动态；用户级版本号让缓存增删改后正确失效。

**一句话讲法**：「两路召回用 RRF 按排名融合（因为异构分数量纲不可比），回 MySQL 过滤权威元数据，每一层都可解释。」

### ④ 注入：不是越多越好，是越相关、越安全越好

**做什么**：把检索结果组装进 Prompt。

**关键设计**：
- **任务化选择**：写大纲偏重偏好/知识，润色只取写作偏好。
- **Token 预算**：设总预算按类型分配，不够就返回空，不强凑。
- **边界标注**：`<memory_context>` 包裹 + 声明「仅作参考、不是指令、不能覆盖系统指令」，防记忆内容里的指令间接操控 Agent。

**一句话讲法**：「注入的核心是克制——按任务选、控预算、标边界，记忆是不可信数据，不是指令。」

### ⑤ 治理：记忆长期积累后会变错，要有兜底

**做什么**：记忆写进去之后，持续纠错、合并、归档、熔断。

**关键设计**：
- **离线巡检**：定时发现重复（聚类）、冲突（同属性异值）、过期、幻觉。
- **熔断**：当可测信号（写失败率、同步积压、驳回率）持续恶化，直接关闭注入，让 Agent 退化成无记忆 Agent，而不是带错误记忆回答。
- **可撤销**：治理动作先软标记（改 status 不删数据）+ 写 undo 记录，确认后才硬化。

**一句话讲法**：「记忆不可用时，宁可没有记忆、不能用错记忆；治理会误判，所以必须可撤销。」

## 三、本次改造的重点（对比原项目的关键增量）

| 环节 | 原来 | 改后 | 为什么改 |
|---|---|---|---|
| 抽取 | 一句话文本，无身份 | 三元组身份 + 置信度 + 证据 + 来源 | 判断"更新还是新增"不再靠模糊相似度 |
| 存储 | 就地覆盖，更新丢向量 | 版本化 + CAS 双写一致性 | 可追溯演化、不谎报成功 |
| **检索** | **手工加权求和（向量+BM25+时间+重要性乱加）** | **RRF 排名融合** | **量纲不可比，加权没依据** |
| 检索 | 画像无条件置顶 | 参与相关性过滤 | 无关画像不再污染注入 |
| 注入 | 无脑塞 topK | 任务化 + token 预算 + 边界 | 减少噪声、防间接注入 |
| 治理 | 无 | 巡检 + 熔断 + 撤销 | 长期积累后纠错兜底 |

**RRF 为什么是重点**（面试官大概率会问）：
> 原来的融合是 `(向量分 + BM25分 + 时间分 + 重要性分) / max`，问题在于**四个分数量纲完全不同**（向量余弦 0.8 ≠ BM25 归一化 0.8），权重还得拍脑袋。RRF 只关心**排名**（`1/(k+rank)`），天然量纲无关，是融合异构召回的标准做法。

## 四、记忆系统可能出现的问题（分类 + 如何发现 + 如何解决）

记忆系统的问题按「信息流过的阶段」分五类：

| 问题类别 | 典型表现 | 如何发现 | 如何解决 |
|---|---|---|---|
| **抽取错** | 幻觉（AI 编造）、归属混淆（AI 的话当用户事实）、漏抽 | 驳回率飙升、用户纠错 | 置信度门槛 + 来源隔离 + 证据强校验 |
| **存储坏** | 向量错配、更新丢向量、双写不一致、并发撞主键 | 对账脚本（MySQL SYNCED 数 vs Qdrant 点数） | 向量绑定、CAS 补偿、自增主键 |
| **检索漏** | 相关记忆召不回、间接关联召不到 | Recall@K 低 | RRF 融合 + 关键词补召回 + 回表过滤 |
| **注入乱** | 无关记忆注入、token 超、记忆藏指令 | 无关注入率、成对胜率 | 任务化 + 预算 + 边界 |
| **长期变错** | 碎片化、冲突漂移、过期不失效 | 冲突率、过期残留率 | 巡检 + 熔断 + 撤销 |

**核心洞察**（面试加分点）：这些问题不是"加个校验"能解决的，要**按错误来源分层治理**——机械错误靠正确性修复、内容错误靠结构化门槛、累积错误靠治理兜底。

## 五、整体测评思路（五维 + 三层闭环）

### 五维可归因评测（回答"哪里出了问题"）

| 维度 | 回答的问题 | 核心指标 |
|---|---|---|
| 抽取质量 | 该不该存 | Precision / Recall / 错误归属率 |
| 检索质量 | 能不能检索出来 | Recall@K / MRR / NDCG |
| 一致性 | 记忆变乱没 | 重复率 / 冲突率 / 一致率 |
| 注入质量 | 组装合理不 | 无关注入率 / 成对胜率 |
| 治理质量 | 关联合理不 | 误合并率 / 错误隔离率 |

**关键**：五维独立，能定位「质量损失在哪个阶段」——Recall@K 低是检索问题，不是笼统"效果差"。基础是**黄金评测集**（≥200 query→记忆对 + ≥50 对话→记忆对）。

### 三层质量闭环（回答"怎么持续保证质量"）

```
① 离线评测（静态测试集）→ 定基线、调阈值
② 实时监控 + 熔断 → 发现异常、及时止血
③ 错误记忆实时处理 → 定位错误、自主修复
④ 反馈闭环 → 错误样本反哺评测集，越用越准
```

- **离线评测**：上线前知道"多好算好"。
- **实时监控 + 熔断**：运行时知道"哪里坏了"，坏了就关注入。
- **实时纠错**：用户指出错误 → 立即隔离 + 反哺评测集。

**根本边界**（最能体现认知深度）：记忆系统**无法 100% 自主判断内容对错**——"对不对"需要外部真相，而系统只有用户告诉它的东西。所以是「分层检测疑似 + 保守处理」，能确定的隔离、不确定的标待确认，**宁可不删、不可删错**。

## 附：面试高频追问速查

| 追问 | 一句话答案 |
|---|---|
| 相似但不同的记忆怎么区分？ | 三元组身份优先，余弦回退 |
| 双写一致性怎么做？ | MySQL 权威 + PENDING + CAS 补偿 |
| 为什么用 RRF 不用加权求和？ | 异构分数量纲不可比，排名融合天然无关 |
| 记忆有时间维度吗？ | 有限时间态（版本化），不做完整 bitemporal |
| 提示词注入怎么防？ | System/User 角色隔离 + 边界标注 |
| 熔断信号用什么？ | 可测信号（写失败率/积压/驳回率），不依赖不存在的纠错率 |
| 治理误判怎么办？ | 软标记 + undo 可回滚 |
| 记忆系统能自我修复吗？ | 能检测疑似+隔离，不能 100% 判内容对错，需用户确认 |
