# 记忆系统独立评测平台：整体架构讲解

> 本文是《记忆系统独立评测平台方案（v18 终稿）》的架构阅读版。
> 原始方案文件保持不变，仍是全部 ADR、DDL、契约、验收标准和修订历史的唯一权威来源：
> `docs/superpowers/specs/记忆系统独立评测平台方案.md`
>
> 本文只做结构化讲解和开发导航，不替代、不删减原始方案。

## 1. 平台定位

平台解决的问题不是单次离线打分，而是让记忆系统能够持续调优：

1. 连接真实 Java 记忆系统。
2. 管理可版本化的评测集和 ground truth。
3. 调整参数、模型和冻结模式。
4. 异步运行评测并支持 A/B 并行。
5. 观察抽取、检索、一致性、注入、治理五个维度。
6. 将错误样本复核后反哺为新数据集版本。

核心原则是：**部署独立、逻辑不独立**。平台单独部署 FastAPI、Celery、Postgres、Redis 和前端，但评测请求必须进入线上同源 Java 逻辑，避免复制业务实现后产生评测失真。

## 2. 设计边界

### 2.1 平台负责

- 用户、RBAC、审计。
- 测试集导入、版本化和标注。
- 参数快照、模型版本和配置指纹。
- run 编排、租约、心跳、重试、取消、reaper。
- 五维指标计算、结果 upsert、趋势和 A/B 展示。
- LLM-judge 异步任务。
- 反馈样本审核、归档和回归 diff。

### 2.2 Java 评测实例负责

- 使用现有记忆抽取、检索、注入和治理逻辑。
- 提供 `/api/v1/eval/**` 最小权限端点。
- 管理专用 eval MySQL database、Qdrant collection 和 eval 用户命名空间。
- 对 reset、seed 等破坏性操作执行 fencing 权威校验。

### 2.3 明确不做的事情

- 不复制一套 Java 记忆核心逻辑到 Python。
- 不把评测语料永久作为业务数据保存。
- 不使用 createdId 作为跨 reset 的评测身份。
- 不把 Postgres 中的 fencing 镜像当作破坏性写的决策依据。

## 3. 服务拓扑

```text
内网用户
  |
  v
React 前端 --> FastAPI API --> Postgres
                    |             |
                    v             v
                 Celery       Redis broker/result
                    |
                    v
          Java Memory Eval 实例
             |             |
             v             v
        专用 MySQL       专用 Qdrant
```

- platform 网络与 memory 网络隔离。
- 只有 FastAPI 和 Celery worker 可以访问 Java eval 实例。
- Flower 和管理端点仅内网开放并配置认证。
- Java eval 实例与业务实例使用同一套代码和迁移，只切换配置；业务 cron 在 eval profile 下禁用。

## 4. 一次 run 的生命周期

1. 用户提交 `dataset_version`、`param_snapshot_id`、模式和幂等键。
2. FastAPI 鉴权并计算 `config_fingerprint`。
3. 按配置指纹派生 `eval_user_id`。
4. 校验幂等键、同配置单飞、哈希碰撞和 exclusive guard。
5. 创建 `PENDING` run，投递 Celery 任务。
6. worker 用 CAS 抢占，进入 `RUNNING`，开始心跳。
7. 首次破坏性写前从 Java 读取权威 fencing 版本并 acquire。
8. 调用 reset 清理当前命名空间，再幂等 seed。
9. HNSW 模式等待向量同步；exact 模式跳过等待。
10. 执行五维评测并按 case 和维度 upsert 结果。
11. finalize 先清理自身命名空间，再 release fencing，最后 CAS 置成功。
12. 前端轮询 run 状态；后台 reaper 处理 stale worker。

## 5. 核心并发与隔离机制

### 5.1 per-config 命名空间

```text
eval_user_id =
  EVAL_USER_ID_BASE + hash(config_fingerprint[:8]) mod EVAL_USER_ID_RANGE
```

- 同一配置的多个 run 共享命名空间，但由唯一索引保证串行。
- finalize 先清空 MySQL 和 Qdrant，再释放 active 槽位。
- 不同配置使用不同命名空间，可以并行 A/B。
- 哈希碰撞由 `uq_runs_active_user` 降级为 409 串行，不允许互删。

这样解决两个问题：历史语料不会累积导致 FULLTEXT IDF 漂移；不同配置也不会在 reset 时误删彼此语料。

### 5.2 exclusive 可复现 run

exact 模式仍包含常驻 BM25 FULLTEXT 路径，因此全局 IDF 仍可能受其他配置语料影响。可复现 run 设置 `exclusive=true`：

- exclusive run 运行期间不允许其他 active run。
- 普通 A/B run 运行期间不允许创建 exclusive run。
- 使用单行 `eval_run_guard` 在事务内完成占位。
- finalize、reaper 和 stale 心跳三条路径都必须回收 guard。

### 5.3 fencing token

fencing 权威状态在 Java MySQL 的 `eval_fencing` 表中按 `eval_user_id` 键控，Postgres 只保留观测镜像。

- acquire 在同一事务内 `SELECT ... FOR UPDATE`，无行时建立 version=1，有行时对账后递增。
- lease 接管不直接递增 fencing；接管成功后再调用 Java acquire。
- reset、seed、finalize 清理都携带 `X-Eval-Fencing` 和 `X-Eval-Run-Id`。
- Java 在同一事务内锁定读取权威状态，校验 token 和 active run，失败返回 403。
- reaper 判死后调用 release 清空 `active_run_id`，后继 run 才能接管。
- token 刷新必须实时 GET Java 权威端点，不能读取陈旧镜像。

它闭合的是 zombie worker 在后继 run 已经接管后继续删除语料的 TOCTOU 风险。

### 5.4 状态、租约和恢复

| 场景 | 机制 |
|---|---|
| pending 抢占 | `status='pending'` CAS |
| running 接管 | owner + heartbeat CAS |
| worker 崩溃 | `acks_late`、拒绝 worker 丢失、checkpoint 续跑 |
| stale running | reaper revoke + CAS failed |
| stale pending | reaper 置 failed |
| 取消 | `CANCELLED` + 阶段间检查 + revoke |
| finalize 复活 | `status='running' AND lease_owner=:me` CAS |
| 阶段提前失败 | per-stage lease check，作为快速失败和观测层 |

## 6. 评测维度与数据流

### 6.1 五维指标

| 维度 | 主要通道 | 代表指标 | 结果性质 |
|---|---|---|---|
| 抽取 | `/eval/extract` | Precision、Recall、错误归属率、低价值写入率 | LLM 生成，带方差 |
| 检索 | `/eval/search` | Recall@K、MRR、NDCG@K、Hit@1 | exact 确定，HNSW 带方差 |
| 一致性 | 语料扫描、replay | 重复率、冲突率、MySQL/Qdrant 一致率、过期残留率 | 确定性 |
| 注入 | `/eval/retrieve-context`、judge | 无关注入率、token 超预算率、成对胜率、事实错误率 | 混合确定性与 judge |
| 治理 | `/eval/governance/replay` | 误合并率、错误隔离率、误归档率、撤销成功率 | Shadow Mode，只读 |

### 6.2 contentHash 评测身份

`content_hash` 是 exact content 的 UTF-8 字节 MD5，小写十六进制，不做规范化。Recall 直接以返回内容的 hash 和 ground truth 中的相关 hash 匹配，避免自增 ID 在 reset 后漂移。

### 6.3 冻结六要素

`freezeSideEffects=true` 时：

1. 跳过访问回写。
2. 旁路缓存。
3. 固定 recency epoch。
4. 旁路 reranker。
5. pin expire 墙钟。
6. `exact=true` 贯穿到 Qdrant。

冻结模式用于可复现；HNSW 模式用于观察真实线上近似检索行为。

## 7. 数据模型分层

### 7.1 评测资产

- `eval_datasets`：逻辑数据集。
- `eval_dataset_versions`：不可变版本。
- `eval_cases`：稳定自然键、content_hash、ground_truth。
- `eval_feedback_samples`：错误样本审核和归档。

### 7.2 配置资产

- `eval_param_snapshots`：参数和 freeze 配置快照，按 `params_hash` 去重。
- `eval_model_versions`：embedding、reranker 和抽取相关配置，按 `config_hash` 去重。
- `config_fingerprint`：参数、模型、数据集摘要和 mode 的组合指纹。

`content_digest` 必须把 ground truth 纳入 canonical JSON。ground truth 修正会使 digest 和 fingerprint 变化，从而让反哺归因可见。

### 7.3 执行和结果

- `eval_runs`：run 状态、租约、心跳、checkpoint、fencing 镜像、exclusive 标志。
- `eval_run_guard`：exclusive 全局互斥占位。
- `eval_run_results`：维度级指标，upsert。
- `eval_case_results`：case 级指标，upsert。
- `eval_judge_jobs`：位置交换后的成对 judge 任务。
- `eval_audit_log`：append-only 审计。

结果表使用 `ON CONFLICT` 幂等，且对 run 使用 `RESTRICT` 保留审计链。

## 8. Java eval 端点边界

| 端点 | 用途 |
|---|---|
| `/eval/seed` | 批量幂等写入，返回 inserted/existed |
| `/eval/reset` | 物理删除 MySQL 语料并同步删除向量 |
| `/eval/fencing/{eval_user_id}` | 读取 Java 权威 fencing |
| `/eval/fencing/acquire` | 事务内建立或递增 fencing |
| `/eval/fencing/release` | finalize/reaper 后清理 active run |
| `/eval/search` | 返回含 content 的检索结果 |
| `/eval/extract` | 返回 MemoryCandidate |
| `/eval/retrieve-context` | 返回 budgeted/formatted 注入上下文 |
| `/eval/governance-samples` | 导出治理样本 |
| `/eval/governance/replay` | 只读调用 compute 层 |
| `/eval/circuit-breaker` | 查询降级状态 |
| `/eval/metrics` | 查询抽取驳回和向量同步指标 |
| `/eval/params` | 读取参数单一真源 |

所有 Java eval 端点使用 `ROLE_EVAL`、内网访问和 eval 命名空间范围校验。

## 9. 跨模型可比性

指标按照依赖的模型维度分层：

- **绝对可比**：一致性、治理、无关注入率。只依赖内容、结构和确定性规则，趋势线可跨模型连续展示。
- **相对可比**：检索指标、抽取指标、judge 成对胜率和事实错误率。按 `config_hash` 分段；judge 指标使用 `config_hash + judge_model`。

这避免把模型升级、参数调优和数据集修正混在同一条趋势线上。

## 10. 安全、可靠性与观测

- platform 使用 JWT + bcrypt，两档角色为 admin/viewer。
- 所有 mutation 写审计；Java 端点最小权限。
- platform/memory 双网络隔离，凭据使用 secrets/env。
- Flower 仅内网 basic-auth。
- Postgres 使用 WAL、dump 和 basebackup。
- `eval_fencing` 虽然数据量小，但属于不可重建的权威态，必须纳入备份。
- 先用 Flower 和结构化 JSON 日志，后续再接 Prometheus/Grafana。
- 关键告警包括 run 卡死、空结果、可复现漂移、Java 连接异常、语料残留、judge 不一致和参数漂移。

## 13. 模块职责与接口方向

| 模块 | 核心职责 | 主要输入 | 主要输出 | 不应承担的职责 |
|---|---|---|---|---|
| `auth` | 登录、JWT、角色检查 | 用户名、密码、JWT | 当前用户和角色 | 不直接决定 run 是否可执行 |
| `datasets` | 三源导入、版本化、hash/digest | 文件、治理样本、人工标注 | immutable dataset version | 不修改历史版本 |
| `params` | 参数读取、快照、hash | Java 当前参数、用户修改 | params snapshot | 不直接改变历史 run 参数 |
| `connector` | Java HTTP 契约、重试、熔断 | eval endpoint request | typed response/error | 不在 Python 复制 Java 业务规则 |
| `tasks` | run 编排、租约、心跳、reaper | run_id、checkpoint | 状态变更和阶段结果 | 不计算指标细节 |
| `engine` | 五维指标和分层 | Java response、ground truth | metric values/detail | 不写 Java 业务存储 |
| `results` | 结果查询、聚合、趋势 | run/result tables | API DTO、图表数据 | 不重新执行评测 |
| `judge` | 成对比较、位置偏置消解 | A/B 输入、模型配置 | judge job/verdict | 不阻塞主 run |
| `feedback` | 样本审核、归档、回归 diff | case result、人工修订 | 新 dataset version | 不覆盖旧版本 |

接口边界的判断标准是：每个模块可以替换内部实现，但不能改变上游已固定的请求、响应、状态和幂等语义。

## 14. 关键时序说明

### 14.1 创建 run

```text
Client
  -> POST /runs
FastAPI
  -> 鉴权/RBAC
  -> 读取 dataset、params、model
  -> 计算 content_digest/config_fingerprint
  -> 检查 idempotency_key
  -> 派生 eval_user_id
  -> 锁定 eval_run_guard（exclusive 场景）
  -> 插入 eval_runs(pending)
  -> 投递 Celery task
Client <- 202(run_id)
```

创建阶段只负责确定“这次执行是什么”，不提前写入 Java 语料。配置指纹和参数快照一旦绑定 run，后续不能从当前线上参数重新推导覆盖。

### 14.2 worker 接管与 fencing

```text
Worker A -> CAS pending/running -> 成功
Worker A -> GET Java fencing version
Worker A -> POST acquire
Worker A -> 写回 Postgres fencing_version（仅观测镜像）
Worker A -> reset/seed（携带 token + run_id）

Worker A crash
Reaper   -> CAS failed + release(dead_run_id)
Worker B -> lease CAS 接管
Worker B -> GET 当前权威 version
Worker B -> acquire(version + 1)
Worker B -> reset/seed（旧 A token 已失效）
```

Postgres 镜像不参与破坏性写决策。任何需要刷新 token 的场景都实时读取 Java 权威值，避免缓存造成合法请求被错误拒绝。

### 14.3 finalize

finalize 不是简单的状态更新，而是一个有顺序要求的收尾协议：

1. 检查当前 worker 仍拥有 lease。
2. 复用带 fencing 守卫的 reset 清理 MySQL 和 Qdrant。
3. 清理成功或确认已清理后，调用 fencing release。
4. 使用 `status='running' AND lease_owner=:me` CAS 置 `succeeded`。
5. 同事务回收 exclusive guard。

如果在第 3 步之后崩溃，run 可能暂时保持 running，但不会重新拥有破坏性写权限；后续由心跳超时和 reaper 收敛。

## 15. 状态机与错误语义

### 15.1 run 状态

```text
PENDING -> RUNNING -> SUCCEEDED
    |         |
    |         +----> FAILED
    |         +----> CANCELLED
    +--------------> FAILED（pending stale）
```

- `PENDING` 只表示已经持久化但尚未被 worker 抢占。
- `RUNNING` 只有持有 lease 的 worker 可以推进阶段。
- `SUCCEEDED`、`FAILED`、`CANCELLED` 为终态，不能被普通重试重新打开。
- crash-resume 是接管同一个 run，不是创建一个新的 run。

### 15.2 错误分类

| 错误类型 | 示例 | 处理 |
|---|---|---|
| 客户端确定性错误 | schema 不合法、权限不足、fingerprint 冲突 | 4xx，不能自动重试 |
| 资源冲突 | active config、exclusive guard、哈希碰撞 | 409，按交互策略立即失败或退避 |
| Java 业务拒绝 | fencing 403、IDOR 403 | 终止当前阶段并告警，不盲目重试 |
| 短暂基础设施错误 | 超时、连接重置、Redis 暂时不可用 | 有上限的指数退避 |
| worker 故障 | 进程退出、容器被杀 | 依靠 ack/reaper/lease 接管 |
| 指标数据错误 | ground truth 缺失、响应字段不兼容 | run failed，保留错误上下文 |

重试必须区分“重新执行当前阶段”和“从 checkpoint 续跑”。reset、seed、结果 upsert 都要幂等，才能允许阶段重试。

## 16. 数据生命周期

```text
原始样本
  -> dataset version（不可变）
  -> run 绑定 dataset/params/model
  -> eval_user_id 命名空间临时 seed
  -> 五维结果和审计永久保留
  -> finalize 清理 MySQL/Qdrant 临时语料
  -> feedback 复核
  -> 新 dataset version
```

- Postgres 中的数据集、结果、反馈和审计是长期资产。
- MySQL eval 语料和 Qdrant 向量是可重建的短暂态。
- `eval_fencing` 是小体量但不可随意丢失的权威态。
- 历史 run 不依赖当前参数和当前模型重新计算其原始配置。

## 17. 参数、模型和模式的关系

一次 run 的有效配置至少由以下四部分组成：

```text
config_fingerprint =
  hash(params_hash | config_hash | content_digest | mode)
```

- `params_hash` 描述检索、注入、抽取阈值和 freeze 配置。
- `config_hash` 描述 embedding、reranker、抽取或其他模型配置。
- `content_digest` 描述评测集内容和 ground truth。
- `mode` 区分 exact 和 HNSW。

因此，任何会改变输入分布、模型空间、参数行为或检索模式的变化，都应产生新的可追溯指纹。

## 18. 可复现与真实性的使用建议

| 目标 | 推荐模式 | 主要控制项 | 结论口径 |
|---|---|---|---|
| 回归基线 | exact + exclusive | 冻结六要素、单配置独占 | 用于判断版本变化 |
| 参数 A/B | exact + per-config 并行 | 各自命名空间、相同数据集 | 对比相对变化 |
| 线上真实性 | HNSW | 等待向量同步、保留近似检索 | 观察实际服务行为 |
| 注入质量 | retrieve-context + judge | 固定 judge 版本并记录 | 解释“记忆是否有用” |

exact 并不意味着所有路径都变成确定性全扫描；BM25 仍然存在，所以需要 per-config 清理和 exclusive 机制共同保证 IDF 口径。

## 19. 评审时优先检查的十个不变量

1. 所有 Java eval 读写都带 `userId/eval_user_id` 维度。
2. reset 同时清 MySQL 和 Qdrant。
3. seed 重复调用不会产生重复语料。
4. Recall 使用 contentHash，不使用 createdId。
5. 同 config active run 不超过一个。
6. 不同 config 不共享破坏性命名空间，碰撞时只能串行。
7. fencing 权威态在 Java，旧 token 必须被拒绝。
8. finalize 必须先清理、再 release、最后释放 run 槽位。
9. exclusive guard 必须可回收。
10. ground truth 改动必须反映到 content_digest 和 fingerprint。

这些不变量比单个接口是否返回 200 更能判断方案是否真正落地。
