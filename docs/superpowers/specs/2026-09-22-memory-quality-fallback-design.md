# AgentWrite 记忆持续治理与兜底方案

> 状态：方案记录，暂不实施。
>
> 本文补充 [长期记忆系统全生命周期治理方案](2026-09-22-memory-lifecycle-governance-design.md)，聚焦记忆写入后的长期质量维护，不重复主链路改造。

## 1. 定位与边界

已有方案关注“一次记忆如何正确经过抽取、存储、检索、注入”。

本方案关注“记忆长期积累后，如何持续纠错、去重、复审、归档和跨会话演化”。

沿用已有方案的证据来源、版本记录、存储一致性和缓存失效能力，不重新设计以下内容：

- 候选文本与 Embedding 绑定、Qdrant upsert、双写补偿。
- 结构化抽取字段、混合召回、RRF 和 Reranker。
- 注入 Token 预算、任务类型选择和 Prompt 数据边界。

本文新增的是独立的持续治理层，其职责包括：

1. 错误抽取后的隔离与纠正。
2. 跨批次、跨会话重复记忆的整理。
3. 记忆过期、失效与休眠后的复审。
4. 跨会话碎片的关联和规范化。
5. 冲突、漂移及错误传播的止损。
6. 治理操作自身的误判恢复。

## 2. 总体架构

采用已经确认的“规则 + 低频 LLM”策略：

```text
记忆写入
  -> 写后轻量检测
  -> 正常 / 观察期 / 隔离
  -> 事件驱动增量治理 + 周期巡检
  -> 按用户、项目、主题批量复审
  -> 提升 / 合并 / 降级 / 归档 / 纠错建议
  -> 风险操作校验
  -> 治理结果应用
  -> 检索前状态兜底
```

- 写后轻检：使用规则发现明显异常，不在在线链路追加重型模型调用。
- 周期深治：按变化量和风险优先级批量调用 LLM，不反复全库扫描。
- 检索前兜底：读取已有治理状态，拦截不可用记忆，不现场执行深度整理。
- 风险操作：先隔离或生成建议，不让治理模型直接物理删除数据。

写后检测存在延迟，因此需观察或复审的记忆在写入时即标记为观察状态，不能等后台发现问题后才阻止注入。

## 3. 两层记忆模型

### 3.1 Observation：原始观察

表示“某次会话出现过某项信息”，并不等于已确认的长期事实。

保存来源消息、所属会话、主体、项目或任务范围、观察时间，以及与已有证据的来源关联。具体证据字段复用主方案。

### 3.2 Canonical Memory：规范记忆

表示“经过多条观察整理形成的稳定认知”。

- 一条规范记忆可关联多个会话的观察。
- 同一观察也可以支持多条不同属性的规范记忆。
- 原始观察作为证据保留，不能用归纳摘要替代全部原始事实。
- 规范记忆的范围必须明确，项目局部事实不能自动上升为用户全局属性。

例如，“用户使用 Java”“用户开发 AI Agent”“用户准备秋招”应形成相互关联的不同记忆，而不是强行合并成一个难以独立更新的大段摘要。

## 4. 抽取错误兜底

### 4.1 观察期与隔离区

```text
PROBATION（观察期）
  -> ACTIVE（证据充分）
  -> QUARANTINED（疑似错误，暂停使用）
```

- 用户明确、无歧义且范围清楚的陈述，可经规则校验直接进入有效状态。
- AI 推断、指代不明或临时要求默认进入观察期。
- 单轮抽取数量突增、类型分布异常时，触发批次复审。
- 用户明确否认后，相关记忆立即隔离，不等待周期任务。
- 观察期不设为所有记忆必须多次确认的硬门槛，避免一次性明确事实永远无法生效。

### 4.2 独立证据判定

多个会话重复出现可以增加支持度，但必须追踪证据来源：

- 同一消息的重放、转述和复制不算新的独立证据。
- AI 基于旧记忆生成的回答，不算对旧记忆的再次确认。
- 用户未反对、检索命中或访问频繁，不代表事实正确。
- LLM 自报置信度只作为复审信号，不直接视为事实概率。

### 4.3 错误传播止损

记录规范记忆和派生摘要的依赖关系。源记忆被否认或隔离时，将依赖它的摘要、聚合记忆加入复审队列，暂停未经复核的派生内容。

不因共享同一主题就批量否定其他独立证据支持的记忆。

## 5. 重复记忆兜底

### 5.1 跨批次整理

写入时去重无法覆盖所有历史记录，因此后台按用户、范围、类型和主题生成重复候选：

```text
“Java 是我的主要语言”
“我平时主要写 Java”
“用户主要使用 Java”
          -> 同一规范记忆 + 多条来源观察
```

### 5.2 合并规则

- 语义相似度用于发现候选，不作为自动合并的唯一依据。
- 检查主体、属性、否定关系、时间和项目范围。
- 区分同义重复、互补信息、时间变化及矛盾，只有同义重复直接归并。
- 限制聚类范围并检查组内一致性，避免 A 类似 B、B 类似 C 就误判 A 等价于 C。
- 合并后保留原 ID 到规范记忆的映射、证据关系和撤销记录。

检索侧只返回同一规范记忆一次。误合并时允许拆分并重新绑定来源，而不是依靠重新抽取恢复。

## 6. 过期、休眠与遗忘兜底

### 6.1 区分三个概念

- 不常用：表示近期价值较低，不代表事实错误。
- 待复核：表示真实性或适用性可能变化。
- 已失效：表示有明确截止时间或替代证据。

Redis 缓存 TTL、最近访问时间和记忆事实有效期是不同概念。被频繁访问不能自动延长事实有效期。

### 6.2 类型化策略

| 类型 | 兜底策略 |
| --- | --- |
| 稳定事实 | 不因久未访问自动判错，必要时进入待复核 |
| 工作、位置等易变事实 | 按变化频率安排复审，保留观察时间 |
| 用户偏好 | 缺少近期支持时降低默认使用强度，新证据可重新激活 |
| 技术知识 | 绑定版本与适用范围，版本变化时触发复审 |
| 历史事件 | 保留“曾经发生”的语义，不继续当作当前状态 |
| 临时状态 | 优先使用用户明确的截止时间，到期退出当前上下文 |

复审周期由类型和运行数据确定，不给所有记忆统一设置固定天数。

### 6.3 状态语义

| 状态 | 含义 |
| --- | --- |
| PROBATION | 尚待确认 |
| ACTIVE | 当前可用 |
| DORMANT | 低频使用，默认不优先召回，但不表示错误 |
| STALE | 需要复核，不能作为当前确定事实 |
| ARCHIVED | 退出日常使用，按保留策略保存 |
| QUARANTINED | 疑似错误或异常，暂停使用 |
| DISPUTED | 存在尚未解决的冲突 |
| SUPERSEDED | 已被明确的新事实替代 |

这些状态不是必须依次经过的线性阶段。例如，ACTIVE 可直接转为 DISPUTED，DORMANT 经新证据确认可回到 ACTIVE。

归档不等于永久保留。用户明确要求删除或遗忘时，走独立的删除流程，处理原始观察、派生记忆、索引和缓存；不能用“可回滚”作为保留已要求删除内容的理由。

## 7. 跨会话碎片化治理

### 7.1 周期性整理

1. 收集最近发生变化的用户观察，而非每次全量重读历史。
2. 按主体、项目、主题、时间与类型分组。
3. 建立别名和指代关联，不以 sessionId 作为认知边界。
4. 合并同义信息，关联互补信息，保留不同时间和范围的差异。
5. 为规范记忆挂载多个来源，保留能支持每一条结论的证据。

### 7.2 防止错误跨会话泛化

```text
项目 A 使用 Java 8
项目 B 使用 Java 17
```

以上不是冲突，也不应合并成“用户只使用 Java 17”。

“这个项目”“上次那篇文章”等指代无法唯一解析时，保留为待关联观察，不能由模型猜测后写入全局画像。

“以前用 Java 8，现在升级到 Java 17”则可在同一项目范围内形成时间演化关系。

## 8. 冲突与漂移兜底

本节不重复主方案的单次 UPDATE 决策，而是处理长期积累后才发现的冲突。

| 情况 | 后台治理动作 |
| --- | --- |
| 用户明确纠正 | 隔离错误主张，标记被替代关系 |
| 状态随时间变化 | 保留时间边界，不删除历史事实 |
| 项目范围不同 | 拆分适用范围，不当作互斥 |
| 临时任务要求不同 | 保持局部作用域，不修改长期偏好 |
| 多条证据仍无法消解 | 标记 DISPUTED，必要时向用户确认 |

- 新陈述不总是覆盖旧陈述，应先判断是否同主体、同范围、同时间语义。
- 只在当前任务确实依赖该冲突事实时询问用户，避免频繁打断。
- 对反复被改写的属性设置复审冷却与告警，防止后台任务来回覆盖。
- 纠正记录参与后续治理，防止旧会话重放后重新产生已被否认的事实。

## 9. 检索前治理兜底

这里不修改召回、融合、精排算法，只消费治理结果：

- 隔离和争议记忆不得进入正常注入。
- 待复核记忆不得被当作当前确定事实。
- 历史查询可以使用带时间限定的已替代记录，不能简单过滤所有历史版本。
- 同一规范记忆去重返回。
- 同一属性存在未决互斥主张时，暂停相关主张的确定性注入，而非丢弃全部无关记忆。
- 高风险且缺少明确来源的主张，要求额外独立支持或用户确认。

无法完成治理校验时，受影响候选默认不注入，不延长在线请求等待深度治理。

## 10. 记忆健康度

将“是否值得使用”和“是否值得相信”分开：

- `importance`：业务价值与使用优先级。
- `healthScore`：证据质量与治理风险的汇总信号。

健康度可参考：

```text
证据可靠性 + 独立支持度 + 时间适用性 + 一致性 + 用户确认
  - 未决冲突 - 明确否认 - 异常抽取风险
```

以上是特征定义，不是已校准的计算公式。权重与阈值需通过样本确定。

硬性状态优先于分数：明确否认、已过期或被隔离的内容，不能因访问次数高或其他正向分数而重新放行。

## 11. 治理任务自身的兜底

### 11.1 幂等与并发

- 每次治理记录输入记忆版本、证据集合和治理策略版本。
- 同一用户或主题的冲突操作使用锁或租约串行化。
- 应用结果前再次校验版本，过时的治理建议作废并重新计算。
- 用户纠正优先于后台旧任务，不能被巡检结果覆盖。

### 11.2 可恢复操作

- 合并、拆分、隔离、激活、归档均记录原因和影响对象。
- 初期使用 Shadow Mode，只生成建议，不改变实际检索结果。
- 确定性规则可逐步自动执行；语义合并等高风险操作先建议、再校验。
- 保存操作批次和撤销信息，支持恢复误归档、误隔离和误合并。
- LLM 复审失败保持待处理状态，不能将调用失败解释为记忆错误。

### 11.3 成本控制

- 按新增量、冲突数、纠错反馈和证据变化触发增量治理。
- 设置用户级、全局调用预算及每批候选数量上限。
- 优先处理正在被使用且存在风险的记忆，同时轮转检查冷数据。
- 输入和策略均未变化时不重复调用模型。
- 记录队列积压与最久未治理时间，避免有限预算下冷数据永久遗漏。

## 12. 专项验收

与原方案的通用质量评测不同，本方案重点验证长期治理的副作用与恢复能力：

1. 跨会话复制同一信息不会被误算为多份独立证据。
2. 用户否认后，相关记忆及依赖它的摘要及时停止使用。
3. 两个项目的相似属性不会被错误合并。
4. 同义重复合并后可撤销，证据仍可追溯。
5. 常被访问的过期事实不会自动恢复为有效事实。
6. 历史事件不会因低访问量被误认为错误。
7. 后台旧任务不会覆盖刚发生的用户纠正。
8. 治理模型失败、预算耗尽时不误删或误激活记忆。
9. 用户要求遗忘后，不会因历史会话重放而重新恢复被删除内容。

专项指标包括误合并率、错误隔离率、纠错生效延迟、过期发现延迟、跨会话关联准确率、错误派生内容残留率、治理撤销成功率及每用户治理成本。上线门槛通过 Shadow Mode 标注样本确定，不预设未经验证的准确率承诺。

## 13. 后续顺序

本轮只保存方案，以下是后续建议顺序，不代表已经获准实施：

1. 在主方案证据与版本能力基础上建立 Observation 与 Canonical Memory 关系。
2. 增加观察期、隔离区、用户纠正及派生影响追踪。
3. 以 Shadow Mode 验证跨会话重复聚类、碎片关联和误合并恢复。
4. 引入类型化复审、休眠与归档。
5. 增加长期冲突与漂移巡检。
6. 根据专项验收结果逐步开放规则自动治理和低频 LLM 辅助治理。

## 14. 总结

主方案保证记忆主链路正确；本方案保证记忆长期运行后仍然可信。

核心原则是：保留可追溯证据、独立证据才增信、不同范围不混合、常用不等于正确、风险操作先隔离、治理误判可恢复。
