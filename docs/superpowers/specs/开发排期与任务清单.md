| 阶段 | 目标 | 人天 | 里程碑（可独立交付） |

## 二、开发顺序（依赖驱动）

```
P0 正确性修复 + trace_id 埋点 + 基础指标
        │  (EmbeddedMemoryCandidate + 自增ID 就绪)
        ▼
P1 结构化抽取/存储/版本化 + Outbox 向量同步
        │  (subject/predicate/value/status 字段就绪)
        ▼
P2 RRF 检索 + 回表过滤 + 任务化注入 + 缓存失效
        │  (注入链路 + 缓存失效就绪)
        ▼
P3 观测闭环 / 错误分级 / 熔断
```

**关键依赖链（不可跳）**：
1. `trace_id` 埋点随 P0 落地 → P1 结构化落库时 `trace_id` 列才就绪。
2. P1 身份化 UPDATE 依赖 P0-1 的 `EmbeddedMemoryCandidate` 与 P0-4 自增 ID（版本化需稳定主键）。
3. P2 的过滤/任务化选择依赖 P1 的 `status`/`subject/predicate` 字段。
4. P3 熔断的降级动作是「关注入」，依赖 P2 注入链路。

## 三、任务清单

### P0：正确性修复（约 6 人天）

- [ ] **P0-1 embedding 下标错位修复**（1.5 天）
  - 新增 `EmbeddedMemoryCandidate`（候选 + hash + 向量绑定）；**先去重再 embed**；重写 Phase 3/5/7
  - 补「embedBatch 保序」契约测试
  - 涉及：`MemoryManager`、`EmbeddedMemoryCandidate`(新)、`MemoryManagerTest`
  - 验收：Hash 去重发生在候选中间时文本与向量仍一致

- [ ] **P0-2 Qdrant update→upsert**（0.5 天）
  - `IMemoryVectorStore` 接口统一为 `upsert`；`QdrantVectorStore` + `SimpleMemoryVectorStore` 都改；替换调用点
  - 涉及：`IMemoryVectorStore`、`QdrantVectorStore`、`SimpleMemoryVectorStore`、`MemoryManager`
  - 验收：UPDATE 后 MySQL + Qdrant 都能检索新版本

- [ ] **P0-3 吞异常修复**（0.5 天）
  - 新增 `MemoryVectorStoreException`；写路径失败上抛；`catch` 标 `PENDING` 不标 SYNCED
  - 涉及：`QdrantVectorStore`、`MemoryManager`
  - 验收：Qdrant 写失败时记录保持 PENDING

- [ ] **P0-4 nextId→自增**（0.5 天）
  - `useGeneratedKeys`；`insert` 返回 `Long` 回填；清点 `addDirect` 调用点；`uk_user_hash` 兜底
  - 涉及：`IMemoryRecordDao`、`IMemoryRepository`、`MemoryRepository`、`MemoryManager`
  - 验收：并发写入无主键冲突

- [ ] **P0-5 retry_count 状态机**（1 天）
  - `retryCount`/`vectorStatus` 字段**前移 P0**；重写 `syncPendingVectors` 用 `retry_count` 判上限
  - 涉及：`MemoryRecordEntity`、`MemoryRecordPO`、`MemoryRepository`、`MemoryManager`
  - 验收：补偿任务用 `retry_count` 判上限，达上限标 FAILED

- [ ] **P0-6 IDOR/安全**（0.5 天）
  - `detail`/`delete` 加 userId 归属校验；新增 `MemoryAccessDeniedException`；`migrate/all` 鉴权收紧
  - 涉及：`MemoryController`、`SecurityConfig`、`MemoryManager`
  - 验收：越权访问全部拒绝

- [ ] **P0-7 trace_id 埋点**（1 天）
  - `MemoryTraceId` **显式参数透传 + MDC**（不用 ThreadLocal）；结构化日志字段
  - 涉及：`MemoryTraceId`(新)、`MemoryManager`、`MemoryRetriever`
  - 验收：trace_id 在抽取/存储日志中可见

- [ ] **P0-8 基础指标**（0.5 天）
  - `MemoryMetrics` 只上 4 个核心指标（qdrant.failures / vector.sync.pending / extraction.accepted/rejected / retrieval.duration）
  - 涉及：`MemoryMetrics`(新)
  - 验收：4 指标可观测

**P0 内部顺序**：P0-1 → P0-4 → P0-2/P0-3（可合并）→ P0-5 → P0-6（可插队）→ P0-7/P0-8。

### P1：结构化抽取与存储（约 8～9 人天）

  - 加 `operation/targetMemoryId/subject/predicate/value/evidence/confidence`，保留旧构造兼容
  - 涉及：`MemoryCandidate`

- [ ] **P1-2 抽取 Prompt 改造**（1 天）

- [ ] **P1-3 模型 + DDL 扩展**（1.5 天）
  - Entity/PO 加新列；DDL 加列；`MemoryStatus` 权威枚举 + **status×查询路径可检索性矩阵**；SELECT 列补全
  - 涉及：`MemoryRecordEntity`、`MemoryRecordPO`、DDL、`MemoryStatus`(新)、`IMemoryRecordDao`

- [ ] **P1-4 版本化更新 + 向量同步**（3 天，分水岭）

## 六、面试讲解角度（怎么讲「排期拆解」）

> "我按**依赖驱动**拆，不是按功能平铺。先排正确性 P0（数据一致性 bug 必须先止血），再排结构化 P1（依赖 P0 的主键和绑定对象），再排检索 P2（依赖 P1 的字段），最后排观测 P3（先埋点后调阈值）。每个阶段结束是可发布里程碑。总量 26~30 人天，最重的是 P1 版本化存储，单独留 3 天并拆两个子步降风险。"

这段话同时展示：**工程判断**（依赖驱动）、**风险意识**（先止血、分水岭留足时间）、**可交付思维**（里程碑切分）。

## 七、并行开发拆分

> 核心判断：能不能并行，取决于「会不会碰同一个文件」。串行主干在热点文件里，能并行的活几乎都是「建新文件」。

### 7.1 冲突热点（决定并行边界）

| 文件 | 被多少任务触碰 | 结论 |
|---|---|---|
| `MemoryManager.java` | 13 个（P0-1~P0-7、P1-4~P1-6、P2-5、P2-7、P3-4） | 🔴 串行主干 |
| `MemoryRetriever.java` | 7 个（P0-7、P2-2~P2-7） | 🔴 检索线串行 |
| `IMemoryRecordDao` / `MemoryRecordPO` | 4 个 | 🟡 存储线串行 |
| `QdrantVectorStore` | 3 个 | 🟡 短链 |
| `MemoryController` / `SecurityConfig` | 1 个（P0-6） | 🟢 完全独立 |
| 新增文件（`MemoryTraceId`/`MemoryMetrics`/`MemoryAccessService`/`MemoryVectorSyncJob`/`MemoryGovernanceJob`/`MemoryCircuitBreaker`/`MemoryStatus`/`EmbeddedMemoryCandidate`） | 各自独立 | 🟢 真正的并行单元 |

### 7.2 串行主干（Critical Path，约 12～15 天，不能并行）

```
P0-1（1.5d）→ P0-4（0.5d）→ P0-2/P0-3（1d）→ P0-5（1d）
  → P1-1（0.5d）→ P1-2（1d）→ P1-3（1.5d）→ P1-4（3d）
  → P1-5/P1-6（1d）
  → P2-1（0.5d）→ P2-2（1d）→ P2-3（0.5d）→ P2-5（0.5d）→ P2-7（1.5d）
```

### 7.3 可并行开发的 4 条独立工作流

| 工作流 | 任务 | 人天 | 为何独立 | 协调点 |
|---|---|---|---|---|
| **A 安全与外围** | P0-6 | 0.5 | 只碰 Controller/SecurityConfig | `MemoryManager.delete()` 方法签名与主干约定 |
| **B 可观测埋点** | P0-7、P0-8、P3-1、P3-2 | ~4 | 新文件 `MemoryTraceId`/`MemoryMetrics` | 往热点文件插 hook 延迟到主干稳定后批量插 |
| **C 检索独立项** | P2-4、P2-6 | 1 | `RerankerClient` + 新文件 `MemoryAccessService` | 不碰 RRF 融合逻辑 |
| **D 治理/熔断骨架** | P3-3、P3-4、P3-5 | ~6 | 新文件 `MemoryGovernanceJob`/`MemoryCircuitBreaker` + 撤销 DDL | 骨架先建，依赖 P1 的 `status` 字段后填逻辑 |

- 流 A 可从第一天与 P0-1 同时启动。
- 流 C 可在 P1 进行中并行做掉。
- 流 D 骨架可提前写，逻辑等 P1 字段就绪。

### 7.4 分人 / 分 agent 方案

**方案 A：双轨（写路径 vs 读路径）**——适合 2 个 agent/2 人：

| 轨道 | 负责 | 冲突约定 |
|---|---|---|
| 轨道 1「写路径」 | P0-1~P0-5 + P1-1~P1-6 | 独占 `MemoryManager.add()` 相关方法 |
| 轨道 2「读路径 + 外围」 | P0-6 + P2-1~P2-7 + P3-1~P3-4 | 独占 `search()/retrieveContext()` + `MemoryRetriever` |

**方案 B：三轨（核心 / 外围 / 观测）**——适合 3 个 agent：

| 轨道 | 负责 | 备注 |
|---|---|---|
| 轨道 1 核心 | 串行主干 | 单人顺序，14 天 |
| 轨道 2 外围 | P0-6 + P2-4/P2-6 | 最早启动，1.5 天 |
| 轨道 3 观测 | P0-7/P0-8 + P3-1~P3-4 | 全是新文件，4+ 天 |

### 7.5 并行协调规则（避免 merge conflict）

1. **按方法划分热点文件**：`MemoryManager` 的 `add()` 归写路径、`search()/retrieveContext()` 归读路径。
2. **新文件是天然的并行单元**：谁建的新类谁负责，不交叉改。
3. **hook 插入后置**：埋点、指标计数这类「往别人文件插一行」的活，攒到主干稳定后一次性批量插。
4. **DDL 统一由主干 owner 管理**：`memory_record` 加列、索引，只有一个人写。

### 7.6 时间账

| 模式 | 总周期 |
|---|---|
| 单人串行 | 26～30 天 |
| 双轨并行 | 约 15～18 天 |
| 三轨并行 | 约 15 天（仍是主干主导） |

> 主干（`MemoryManager` 写路径 + 版本化存储）是硬下限，怎么并行都压不过它。最划算：主线单人慢慢推，把安全/埋点/治理骨架这些「新文件活」丢给并行 agent 提前做掉。
