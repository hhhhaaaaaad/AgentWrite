# 记忆系统独立评测平台：独立平台项目工作

> 本文从《记忆系统独立评测平台方案（v18 终稿）》中拆出“新的独立评测平台项目需要完成的工作”。
> 它覆盖 FastAPI、Celery、Postgres、Redis、React、LLM-judge、反馈闭环、部署和验收。
> 当前 AgentWrite 项目内的 Java 改造见：
> `docs/superpowers/specs/记忆系统独立评测平台-AgentWrite项目改造工作.md`

## 1. 项目定位

独立评测平台是 AgentWrite 记忆系统之外的一套工具系统。它不实现记忆抽取、检索、治理本身，而是负责编排、记录、比较和反哺。

核心职责：

1. 管理用户、权限和审计。
2. 管理评测集、版本、case 和 ground truth。
3. 管理参数快照、模型版本和配置指纹。
4. 创建、调度、恢复和取消评测 run。
5. 调用 AgentWrite Java eval 端点。
6. 计算五维指标并持久化。
7. 展示雷达图、趋势图、A/B 对比和 case 明细。
8. 运行 LLM-judge 并消解位置偏置。
9. 将错误样本审核后归档为新评测集版本。
10. 提供部署、备份、观测和验收工具。

## 9. 独立平台风险重点

| 风险 | 表现 | 处理 |
|---|---|---|
| 契约漂移 | Java 字段变化导致解析失败 | connector 契约测试前置 |
| run 状态复杂 | 双 worker、reaper、cancel 相互覆盖 | 所有状态更新必须 CAS |
| 指标口径不稳定 | 数据集、模型、参数混线 | 强制 fingerprint 和可比分层 |
| 前端过早开发 | 后端 schema 变化导致重做 | 先做 API DTO 和 mock，再做页面 |
| judge 成本失控 | 每个 case 全量 judge | 抽样、异步、可配置预算 |
| 反馈污染历史 | 直接改旧 dataset version | 历史版本不可变，只生成新版本 |

独立平台最大的工程风险不是某个指标公式，而是 run 编排和结果身份。如果这两块不稳，后续图表和反馈都会建立在不可信数据上。

## 10. 平台 API 分层

独立平台 API 建议按照“资产、执行、结果、治理”四组组织，而不是按照数据库表逐个暴露：

| API 分组 | 代表接口 | 责任 |
|---|---|---|
| 资产 API | `/datasets`、`/dataset-versions`、`/params`、`/models` | 管理不可变评测资产 |
| 执行 API | `/experiments`、`/runs`、`/runs/{id}/cancel` | 创建和控制评测执行 |
| 结果 API | `/runs/{id}/results`、`/trends`、`/comparisons` | 聚合结果和对比 |
| 反馈 API | `/feedback`、`/feedback/{id}/review`、`/regressions` | 复核样本和回归 |
| 运维 API | `/health`、`/ready`、`/metrics` | 服务健康与观测 |

API 层只负责鉴权、参数校验和事务边界；run 具体执行必须进入 Celery，不允许在 FastAPI 请求线程内同步跑完整评测。

## 11. Run 阶段模型

建议将一次 run 固定为以下阶段，每个阶段都写入 `current_stage` 和 checkpoint：

```text
claim
  -> fencing_acquire
  -> reset
  -> seed
  -> vector_ready（仅 HNSW）
  -> extraction
  -> retrieval
  -> consistency
  -> injection
  -> governance
  -> finalize_cleanup
  -> release
  -> succeeded
```

阶段执行规则：

- 每个阶段开始前检查 lease 和取消标记。
- 阶段成功后立即更新 checkpoint，避免从头重跑。
- reset、seed、结果 upsert 和 finalize cleanup 必须幂等。
- `fencing_acquire` 失败不能继续执行 reset/seed。
- `vector_ready` 超时应让 run 明确失败，不以“可能已同步”继续。
- judge 不阻塞主 run，可在 finalize 后创建补充任务。

## 12. 平台数据库不变量

以下约束必须由数据库索引、事务或代码共同保证：

1. 一个 `idempotency_key` 只能对应一个请求身份。
2. 同一个 `config_fingerprint` 同时最多一个 active run。
3. 同一个 `eval_user_id` 同时最多一个 active run。
4. exclusive run 与普通 active run 不能违反互斥规则。
5. run result 的 `(run_id, dimension, metric_name)` 唯一。
6. case result 的 `(run_id, case_id, dimension)` 唯一。
7. dataset version 不可原地修改。
8. ground truth 修改必须生成新的 `content_digest`。
9. 终态 run 不被普通 worker 改回 running。
10. 历史结果不能因为 feedback 归档而被删除。

这些不变量不能只放在 Python if 判断里；涉及并发和唯一性的部分必须下沉为 Postgres 约束或事务锁。

## 13. Connector 错误分类和重试矩阵

| Java 返回/异常 | 平台分类 | 是否重试 | 处理 |
|---|---|---:|---|
| 400/422 | 请求或数据错误 | 否 | run failed，保存响应摘要 |
| 401/403 | 鉴权、IDOR、fencing | 否 | 告警并终止当前破坏性阶段 |
| 409 | 并发冲突或 fencing conflict | 仅按场景 | 读取权威状态后有限重试 |
| 429 | 限流 | 是 | 指数退避，达到上限后失败 |
| 500 | Java 内部错误 | 有上限 | 记录 endpoint 和 request_id |
| timeout/connection reset | 基础设施瞬态 | 有上限 | 熔断并等待后续恢复 |
| 返回结构不兼容 | 契约错误 | 否 | 立即失败，禁止猜测字段 |

重试策略必须带上 `run_id`、阶段名和 attempt 次数；禁止对所有异常统一 retry。

## 14. 结果模型的解释性要求

每条维度级结果至少要能回答：

- 使用了哪个 `dataset_version`？
- 使用了哪个 `params_snapshot` 和 `model_version`？
- 是 exact 还是 HNSW？
- 使用了哪个 `config_fingerprint`？
- 指标由多少 case 计算？
- 是否有方差、置信度或抽样？
- 是否依赖 judge，judge_model 是什么？
- 失败 case 或样本明细在哪里？

建议把这些信息放在 result detail 或 run snapshot 中，而不是只依赖当前表连接临时推断。历史 run 必须可脱离当前默认配置解释。

## 15. 指标实现顺序

为了尽快形成可信闭环，指标实现建议分三批：

### 第一批：确定性检索指标

- contentHash 匹配。
- Recall@5/10。
- MRR。
- NDCG@5。
- Hit@1。

先用 exact 模式验证数据流、seed/reset、结果 upsert 和 case identity。

### 第二批：确定性一致性与治理指标

- 重复、冲突、过期残留。
- MySQL/Qdrant 对账。
- 治理 replay 的误合并、隔离和归档指标。

这些指标适合先建立基线，不依赖 judge。

### 第三批：生成式和 judge 指标

- 抽取 Precision/Recall 和方差。
- 无关注入率、token 预算。
- 成对胜率、事实错误率。

LLM 指标必须保存原始响应摘要、模型版本和抽样信息，不能只保存一个最终浮点数。

## 16. 测试策略

### 16.1 后端单元测试

- canonical_json、content_hash、content_digest。
- fingerprint 和 eval_user_id 派生。
- 所有五维指标的边界样例。
- 状态机合法/非法迁移。
- 重试分类和错误映射。
- 结果 upsert。

### 16.2 数据库集成测试

- Alembic 从空库创建。
- partial unique index 并发冲突。
- guard 行锁和回收。
- 终态 run 防覆盖。
- feedback 生成新 dataset version。

### 16.3 worker 故障测试

- worker 在 reset 后、seed 中、指标中、finalize 前退出。
- reaper 判死后旧 worker 晚到。
- 两个 worker 同时接管 stale run。
- Redis/Java 短时不可用。
- fencing 权威版本与 Postgres 镜像暂时不一致。

### 16.4 前端验收

- viewer/admin 权限差异。
- run 创建冲突提示。
- 进度和失败原因展示。
- 趋势分段和口径标识。
- case 详情到反馈入口的跳转。

## 17. 配置与环境管理

建议至少区分 `local`、`staging`、`production` 三套配置：

| 配置项 | local | staging | production |
|---|---|---|---|
| Java eval base URL | 本地容器 | 内网 staging | 内网生产 |
| Postgres | compose volume | 独立实例 | 托管/高可用 |
| Redis | compose | 独立实例 | 托管/高可用 |
| Celery 并发 | 1 | 2-4 | 按 run 压测 |
| judge | mock/低成本模型 | 抽样模型 | 配置化正式模型 |
| 告警 | 日志 | 低阈值观测 | 按基线启用 |

任何环境都不能把真实业务数据库配置给 eval connector。生产环境 secrets 不应提交仓库。

## 18. 发布和迁移顺序

1. 创建 Postgres schema 和索引。
2. 部署平台 API，但暂不开放 run 创建。
3. 联调 Java connector 的 health、params、fencing GET。
4. 开放 dataset 和 params 管理。
5. 使用小数据集创建单一 exact run。
6. 验证 reset/seed/finalize 清理。
7. 开启指标引擎和结果查询。
8. 再开启并行 A/B、HNSW、judge 和反馈闭环。
9. 最后启用告警阈值。

每一步都应可单独回滚。不要在第一次部署时同时开启并行 worker、HNSW、judge 和自动反馈归档。

## 19. 独立平台工作包完成定义

平台达到第一版生产可用的必要条件：

- EP-0 至 EP-15 有交付物和测试证据。
- 单一 exact run 能完整走通 reset、seed、指标、finalize 清理。
- 同 config、同 user、exclusive、hash collision 的并发约束通过。
- worker crash、reaper、fencing、取消和重试语义通过。
- 五维指标可追溯到 case 和配置快照。
- 趋势图正确区分绝对可比和相对可比。
- judge 位置偏置不一致时不会自动采信。
- feedback 不修改历史 dataset version。
- 备份恢复和 runbook 至少演练一次。
- 24 条 Acceptance Criteria 均有测试或人工证据。

未达到这些条件时，平台可以作为实验工具使用，但不应把结果当作长期模型调优基线。
