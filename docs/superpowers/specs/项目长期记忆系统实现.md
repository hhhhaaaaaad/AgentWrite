长期记忆系统主要分为两条链路：

- **写入链路**：上下文收集 → 召回已有记忆 → LLM 抽取 → Embedding → MD5 精确去重 → 向量相似度 `> 0.9` 转 UPDATE → MySQL/Qdrant 持久化。
- **检索链路**：查询标准化 → Qdrant 语义召回 + MySQL FULLTEXT → 画像记忆注入 → 时间/重要性融合 → Reranker 精排 → TopK 注入 Prompt。
- **三级去重**：LLM 语义去重、MD5 精确去重、向量近似记忆更新。
- **可靠性设计**：向量写入失败标记 `PENDING`，定时任务补偿同步。
- **缓存设计**：Redis 搜索缓存和高重要性画像缓存。
- **业务入口**：普通 Agent 对话、写作对话以及 `AiWritingService` 写作任务均会检索注入，并在执行完成后异步抽取记忆。


**第一阶段：记忆抽取**

1. **用户记忆与 AI 输出混合污染**

调用方同时传入用户消息和 AI 回答，Prompt 还明确允许抽取 `attributed_to=agent`，但该字段解析后没有持久化。

```text
AI 推测用户偏好 → 存成记忆 → 下次注入 → AI 更确信该偏好
```

2. **没有“记忆身份”，只能靠相似度猜测 ADD 还是 UPDATE**

当前记忆只有自然语言文本和四种宽泛类型，没有类似：

```text

predicate=preferred_language

```

因此系统无法判断：

- “用户使用 Java”与“用户偏好 Java”是两条记忆还是一条。
- “用户目前在北京”与“用户曾去北京旅游”是否冲突。
- “偏好简洁表达”与“这次要求简洁表达”哪个是长期偏好。

现有逻辑只要余弦相似度 `> 0.9` 就覆盖旧记忆，容易错误合并不同事实。

3. **冲突处理只存在于 Prompt，没有确定性机制**

Prompt 声明“新记忆与旧记忆冲突时以新记忆为准”，但 LLM 输出没有 `operation`、`targetMemoryId` 或冲突关系。后续只能再次通过向量相似度寻找更新目标。

也就是说，LLM 即使识别出冲突，也没有结构化方式告诉存储层应该更新哪一条。

4. **已有记忆召回不足，导致 LLM 去重视野不完整**

抽取前只取向量 Top10；只有 Embedding 完全不可用时才使用 FULLTEXT。它不是混合召回。

- 它来自用户哪句话？

目前抽取链路解决了“从文本中生成候选记忆”，但尚未可靠解决四个关键问题：

```text

冲突：它与哪条旧记忆是什么关系？
证据：为什么相信并长期保存它？
```

```text

├── type
├── subject
├── predicate
├── value
├── operation: ADD / UPDATE / DELETE / NOOP
├── targetMemoryId
├── attributedTo
├── evidence
├── confidence
└── sensitivity
```

**Assistant**

当前记忆系统主要有以下问题：

**1. 记忆抽取**
- 用户事实与 AI 生成内容可能混存。
- 缺少置信度、证据来源和敏感信息过滤。
- 仅靠 LLM 判断长期价值，容易产生错误记忆。
- 冲突记忆没有明确的新增、更新、删除语义。

**2. 记忆存储**
- Hash 去重后，记忆与 Embedding 下标可能错位。
- 相似度 `> 0.9` 就覆盖，可能误合并不同记忆。
- Qdrant 更新会删除向量但不重新写入。
- Qdrant 写入失败仍可能标记为 `SYNCED`。
- MySQL 与 Qdrant 双写缺少可靠一致性保障。
- `MAX(id)+1` 生成主键存在并发冲突。

**3. 记忆检索**
- 画像记忆可能无视当前问题直接参与注入。
- Qdrant 结果缺少重要性和访问时间，融合评分部分失效。
- BM25、向量、重要性、时间权重缺少评测依据。
- 精排固定 Top5，可能违背调用方的 `topK`。
- Redis 缓存没有有效失效机制，容易返回旧记忆。
- 中文 FULLTEXT 查询质量不稳定。

**4. 记忆注入**
- 最终只注入纯文本，丢失类型、来源、置信度和时间。
- 没有 Token 预算、冲突处理和多样性控制。
- 不区分事实、偏好、知识和事件的注入策略。
- 缺少“注入后是否改善回答”的效果评测。

**核心总结：**当前实现更接近“文本抽取 + 向量召回”，还没有形成具备**可信来源、结构化身份、冲突演化、一致存储和效果反馈**的完整长期记忆系统。

- 保留来源消息、置信度、模型版本和有效状态。
- 记忆更新采用版本化，历史记录不可覆盖。
- MySQL 完成事务后，通过 Outbox 异步同步 Qdrant。
- 数据库唯一约束作为并发去重兜底。

**P1：优化检索链路**

推荐流水线：

```text
查询标准化
→ 向量召回 + BM25 召回
→ RRF 融合
→ 加载 MySQL 完整元数据
→ 类型/时间/置信度过滤
→ Reranker 精排
→ TopK
```

关键调整：

- 画像记忆不再无条件注入，而是参与相关性过滤。
- Qdrant 只负责召回，MySQL 提供权威元数据。
- 精排数量根据 `topK` 动态计算。
- 使用用户级记忆版本号处理缓存失效。
- 通过评测结果确定阈值和权重，避免手工拍值。

**P2：优化注入策略**

- 按事实、偏好、知识、事件分组注入。
- 增加 Token 预算、相关性阈值和重复内容压缩。
- 冲突记忆只注入当前有效版本。
- 标明记忆是“不可信上下文数据”，防止其中的指令影响 Agent。
- 不同任务使用不同记忆类型，例如润色偏重写作偏好，技术写作偏重知识和历史事实。

**P2：建立评测闭环**

重点指标：

- 抽取：准确率、召回率、重复率、错误归属率。
- 存储：MySQL/Qdrant 一致率、补偿成功率。
- 检索：Recall@K、MRR、NDCG。
- 注入：回答胜率、事实错误率、无关记忆注入率。

推荐实施顺序是：**一致性 Bug → 结构化记忆 → 检索重构 → 类型化注入 → 评测调参**。这套方向可以作为后续详细设计的基础。

基于“规则 + 低频 LLM”，有三种可选架构：

1. **事件驱动 + 周期巡检（推荐）**：写入后发送治理事件做轻量检查，后台再按用户/主题批量做深度整理。发现问题及时，又能处理跨会话累积。
2. **纯周期批处理**：每天统一扫描，接入简单，但错误记忆会在巡检前参与检索与注入。
3. **检索时修复**：命中时顺便检查和合并，按需成本低，但会污染在线延迟，冷门错误长期得不到治理。

推荐第一种，并将治理结果先进入隔离或待确认状态，而不是让后台模型直接物理删除记忆。

理解。已有方案解决“主链路如何正确运行”，本方案只补充**记忆写入后的持续治理与兜底机制**。

**一、整体架构**

新增独立的 `Memory Governance Plane`：

```text
记忆写入
  → 写后轻量检测
  → 正常 / 观察期 / 隔离
  → 周期性跨会话治理
  → 提升 / 合并 / 降级 / 归档 / 纠错
  → 检索前最后防线
```

采用“规则实时检查 + 低频 LLM 深度治理”，不让治理模型直接物理删除数据。

**二、抽取错误兜底**

新记忆不立即成为强可信记忆，而是经历：

```text
PROBATION（观察期）
→ ACTIVE（证据充分）
→ QUARANTINED（疑似错误）
```

提升依据：

- 用户明确陈述，可信度较高。
- 多个独立会话重复出现，增加可信度。
- AI 推断、单次临时指令默认停留在观察期。
- 用户明确否认时立即隔离，并生成纠错记录。
- 单轮抽取数量、类型分布异常时整批进入隔离区。

这样即使 LLM 抽取错误，也不会立即污染长期画像。

**三、重复记忆兜底**

当前去重只发生在单次写入附近，后续应增加用户级全量聚类：

```text
Java 是我的主要语言
我平时主要写 Java
用户长期从事 Java 开发
          ↓
Canonical Memory：用户主要使用 Java
```

治理策略：

- 定期按用户、类型、主题进行语义聚类。
- 一个规范记忆关联多条原始观察记录。
- 合并前同时检查中心相似度和两两相似度，避免链式误合并。
- 合并操作可撤销，原始证据不删除。
- 检索只返回规范记忆，避免重复占用 TopK。

**四、过期与遗忘兜底**

不能简单按时间删除，需要区分“不常用”和“已经失效”。

建议采用类型化生命周期：

| 类型 | 过期策略 |
| --- | --- |
| 用户事实 | 不自动删除，长期未确认则转为待复核 |
| 用户偏好 | 随时间衰减，新证据可重新激活 |
| 技术知识 | 按技术版本和更新时间复审 |
| 历史事件 | 保留事实，但降低默认召回权重 |
| 临时状态 | 设置明确有效期，到期自动归档 |

生命周期状态：

```text
PROBATION → ACTIVE → DORMANT → STALE → ARCHIVED
                 ↘ QUARANTINED / SUPERSEDED
```

访问次数只能代表“常用”，不能证明记忆仍然正确。

**五、跨会话碎片化治理**

核心是将“会话记忆”提升为“用户级规范记忆”。

增加两层模型：

```text
Observation：某次会话中的原始观察
Canonical Memory：跨会话聚合后的稳定认知
```

后台按用户执行周期性整理：

1. 收集最近多个会话产生的 Observation。
2. 按实体、主题、时间和记忆类型聚类。
3. 合并互补碎片，而不只是删除相似文本。
4. 将多个来源挂到同一 Canonical Memory。
5. 新会话出现变化时更新证据，不直接覆盖历史。

例如：

```text
会话 A：用户是 Java 开发
会话 B：用户在做 AI Agent
会话 C：用户准备秋招
```

可以形成多个相互关联的稳定记忆，而不是三个孤立会话片段。

**六、冲突与记忆漂移兜底**

将新旧内容视为“主张及证据”，而不是直接覆盖：

- 明确纠正：“我现在不用 MySQL 了” → 旧记忆 `SUPERSEDED`。
- 时间变化：“以前用 Java 8，现在用 Java 17” → 保留时间版本。
- 暂时变化：“这个项目临时用 Python” → 不覆盖长期技术偏好。
- 无法判断的冲突 → 标记 `DISPUTED`，暂不注入。
- 用户显式陈述的优先级高于 AI 推断和隐式行为。

**七、检索前最后防线**

即使前面治理失败，检索结果进入 Prompt 前还应执行：

- 过滤隔离、争议、过期和低健康度记忆。
- 同一规范记忆只保留一次。
- 检查当前查询是否与记忆时间范围冲突。
- 发现互斥记忆时全部暂停注入，而不是任选一条。
- 高风险事实可要求至少两条独立证据。

**八、记忆健康度**

为每条规范记忆计算治理分，而不是复用检索重要性：

```text
healthScore =
  证据可靠性
+ 跨会话支持度
+ 新鲜度
+ 一致性
+ 用户确认
- 冲突次数
- 负反馈
- 异常抽取风险
```

`importance` 决定“值不值得召回”，`healthScore` 决定“能不能相信”，两者必须分离。

**九、安全执行机制**

- 治理任务必须幂等，并使用用户级锁避免并发合并。
- 所有合并、降级、隔离和归档动作写入审计日志。
- 先以 Shadow Mode 运行，只输出治理建议，不修改数据。
- 高置信规则可自动执行；LLM 判断只生成建议或隔离。
- 设置每日用户级处理预算，避免批量 LLM 成本失控。
- 支持人工恢复、撤销合并和重放治理任务。

**十、推荐落地顺序**

1. 建立 Observation、Canonical Memory 和治理状态。
2. 上线写后异常检测与隔离区。
3. 增加用户纠错、否认和撤回入口。
4. 实现跨会话重复聚类与碎片合并。
5. 增加类型化过期、休眠和归档策略。
6. 实现冲突检测及时间版本治理。
7. 最后上线低频 LLM 治理和自动化决策。

这套方案与已有文档的区别是：已有方案关注**一次记忆如何正确流过四阶段**，本方案关注**记忆长期积累后如何持续纠错、合并、遗忘和跨会话演化**。

以“错误不扩散”为第一目标，可以有三条架构路线：

1. **控制面 + 数据面分离（推荐）**：记忆读写数据面保持简单，独立控制面负责策略版本、健康状态、熔断、隔离、灰度和回滚。侵入适中，最适合现有 DDD 与 MQ 基础。
2. **事件溯源账本**：所有观察、治理决策和状态变化只追加事件，当前记忆由投影生成。恢复和审计最强，但模型、迁移和维护成本最高。
3. **按用户分舱隔离**：以用户或租户为 Cell 划分队列、预算、索引命名空间和故障域。爆炸半径最小，但对当前规模可能偏重。

我的建议不是三选一到底，而是以第一种为主干，吸收第二种的“不可变事件账本”和第三种的“逻辑分舱”，避免一步走向过度设计。

**第一部分：系统级边界与运行模式**

建议将记忆子系统拆成四个清晰边界：

```text
业务 Agent
  ↓ 仅依赖 Memory Gateway
Memory Gateway
  ├── Data Plane：在线写入、检索、注入
  ├── Control Plane：策略、健康度、灰度、熔断、隔离
  ├── Memory Ledger：不可变事件账本
  └── Projection Plane：MySQL 当前视图、Qdrant 索引、缓存等可重建投影
```

关键变化是：Agent 不再直接相信某个检索实现，而是只调用 `Memory Gateway`。Gateway 根据用户、任务、策略版本和系统健康状态决定本次请求进入哪种运行模式：

- `FULL`：正常抽取、治理、检索和注入。
- `READ_ONLY`：暂停新增和治理，只读取已确认记忆。
- `SAFE_READ`：只允许用户明确确认、无争议的高可信记忆。
- `BYPASS`：完全绕过记忆，保证 Agent 主功能继续运行。
- `SHADOW`：新策略只计算不生效，用于对比验证。
- `FREEZE`：冻结指定用户、主题或策略版本，阻止错误继续扩散。

这里最重要的兜底不是“记忆必须始终可用”，而是**记忆不可用或不可信时，系统能够退化为无记忆 Agent，而不是带着错误记忆继续回答**。
