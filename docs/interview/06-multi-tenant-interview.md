# 多租户模型配置：面试话术（面试准备）

## 背景

项目从单一共享 API Key 演进为每用户独立配置 API Key + 模型 URL 的多租户架构。

---

## Q1：你的项目最初是怎么处理 AI 模型调用的，有什么问题？

最初的设计比较简单，就是在配置文件里写死一个 DeepSeek 的 API Key 和 Base URL，所有用户的请求都走这一个 Key。Consumer 线程数设了 2 到 4 个，本来是想控制一下并发，但问题在于——这个并发上限不是我们系统控制的，而是 DeepSeek 那边的 QPS 配额决定的。

实际跑起来有几个明显的痛点：

第一，只要用户稍微多一点，就会触发 429 限流，而且这个限流是打到所有用户头上的，A 用户超额了，B 用户也跟着等，体验很差。

第二，有些用户其实有自己的 DeepSeek Key，他们的配额是独立的，但我们系统没法利用起来，浪费了资源。

第三，从产品角度看，如果以后想做 SaaS，不同套餐用不同模型（比如免费用户用 Qwen，付费用户用 GPT-4），这种架构根本没法扩展。

所以后来我就开始想，能不能让用户自己配置 Key，做成多租户的模式。

---

## Q2：你说的"多租户"在技术上具体是怎么实现的？

核心思路是把 API Key 和模型 URL 从配置文件里拔出来，下沉到用户维度。

数据层面，新建一张 `user_model_config` 表，存储 `base_url`、`api_key`（AES-256-GCM 加密）、`model_name` 等字段，用户可以在设置页面自己配置，也可以不配，不配就 fallback 到系统默认的 Key。

调用层面，原来是启动时构建一个全局的 `InMemoryRunner`（内含固定的 OpenAiApi 实例），现在改为**每次 executeTask 时根据用户配置动态装配 Runner**。策略树（AiApiNode → ChatModelNode → RunnerNode）的节点逻辑不变，只是增加了一个判断：如果有用户自定义配置，用用户的 baseUrl/apiKey 覆盖系统默认值。

限流也要跟着调整——原来是全局令牌桶，现在拆成两层：用户自带 Key 的不受全局限流约束（配额是他们自己的），用系统默认 Key 的仍然受限。

---

## Q3：你提到每次任务动态构建 Runner，有没有性能问题？

这个我考虑过。动态装配一个 Runner 链路本质上就是几个对象的 new 操作（OpenAiApi → ChatModel → LlmAgent → SequentialAgent → Runner），没有 IO，耗时在微秒级，相比 AI 任务本身 30s~2min 的执行时间完全可以忽略。

如果想进一步优化，可以加一层 `LoadingCache<Long, InMemoryRunner>`，以 userId 为 key 缓存 Runner 实例，TTL 设 5 分钟。但需要处理缓存失效问题：用户改了 Key 后要 invalidate 对应缓存，多实例部署需要 Redis Pub/Sub 广播。

当前阶段我选择每次装配，简单可靠，等性能成为瓶颈再加缓存。

---

## Q4：这个改动和你之前做的 Outbox 模式是怎么衔接的？

Outbox 那块影响不大，因为 Outbox 解决的是"消息一定要发出去"的问题，和用哪个 Key 去调 AI 是两件事。

衔接点在于：提交任务时，我在 `ai_task` 表里多存了一个 `model_config_id` 字段——相当于做了一次"配置快照"。这样 Consumer 消费时根据 task 中的 configId 查出用户配置，传给策略树动态装配。

即使用户在任务执行期间改了 Key，也不会影响正在执行的任务（因为用的是提交时快照的配置 ID 对应的数据）。

---

## Q5：如果用户配置了一个无效的 API Key，你怎么处理？

分两种情况。

保存时：提供一个"验证 Key"的接口，用这个 Key 发一个最简单的请求（如 `/models`），4xx 就拒绝保存。

运行时：Key 之前有效后来被撤销了。Consumer 收到 401 后：
1. 不触发无限重试（和网络超时等可重试错误区分）
2. 任务标记为特殊状态（如 `KEY_INVALID`），通知用户重新配置
3. 超过重试次数进死信队列

---

## Q6：多租户之后，Consumer 并发怎么调整？

原来 Consumer 线程数设为 2~4，是为了匹配单个系统 Key 的 QPS 配额。

多租户后，每个用户走自己的 Key，系统总 QPS = 用户数 × 单 Key 配额，Consumer 线程数可以调到 20 甚至更高。真正的上限变成了机器资源（CPU/内存/网络），而不是单个 Key 的配额。

但仍然需要一个 per-user 的并发保护——防止某个用户创建大量任务占满所有 Consumer 线程，影响其他用户。

---

## Q7：安全上怎么处理 API Key 的存储？

使用 AES-256-GCM 加密存储：
- 每个 Key 单独生成 12 字节随机 IV，保证相同明文加密结果不同
- 存储格式：`Base64(IV || CipherText || AuthTag)`
- 加密密钥放在环境变量，不进代码库，生产用 K8s Secret 注入

接口层面，查询列表永远不返回明文 Key，只展示 `****xxxx`（末 4 位）。

---

## Q8：这个架构如果继续演进，你觉得下一步应该做什么？

两个方向：

第一，更细粒度的模型路由——根据任务类型选不同模型，比如普通续写用便宜模型，长文生成用更强的模型，变成策略路由。

第二，Key 生命周期管理——定期检测 Key 有效性、支持多 Key 轮询提高可用性、异常调用量告警。

---

## 关键技术点速查

| 模块 | 改动点 | 核心设计 |
|------|--------|----------|
| 用户配置表 | `user_model_config` | AES-256-GCM 加密存储 |
| 策略树 | `AiApiNode` / `ChatModelNode` | 运行时覆盖 baseUrl/apiKey/model |
| Runner 构建 | 从单例改为 per-task 动态装配 | 微秒级开销，无 IO |
| 任务快照 | `ai_task.model_config_id` | 提交时快照，执行时回查 |
| 限流 | 拆为 per-user + 全局两层 | 自带 Key 的不受全局限制 |
| Consumer | 线程数从 4 调到 20 | 多 Key 消除单 Key 瓶颈 |
