# RocketMQ 在本项目中的应用场景分析（面试准备）

## 一、MQ 在本项目中的定位

**将 AI 写作任务的提交与执行解耦，实现异步长耗时任务的可靠执行。**

```
用户点击"生成" → 毫秒级返回 taskId → MQ 异步消费 → Agent 执行 30s~2min → SSE 推送结果
```

---

## 二、为什么本项目适合用 MQ

### 核心前提：生产者和消费者不需要同步等待

| 前提条件 | 本项目是否满足 | 说明 |
|---------|--------------|------|
| 提交方不需要立即拿到结果 | ✅ | 用户提交后拿 taskId，通过 SSE 异步等结果 |
| 任务可以延迟执行 | ✅ | 晚几秒开始对用户无感（AI 本身就要跑几十秒） |
| 结果可以通过其他通道送回 | ✅ | 通过 Redis Stream + SSE 推回前端 |
| 消费端能独立处理 | ✅ | Consumer 只需 taskId，从 DB 查到所有信息即可执行 |

### 本项目场景特点

| 特点 | 为什么适合 MQ |
|------|-------------|
| AI 调用耗时长（30s~2min） | HTTP 同步等待会超时，必须异步 |
| 用户不需要盯着等 | "提交-通知"模型，用 SSE 推送结果即可 |
| 可能多用户同时提交 | MQ 天然削峰，消息排队按能力消费 |
| AI 调用可能失败 | MQ 原生支持重试（maxReconsumeTimes=3） |
| 未来需要水平扩展 | 加 Consumer 实例即可提升消费能力 |

---

## 三、MQ 承担的三个具体职责

### 1. 异步解耦

```
改造前（同步）：用户请求 → 等 60s AI 执行 → 返回结果     ❌ 超时
改造后（异步）：用户请求 → 写 DB → 返回 taskId（毫秒级） ✅ 秒回
                            ↓
                     MQ → Consumer → AI 执行 → 推送结果
```

### 2. 削峰填谷

```
瞬间 100 个用户同时提交
    ↓
MQ 中 100 条消息排队
    ↓
3 个 Consumer 实例按自身能力逐个消费（不会打爆 AI 接口）
```

### 3. 可靠重试

```java
@RocketMQMessageListener(maxReconsumeTimes = 3)  // 最多重试 3 次

// Consumer 中：
catch (RetryableAgentException e) {
    throw e;  // 抛出异常 → RocketMQ 自动重试
}
catch (Exception e) {
    // 不可恢复错误 → 标记 FAILED，不重试
}
```

## 四、不用 MQ 的替代方案对比

| 方案 | 能否满足需求 | 缺点 |
|------|-------------|------|
| `@Async` 线程池 | 部分满足 | 进程崩溃任务丢失，无法跨实例，无持久化 |
| DB 轮询 | 能满足 | 延迟高（秒级）、轮询有 DB 压力、负载均衡要自己实现 |
| Redis Stream | 部分满足 | 重试/死信/ACK 机制不如 MQ 成熟 |
| Spring Event | 不满足 | 进程内异步，不能跨实例，崩溃即丢 |

**本项目选 MQ 的决定性因素**：长耗时 + 需跨实例 + 需可靠重试 + 需水平扩展。

---

## 五、哪些场景不适合用 MQ（反例）

| 场景 | 为什么不能用 MQ |
|------|----------------|
| 用户登录验证 | 必须同步知道结果，不能"提交后慢慢验" |
| 查询接口 | 用户在等数据，异步增加延迟无意义 |
| 需要事务回滚的操作 | MQ 发出去就收不回来了 |
| 多轮对话 | 实时交互场景，用户等回复是预期行为，直连 SSE 即可 |

---

## 六、本项目中 MQ 的使用范围

| 模式 | 是否走 MQ | 原因 |
|------|----------|------|
| 快捷操作（续写/润色/大纲/配图） | ✅ | 长耗时、可异步、需重试 |
| 多轮对话 | ❌ | 实时交互，同步 SSE 流式即可 |

> **面试话术**：多轮对话是实时交互场景，用户等待 AI 回复是预期行为，用 SSE 流式直连即可；快捷操作是"提交后台任务"场景，用户不需要盯着等，所以用 MQ 异步解耦。场景不同，技术选型不同。

## 七、面试高频问题

### Q: 为什么选 RocketMQ 而不是 Kafka / RabbitMQ？

> RocketMQ 相比 Kafka 延迟更低（毫秒级 vs 批量攒包），适合任务投递场景；相比 RabbitMQ 吞吐更高，且原生支持延迟消息和重试，Java 生态友好（阿里开源，Spring Boot Starter 成熟）。

### Q: 如果 MQ 挂了怎么办？

> Outbox 表兜底。任务和 Outbox 事件在同一事务中写入 DB，即使 MQ 不可用，事件保留在 Outbox 表中。MQ 恢复后，定时任务会自动补发。

### Q: 如何保证消息不重复消费？

> Consumer 端用 **CAS 原子抢占**（`UPDATE ai_task SET status='RUNNING' WHERE id=? AND status='PENDING'`），即使同一条消息被投递多次，只有第一次 CAS 能成功，其他都 return 跳过。

### Q: 如何保证消息不丢？

> 三层保障：
> 1. **Producer 端**：Outbox 模式，事务内写 DB，定时任务可靠投递
> 2. **Broker 端**：RocketMQ 同步刷盘 + 主从复制
> 3. **Consumer 端**：处理成功才 ACK，失败自动重试

### Q: 为什么快捷操作用 MQ，多轮对话不用？

> 快捷操作是"Fire-and-Forget"模型：用户提交后不阻塞等待，结果异步推送。多轮对话是"Request-Response"模型：用户发一条消息就在等回复，同步 SSE 流式是最直接的方案，走 MQ 反而增加延迟和复杂度。
